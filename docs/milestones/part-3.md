## Milestone 48.1 — LAN remote console (phone/web thin client) + per-turn origin routing

- **What ships:** a phone/web console — `http://<pc-lan-ip>:8765/` on a phone (or any browser) — that shows Jarvis's state, lets you type and get streamed-at-completion replies, and **arm/disarm security remotely** (the case that motivated it: arming or disarming when you're not at the keyboard). LAN-only, token-gated. Plus the per-turn **origin→speak routing groundwork**: a message typed from the phone is answered in text only, never spoken aloud on the PC.
- **Architecture — thin client, brain untouched (the load-bearing bet, validated).** PC stays the only brain. A `websockets` server runs in its own asyncio loop on a daemon thread (`src/remote_console.py`); the single-page PWA is served from its HTTP handler (`src/remote_pwa.py`). Two message classes: **converse** (text → the *existing* `text_queue` seam → `process_question`, untouched) and **control** (arm/disarm/status → `SecurityWatcher.activate/deactivate` directly, **bypassing the LLM** — instant, free, reliable). Replies + state reach the phone because `RemoteBridge` is registered as a **third sink on the `JarvisUI` fan-out facade** (alongside console + tray): `set_state`/`add_user_text`/`add_jarvis_text`/`add_system_text`/`set_armed_indicator` each also broadcast. Zero changes to `process_question` or the listen loop. The observed behaviour — "type in either console, see it in both" — *is* this fan-out working as designed.
- **Locked decisions (made over the build):** LAN-only first (Tailscale = M48.4, never port-forward); **token auth even in v1** (`JARVIS_REMOTE_TOKEN`; blank ⇒ the server is never constructed — a surface that can disarm security must not exist without a deliberately-set secret; least-privilege by default); **arm + disarm both** from the phone (gated by the token; remote disarm is needed for a false alarm when you're not at the machine); **PWA not native** (client-agnostic — survives changing phone platform, no App Store/Xcode tax — the strategically right call); **multi-host troubleshooting dropped** (an explicit scope decision: a remote PC won't be diagnosed by logging in *from* it) — which *removed* the target-agnostic-protocol constraint, a simplification.
- **The per-turn origin→speak routing rule (the silent-phone-text slice).** The spec: the reply follows the request's origin/modality. Phone-text → text only (no audio anywhere); phone-voice → phone audio (M48.2/.3, pending); PC paths unchanged. This also fixed a real wart M48.1 shipped with: a phone-typed message *inherited the console text path* and made the **PC speak the reply to an empty room**. Fix: thread an explicit `origin` on the `text_queue` item (`(text, attachments, origin)`; "console" | "phone_text") and a `speak: bool` param on `process_question`, folded into the *same* silent-drain branch `mute` already used (`silent = muted or not speak`) — one branch, no new code path. Phone-text is silent **by origin, independent of the global mute toggle** (a locked decision: mute = "PC stays quiet"; the phone is a separate sink — so phone-voice audio, M48.2, will also be independent of PC mute).
- **websockets 16.0 API (recorded so it isn't re-derived):** server = `websockets.asyncio.server.serve(handler, host, port, process_request=…)`; `process_request(connection, request) -> Response | None` (return a `websockets.http11.Response(status, reason, Headers, body_bytes)` to serve the PWA, `None` to let the WS path upgrade); handler is `async def h(conn)` with `conn.recv()` / `conn.send()`. Cross-thread broadcast: capture the loop, `loop.call_soon_threadsafe(...)` → fire-and-forget `create_task(conn.send(...))` (a slow client must not block the loop or other clients). Auth = `hmac.compare_digest` (constant-time; the token is never logged).
- **Bugs caught + the diagnostics that caught them (measure, don't assume — the session's throughline):**
  - The **loopback smoke test caught a real structural bug**: a follow-up edit adding the `set_on_text`/`set_on_control` methods had orphaned `__init__`'s tail attribute assignments into `set_on_control` — *valid syntax, so `py_compile` passed*, but `_clients`/`_snapshot`/`_loop` were never initialized. Only an actual connect attempt surfaced it. A compile gate is necessary, not sufficient; a behavioral smoke test earns its keep.
  - **"No `[remote] listening` line" live-diagnosed to the right cause:** the log showed `[remote] JARVIS_REMOTE_TOKEN unset — remote console disabled` (so the new code WAS running, branch identified) — the token simply wasn't in the real `.env` (it had been added to `.env.example` only, by adjacency confusion). Other `.env` vars working ≠ this one present; verifying the actual `.env` (key-grep, value masked) was the definitive step, not theorizing.
  - **`grep` tripping into binary mode on `jarvis.log`** (embedded non-UTF-8 bytes) silently truncated results and nearly produced a wrong "last started 2026-05-15" conclusion. **Always `grep -a` (force text) on jarvis.log.** Reusable operational fact — applies to *every* future log diagnosis, not just M48.
  - **Defensive defect introduced + fixed:** `from src.remote_console import …` was *outside* the try/except in main.py — a missing `websockets` would have been an unhandled ImportError at startup, violating the "an optional component must never break the listening loop" contract. Moved inside the try.
- **What's NOT in M48.1 (deferred, by an explicit sequencing decision):** audio. No TTS *to* the phone, no phone mic. That's the harder half (phone-voice → phone-audio) and gates on a **mobile-Safari audio spike** (capture + iOS autoplay/user-gesture playback) — a throwaway on a real device *before* architecting M48.2/.3 around the only genuine unknown. Also deferred: token-streamed (vs at-completion) replies; per-device pairing (M48.4 with Tailscale); off-LAN access (M48.4 Tailscale, never port-forward).
- **Validation.** Loopback smoke test (auth ok/fail, converse→seam, arm/disarm→watcher+broadcast, thread-safe fan-out, HTTP PWA/manifest/404) all pass after the structural-bug fix. **Live-validated on a real phone over LAN (2026-05-19):** type↔reply both ends, arm/disarm reflected on PC + phone badge, silent-phone-text confirmed (phone text → PC silent; console text → PC still speaks; PC voice → still speaks).
- **Files:** `src/remote_console.py` (new — WS+HTTP server, JSON protocol, token auth, thread-safe broadcast), `src/remote_pwa.py` (new — single-page PWA, iOS add-to-home meta + manifest, token-in-localStorage, auto-reconnect on visibilitychange), `src/ui.py` (RemoteBridge as 3rd fan-out sink + `set_remote` + defensive `_remote_call` + `import sys`), `main.py` (token-gated server construction with on_control→SecurityWatcher, late on_text wiring in listen_loop, the `(text,attachments,origin)` queue tuple + `speak` thread through `process_question`, import-inside-try fix), `src/config.py` (`remote_token`/`remote_port`/`remote_bind`), `.env.example` (M48 block + security posture), `requirements.txt` (`websockets>=13.0`, dep-asymmetry rationale); `CLAUDE.md`; this entry.

### M48 mobile-audio spike — findings & roadmap reorder (2026-05-19)

A deliberately **throwaway** de-risk spike (a `/spike` route + `src/spike_audio.py` + a `SPIKE_HTML` page, all since **deleted** — the value of a spike is the *findings*, not the code; "throwaway leaves knowledge, not scratch"). Run on a real device — **iPhone, MS Edge** (which on iOS *is* WebKit; Apple mandates it — Edge-on-iOS ≠ Chromium Edge, so this measured the true Safari/WebKit wall). Loopback-proven first (route/auth/dispatch/real-faster-whisper-decode/playback), then the two unknowns measured on-device:

- **Playback (M48.2): WORKS.** A `<audio>` element fed a `data:audio/mpeg;base64,…` URL plays on iOS Edge/WebKit, **with the hardware silent/ring switch ON *and* OFF**. The Web Audio `AudioContext` path also plays but is the textbook iOS trap (silenced by the ring switch, "succeeds, no sound"). **Decision: M48.2 plays via an `<audio>` element**, not raw Web Audio. Conscious property flagged: Jarvis-on-phone will speak even when the phone is on silent — desirable for "you asked, you hear the answer," but a deliberate choice, not an accident.
- **Capture (M48.3): BLOCKED by secure-context, exactly as predicted.** On a plain `http://<lan-ip>:8765` origin the capability readout was `secureContext:false`, `mediaDevices:false` → iOS WebKit refuses `getUserMedia` entirely on an insecure origin. No code can capture the mic over plain-http LAN. **But the useful half:** `MediaRecorder:true`, `audio/mp4:true`, `audio/webm:true`, `webm;opus:true` — once a secure context exists, recording works and supports modern codecs; faster-whisper (loopback-proven decoding via PyAV) handles either. **→ codec/transcode is a non-issue; the *only* blocker is secure-context.**
- **Interaction finding (bonus):** press-and-hold on a `<button>` triggers iOS text-selection/callout/magnifier (long-press = a system gesture). **M48.3 push-to-talk must be tap-to-start/tap-to-stop (a toggle), not press-and-hold**, plus `-webkit-user-select:none; -webkit-touch-callout:none; touch-action:none`.

**The payoff — the roadmap reorders, evidence-driven (the whole reason to spike):** secure context is now a **hard prerequisite for capture**, so the work order changes:
1. **M48.2a** — the OPEN per-session tool-capability boundary (security gap from M48.1; independent of audio; do first).
2. **M48.2b** — TTS→phone `<audio>` output sink + per-turn audio routing (no secure context needed; playback proven).
3. **Tailscale — pulled forward from M48.4 to here, now a prerequisite.** `tailscale cert` yields a *real, trusted* Let's-Encrypt cert on a `*.ts.net` name → an HTTPS secure context with **zero iOS cert-install friction** (a self-signed LAN cert needs a per-device trusted profile — the worse path), and it *simultaneously* delivers the off-LAN access M48.4 always wanted. One move, two goals.
4. **M48.3** — phone push-to-talk (now possible: secure context ✓, codec ✓), **tap-toggle UX**.

**Reusable lessons:** (1) iOS = WebKit for *every* browser (Edge included) — measure the WebKit wall, don't assume the browser escapes it. (2) `getUserMedia`/mic requires a **secure context** (HTTPS or localhost) — plain-http LAN can never capture; design mobile-capture features HTTPS-first. (3) `<audio>` element (gesture-triggered) ignores the iOS ring switch; Web Audio `AudioContext` does **not** (silent-success trap) — for clip playback prefer `<audio>`. (4) iOS long-press = selection/callout — push-to-talk = tap-toggle, not hold. (5) A spike's deliverable is the *decision*; delete the code, keep the knowledge. **Files:** (spike code created then deleted) — net change is docs only; `CLAUDE.md` (Next + M48 roadmap reorder), this entry.

## Milestone 48.2a — per-session tool-capability boundary (closes the M48.1 OPEN security item)

- **The gap it closes:** M48.1 threaded a phone `origin` for the TTS gate but NOT a tool filter, so a phone-typed message reached `process_question` → `stream_response` with the **full toolset** (`system_control`, `pc_shell`, the collector, `plex_action`, plus the read-only-but-sensitive `read_local_file`/`screen_snapshot`/`camera_snapshot`). Practical risk was low (token-gated, LAN-only, single operator) but it was a *deliberate locked decision* left unbuilt — flagged ⚠️ OPEN across CLAUDE.md and the M48.1 entry for the whole arc. This is the explicit "surface it, don't let an accepted risk go unconscious" item, now resolved.
- **What ships:** a RESTRICTED capability profile for phone-origin turns, **enforced server-side, two gates, never prompt-only** (the diagnostic-vs-action split and least-privilege-by-default rules, applied):
  1. **Primary gate** — `stream_response` filters the `tools` list by schema name against `_RESTRICTED_DENY` *after* all extends, so a phone turn is **never even offered** the denied tools (verified 19→12; the 7 removed are exactly the locked BLOCK+EXCLUDE set; covers built-ins, the SSH family's `plex_action`, and dynamic Plex-MCP names uniformly).
  2. **Defense-in-depth gate** — `_execute_client_tool(restricted=True)` refuses a denied name *by name* even if one reaches it anyway (model quirk, prompt injection from the phone, a future path), returning a readable refusal instead of executing.
  3. **Graceful UX (not enforcement)** — a `build_system_prompt(remote_restricted=True)` addendum so Claude says "not available from the remote console, here's what I can do" instead of promising a tool then failing. Cosmetic; the boundary holds even if the prompt were ignored.
- **`speak: bool` → `origin: str` (the right refactor, not just a filter).** `process_question` now takes `origin` (`voice`|`console`|`phone_text`|future `phone_voice`) and derives BOTH `speak` and `restricted` from it. They're separate axes — phone-voice (M48.3) will `speak=True` *and* `restricted=True` — which the prior single bool structurally could not express. The queue already carried `origin`; this just stops collapsing it to a bool too early.
- **The proof that matters — provably non-regressive for PC.** The loopback test asserts the unrestricted system prompt is **byte-identical** to before and unrestricted dispatch executes normally. M48.2a is purely additive for the phone; PC voice/console are untouched (no behavior drift, no prompt-cache churn — the addendum stays in the cacheable prefix only when restricted). Deny-set asserted typo-free (every name matches a real tool — a typo'd deny entry would be a silent hole).
- **What's NOT in it:** no audio (M48.2b), no Tailscale (M48.3 prereq). Pure boundary. The Plex MCP read/playback tools and `pc_diagnostics`/`plex_laptop_health`/logs (read-only) deliberately stay allowed on the phone — useful from a remote, not dangerous.
- **Validation:** `py_compile` gate; loopback boundary test ALL PASS (filter 19→12 removes exactly the deny-set & keeps the safe/read tools; `restricted+system_control`→refusal; `restricted`+non-denied→passes through; `unrestricted+system_control`→gate OFF/executes; system prompt unrestricted byte-identical, addendum only when restricted). **Live-validated 2026-05-19:** phone "flush my DNS" → declined + redirected (not attempted); phone weather/knowledge → works; PC voice "flush DNS" → still works.
- **Files:** `src/llm.py` (`_RESTRICTED_DENY` frozenset + `_REMOTE_RESTRICTED_ADDENDUM`; `build_system_prompt(remote_restricted=)`; `_execute_client_tool(restricted=)` deny double-gate; `stream_response(restricted=)` → prompt + tools filter + dispatch thread); `main.py` (`process_question` `speak`→`origin`, derives `speak`+`restricted`, 2 call sites, `restricted=` to `stream_response`); `CLAUDE.md` (⚠️OPEN→CLOSED strike, Next, roadmap); this entry.

## Milestone 48.2b — phone reply audio + reconnect hardening (the "Speak replies" toggle)

- **What ships:** an opt-in **"Speak replies"** toggle on the PWA (default OFF, persisted per device in `localStorage`). With it ON, a phone-typed turn returns text **and** a synthesized MP3 reply that plays through the **phone's** `<audio>` element — *unicast* to the originating phone, never the PC, never another phone. Off = today's silent-phone-text behaviour, unchanged.
- **The per-turn audio routing — separate axis from speak/restricted (the locked decision honoured).** `on_text` becomes `(text, reply_audio)` where `reply_audio` is a thread-safe closure bound to *this* WebSocket conn or `None`. `process_question` takes it through, derives `pc_silent = silent or reply_audio is not None` (so the PC speaker stays quiet when the audio goes to the phone instead — never an empty-room speak), then after the reply is fully drained, lazy-imports `_fetch_mp3` + `VOICE_BY_LANG`, synthesizes once at the end-of-turn, and unicasts the bytes. **Phone audio is independent of the PC mute toggle** — locked at M48.1, honoured now: PC mute = "PC stays quiet"; the phone is a separate sink governed by its own toggle. The M48.2a `origin` axis stays clean: phone-voice (M48.3) will *speak through the phone* yet *be restricted*, both flags falling out of one origin string.
- **iOS audio: evidence-driven, no Web Audio acrobatics.** A real-device spike (M48 spike entry above) established that `<audio>` element playback works on iOS WebKit including with the silent switch ON; Web Audio `AudioContext` does not. M48.2b uses `<audio>` — a fresh `data:audio/mpeg;base64,…` URL per reply, `loop=false`, hard-paused before each new src to play the clip **exactly once**. Earlier iterations tried a silent-WAV keepalive (iOS rejected with `NotSupportedError`) and an `ended`→re-prime (which replayed the reply on a lock-screen loop until manually paused); both removed — the evidence says don't fight the platform. The current code does only a file-free `AudioContext.resume()` warm on the gesture (harmless) and otherwise hands iOS native MP3.
- **The iOS "one tap per session, then seamless" pattern (this is by design, not a regression).** iOS requires an `<audio>` element to *successfully* `.play()` from within a user gesture once before it can play from a non-gesture (deferred-reply) callback. So on the first reply after a fresh page load, `<audio>.play()` rejects with `NotAllowedError` and the PWA shows a calm `🔊 Reply ready — tap ▶︎ below to hear it.` line + an unhidden **"▶︎ Tap to hear reply"** button (the audio-side analog of every "ship the reliable manual path" decision in this project). **Tapping ▶︎ unlocks the element for the rest of the session** — subsequent replies play automatically with no tap. Pay one tap per session, not per reply; HTTPS + Add-to-Home-Screen (after Tailscale) loosens the gesture rules further, which is where seamless autoplay properly lands.
- **Reconnect hardening (companion fix, browser-agnostic).** Edge on iOS exposed a real client-state bug while testing M48.2b: a `WebSocket` stuck in `CONNECTING` (readyState 0) fires neither `onopen` nor `onclose`, and iOS *routinely* leaves a post-resume handshake wedged in exactly that state. The previous `dial()` guard (`readyState===0 ⇒ skip`) then treated the zombie as "a connect is in flight" forever — the pill froze on `connecting…`, no retry, no token prompt, no recovery short of a cache clear (the "won't reconnect after closing the browser" report). Fix is *structural*, not a guess about iOS internals: a **per-attempt connect watchdog** (`CONN_TIMEOUT_MS = 6000`) force-closes any socket still in `CONNECTING` past the timeout — which fires `onclose` → the existing backoff retry — and the guard now only skips on `OPEN` or *watched* `CONNECTING`. Live-validated in Edge ("connection timed out — retrying", reconnected ~6 s later — the watchdog firing exactly as designed). Plus a **tap-to-reconnect status pill** as the guaranteed manual recovery (a fresh user-gesture WebSocket creation that iOS lets through even when background JS is throttled — the reconnect analog of the audio ▶︎ button).
- **Engine-vs-app-shell — refining the WebKit lesson.** "iOS = WebKit for every browser" is true for the **engine + media stack** (audio behaved identically in both browsers; same playback gestures, same `<audio>` semantics). It does **not** cover the **app-shell layer**: page lifecycle, background-tab freezing, and bfcache restore are implemented by *each browser app's own code* wrapping `WKWebView`. **Safari has Apple's first-class lifecycle integration** — closing the tab/app often leaves the page suspended with the WS still alive; you return and it's already connected, no reconnect at all. **Edge (and Chrome) on iOS** are third-party app wrappers — same engine, *materially weaker* bfcache + background behaviour. That's why the same M48.2b build needed structural reconnect hardening for Edge while Safari was clean out of the box. **Outcome: Safari is the blessed/supported client (Add-to-Home-Screen recommended); Edge is best-effort with the tap-pill as recovery.**
- **"Presence ≠ valid" institutionalized as `scripts/js_parse_gate.py`.** A bad Edit during this milestone left a duplicate `function setSpk()` in the PWA — `py_compile` passed (valid Python raw string), substring smoke checks passed (the text we looked for *was* present), but the browser threw `SyntaxError` and the whole console went dead. A grep for "is it there?" cannot catch "is it well-formed?". `node --check` is the right tool but `node` isn't installed on this box, so the gate is a deterministic comment/string/template-aware brace/paren balancer plus regression-specific invariants (one of each function, watchdog present, no stale silent-WAV keepalive, no audio-loop, bootstrap ends with `dial();`). Cheap, deterministic, runs in milliseconds, lives next to `leak_repro.py` — the same "build the instrument so future you doesn't have to guess" discipline as the M44.3 leak harness.
- **Validation:** `python -m py_compile main.py jarvis.pyw src/*.py` → PASS; `python scripts/js_parse_gate.py` → PASS (structure balanced; 1× each function; watchdog + clearWD + tap-pill present; bfcache + online handlers kept; no loop). Serve-shape: server imports + `_http()` returns 200 / 14776 B with the reconnect machinery confirmed in the served bytes. **Live-validated on a real iPhone 2026-05-19:** Safari — audio plays through the phone (silent ON+OFF), reconnect not even needed (page stays suspended with WS alive); Edge — audio same; reconnect-after-close auto-recovers via watchdog in ~6 s ("connection timed out — retrying" → connected); manual tap-pill works as the always-available fallback; OFF → text-only silent everywhere; PC voice + console + the M48.2a boundary all unaffected.
- **What's NOT in it:** no zero-tap autoplay (one-per-session unlock is the iOS reality on http-LAN — seamless lands with HTTPS via Tailscale + Add-to-Home-Screen); no phone mic (M48.3 — push-to-talk, gates on secure context); no Tailscale yet (the prerequisite for the *next* increment, not this one).
- **Files:** `src/remote_console.py` (`on_text` contract `(text, reply_audio)`; `_send_audio()` thread-safe unicast `{type:"speak", mime:"audio/mpeg", b64:…}` via `call_soon_threadsafe`; `_dispatch` reads `{speak: bool}` per-message and binds `reply_audio` to *this* conn); `src/remote_pwa.py` (the "Speak replies" toggle + persisted state; `<audio id="ae">`; `playReply` / `onPlayBlocked` / "▶︎ Tap to hear reply" button; `connWD` watchdog + `clearWD` + revised `dial()` guard; tap-to-reconnect pill; bfcache `pageshow`/`persisted` + `online` redial paths kept); `main.py` (`text_queue` item `(text, attachments, origin, reply_audio)`; `process_question` accepts `reply_audio` & `origin`, derives `pc_silent`, end-of-turn `_fetch_mp3` + `reply_audio(mp3)`); `scripts/js_parse_gate.py` (new — institutionalized structural JS gate); `CLAUDE.md` (Next + roadmap: M48.2b done, Tailscale next); this entry.

**Reusable lessons:** (1) **Engine ≠ app shell on iOS.** "Same WebKit" covers rendering/JS/media; it does NOT cover lifecycle, bfcache, or background-tab freezing — those are the browser *app's* code. Safari is materially better than Edge/Chrome there. Don't measure Edge and conclude "WebKit is broken." (2) **A WebSocket stuck in `CONNECTING` is silent forever** — no `onopen`, no `onclose`, no `onerror`. Any retry strategy that relies on `onclose` will deadlock; you *must* add a per-attempt timeout watchdog. (3) **iOS `<audio>` user-activation persists for the page lifetime** — one successful gesture-time `play()` unlocks the element for the whole session, *not* one per clip. Ship one-tap-per-session as the honest done-bar on http-LAN; chase zero-tap only when HTTPS + home-screen-install changes the gesture rules. (4) **iOS rejects synthetic-WAV `<audio src=…>`** with `NotSupportedError` — MP3 is the only safe `data:` mime for `<audio>`. (5) **"`presence ≠ valid`" — a duplicate function or unbalanced brace passes `py_compile` and substring smoke tests, kills the browser silently.** Build a real structural gate the first time it bites; reuse it forever (the same lesson as the M44 leak harness — when you can't reproduce on demand or eyeball-trust, build the instrument). (6) **Manual recovery beats invisible auto-recovery on hostile platforms.** A tap-to-reconnect pill + a tap-to-play ▶︎ button cost one widget each, work 100 % of the time, and pair perfectly with structural auto-fixes that mostly work but can't guarantee.

## Milestone 48.2c — Tailscale HTTPS for the remote console (the four-wins prerequisite)

- **What ships:** opportunistic TLS on the remote-console listener, gated on two new `.env` paths (`JARVIS_TLS_CERT_FILE` + `JARVIS_TLS_KEY_FILE`). Both set + both files present ⇒ `serve(ssl=ssl.SSLContext(...))` and the single port speaks **HTTPS for the PWA fetch AND WSS for the WebSocket upgrade**; either missing or unreadable ⇒ the server logs the precise reason and falls back to plain HTTP/WS (today's LAN-mode behaviour) — same optional-component contract as every other M48 subsystem (a misconfigured cert MUST NOT crash Jarvis). The PWA needs zero client-side changes: `location.protocol === "https:" ? "wss" : "ws"` was already in the connect() code from day one, so the browser sees `https://…` and self-upgrades to `wss://…`.
- **Why this milestone exists — the four wins, all from one secure-context flip.** Plain-http LAN was a hard wall against everything ahead of M48.3:
  1. **Secure context unlocks `getUserMedia`** — iOS WebKit refuses mic access on insecure origins, *period*. Without HTTPS, **M48.3 push-to-talk is structurally impossible.** This is the unlock the M48 spike (see entry above) measured directly and named as the gating constraint.
  2. **iOS `<audio>` gesture rules relax on secure context** — the one-tap-per-session ▶︎ unlock that M48.2b shipped as the honest http-LAN done-bar becomes zero-tap (live-verified on the test device: first reply plays automatically, no manual tap, the "Tap to hear reply" button never even surfaces).
  3. **PWA Add-to-Home-Screen gets a proper app lifecycle** — Apple only grants chromeless-PWA + first-class lifecycle to HTTPS pages. Reconnect behaviour markedly cleaner (verified on the test device: closing/reopening the home-screen icon reconnects on its own; tab-mode's bfcache fragility is gone).
  4. **Off-LAN access** — same URL, same token, works on cellular through Tailscale's encrypted WireGuard tunnel. The original "phone away from the LAN" goal of M48, delivered.
- **The "Tailscale, not dynamic-DNS + port-forward" decision recorded properly.** The Jarvis remote console can DISARM security and (until M48.2a) wielded the full tool surface — a categorically higher risk class than the other homelab apps that ride a dynamic-DNS name + a router port-forward. **No public exposure for it** (least-privilege applied at the network layer). Tailscale's `*.ts.net` MagicDNS + `tailscale cert`'s real Let's Encrypt-backed cert deliver HTTPS *without ever opening a port to the public internet*; iOS trusts the cert with zero device profile install. The pre-existing dynamic-DNS + port-forward setup STAYS for the lower-stakes media apps (Sonarr/Radarr/etc. — don't disrupt working infra). **Migrating the rest of the homelab onto Tailscale is a separate future project, not M48 scope** (a stated intent once the pattern is comfortable; do not scope-creep it in).
- **Three-layer live test before code touched the server.** Tailscale was installed on both PC + phone, then the tunnel itself was measured end-to-end *before* trusting the new code: (L1) both devices "Connected" in the admin console; (L2) Tailscale IP reachable from the phone-on-Wi-Fi via `http://100.x.y.z:8765/` to the still-LAN-mode Jarvis (proves the tunnel + Jarvis-through-tunnel both work); (L3) **Wi-Fi off, cellular only** — same URL still loads, which is what distinguishes "Tailscale really did the work" from "Wi-Fi happens to work and Tailscale was passive". L3 = the off-LAN proof. All three passed on first try; only then did the SSLContext plumbing go in. **This three-layer pattern is the right template for any future network-substrate migration** — never assume the tunnel works because the install completed.
- **The asyncio noise filter (a small bonus close-out cleanup).** First HTTPS boot surfaced three cosmetic `ConnectionResetError [WinError 10054]` tracebacks at startup, before the first real connection. Cause: iOS Safari's TLS handshake opens 2-3 probe sockets in parallel (HTTP/2 connection pool warm-up, OCSP fetch, ALPN attempts) and abruptly closes the ones it doesn't end up using; the remote-side RST hits asyncio's Windows `ProactorEventLoop` `_call_connection_lost` callback, which calls `socket.shutdown(SHUT_RDWR)` on the already-gone socket and raises. **Already-handled inside asyncio**, but the default exception handler still logs the traceback → recurring log bloat over time. Fixed with a surgical `loop.set_exception_handler` that swallows *specifically* `ConnectionResetError` whose `context["message"]` names `_ProactorBasePipeTransport._call_connection_lost`. Any other exception type, OR the same exception in any other callback, still propagates to `default_exception_handler` — we don't blind ourselves to real bugs. Behaviourally smoke-tested: the cosmetic case is swallowed, two negative cases (different callback, different exception type) propagate.
- **What's NOT in it:** no auto-reload on cert renewal (Tailscale renews every ~60 days; re-run `tailscale cert` + restart Jarvis at the next quarterly cadence — documented in `.env.example`; auto-reload is a clean follow-on if the manual rhythm ever bites). No HTTP→HTTPS redirector (the LAN-mode HTTP path is gone once `.env` is set; the new URL is learned once). No cert pinning, no client-cert auth (the token + Tailscale's tailnet boundary are the controls). No coverage of the rest of the homelab (separate future project, explicit decision).
- **Validation:** `python -m py_compile main.py jarvis.pyw src/*.py` → PASS; `python scripts/js_parse_gate.py` → PASS (no PWA changes; rerun confirms no drift). Plumbing smokes: server constructs with `ssl_context=ctx` AND with `ssl_context=None` — both paths clean. Noise-filter behavioural smoke: 3/3 cases (swallow Proactor reset; propagate same exception in different callback; propagate different exception in same callback). **Live-validated on a real iPhone 2026-05-19:** boot log shows the new HTTPS/WSS line; cert trusted (no browser warning, padlock); token prompt → console connects on HTTPS; **reply audio is zero-tap** (the iOS gesture rules relaxed — the M48.2b accepted UX limitation is lifted as predicted); **Add to Home Screen works**, opens chromeless, reconnect cleaner than in tab mode; **cellular-only test passes** (Wi-Fi off, Tailscale on, same URL still works — off-LAN proof). Four deliberate disconnect/reconnect cycles in the log all completed cleanly (no stuck-`CONNECTING`, no watchdog firing) — M48.2b's structural reconnect hardening still in place but rarely needed once HTTPS + PWA lifecycle is in play.
- **Files:** `src/config.py` (two new fields `tls_cert_file` / `tls_key_file`, read from `JARVIS_TLS_CERT_FILE` / `JARVIS_TLS_KEY_FILE`); `src/remote_console.py` (`__init__` accepts `ssl_context: ssl.SSLContext | None`; `_main` passes `ssl=` to websockets `serve()`; startup log line distinguishes HTTPS/WSS vs HTTP/WS modes explicitly; new `_swallow_proactor_resets` exception handler installed on the daemon loop); `main.py` (opportunistic `SSLContext` construction with graceful fallback — half-config / missing-file / `load_cert_chain` failure each log a precise reason and degrade to HTTP); `.gitignore` (`*.crt` / `*.key` / `*.pem` / `tls/` belt-and-suspenders — the cert pair lives in `%LOCALAPPDATA%\Jarvis\tls\` outside the repo, but the patterns catch any accidental path drift); `.env.example` (the new vars + the four-wins rationale + the `tailscale cert` recipe + the auto-renewal note); `CLAUDE.md` (status; Next; roadmap struck — M48.2c done, M48.3 push-to-talk now unblocked); this entry.

**Reusable lessons:** (1) **The right way to migrate a service onto a new network substrate (Tailscale, Cloudflare Tunnel, ZeroTier, etc.) is three layers: tunnel-up, reachable-on-LAN, reachable-off-LAN-only.** L1 (admin console green) proves the tunnel is up. L2 (Wi-Fi on, tunnel URL works) proves the tunnel + the service-through-tunnel both work, but doesn't prove the tunnel is doing the work. L3 (Wi-Fi off, tunnel URL still works) is the only test that proves the tunnel is actually carrying the traffic — otherwise "it works" could be Wi-Fi LAN routing through coincidence. Never collapse those three into one "let me hit the URL" test. (2) **`tailscale cert` is the right answer for personal-scale HTTPS on a service that should never be public.** Real Let's Encrypt cert, automatically trusted by iOS/Android/Safari/Chrome, MagicDNS hostname, zero port-forwarding. Self-signed LAN cert is the worse alternative (per-device profile-install friction; training people to click through "untrusted" warnings is a security regression). Public DDNS + port-forward is wrong for a security-controlling service (categorically higher risk class than media-server apps). (3) **The graceful-fallback contract works when it's *surgical* about *why* it fell back.** Three explicit conditions in `main.py` (half-config / files-missing / `load_cert_chain` raised) each log a different specific reason at fallback time, so a misconfigured `.env` is debuggable in one log line. Don't write a single `except Exception` that swallows TLS into "fell back to HTTP" — that costs an hour of confusion later. (4) **Cosmetic noise IS a real cost over time** — a once-per-reconnect traceback × every page reload × every iOS app-switch for a year = significant log bloat (and pollutes grep). When you find one, fix it surgically (match the specific exception type + callback) — never blanket-suppress, or you blind future-you to real bugs. (5) **A small post-shipped cleanup belongs in the close-out, not in the next milestone.** The asyncio noise filter is 8 LOC and would be 8 LOC of pointless drift if deferred. The milestone's "everything that surfaced during shipping" includes the cleanup that surfaced because of shipping.

## Milestone 48.3 — phone push-to-talk (the phone as a remote mic)

- **What ships:** a mic button on the PWA that turns the phone into a remote microphone for the unchanged PC brain. Tap to start recording, tap to stop (the spike's locked finding: iOS long-press = selection/callout, so it MUST be tap-toggle, never press-and-hold); the recorded clip ships to the PC, gets transcribed through the *existing* whisper pipeline, and the answer comes back as text **and** auto-played audio. With M48.1 (text) + M48.2b (reply audio) + this, the phone is now a full thin terminal — type, talk, listen, see state, arm/disarm — to a PC brain that still has no idea the phone exists.
- **The wire format — symmetric with M48.2b.** A new authenticated-WS message `{type:"audio", mime, b64}`: the `MediaRecorder` Blob, base64-encoded. Reuses the existing token-auth boundary (no new HTTP endpoint, no second auth model); base64's ~33% overhead is trivial for a few-second voice clip. M48.2b already does base64-audio-over-WS *outbound* (the reply MP3); this is the same pattern *inbound*. One protocol, one debug surface.
- **The STT shim — one pipeline, two sources (no parallel STT).** The phone's `MediaRecorder` emits a compressed container (Safari = `audio/mp4`/AAC; others = `audio/webm`/Opus), but the existing `_dispatch_transcription` expects int16 mono 16 kHz numpy. New `speech_to_text.transcribe_blob()` decodes the container → PCM via **PyAV** (already a `faster-whisper` transitive dep — no new requirement; the container is auto-detected from the bytes, we don't trust the client MIME) then hands off to the *unchanged* `_dispatch_transcription`. **The payoff: M36 GPU offload applies to phone voice for free** — a phone clip rides the same remote STT server as the PC mic, ~250-500 ms instead of seconds. Decode failure ⇒ empty `Transcript` ⇒ the turn is dropped, never a stack trace at the client.
- **`origin="phone_voice"` — the routing matrix already had the row.** The transcribed text goes onto the *same* `text_queue` the brain already drains, tagged `phone_voice`. M48.2a/M48.2b had already built the matrix: `phone_voice` ⇒ `restricted=True` (the M48.2a tool-capability boundary applies — a voice command from the phone can't `pc_shell`/`system_control`/etc.) and `pc_silent=True` (the reply audio unicasts to the phone, the PC speaker stays quiet — no empty-room speak). Transcription runs on a **daemon thread**, never the WS loop (whisper can take seconds; the server loop must never block).
- **`text_queue` grew a 5th field — language.** Typed input has no detectable language (it was typed into a box); phone voice DOES — whisper returns `detected_language` with every transcript. The queue item became `(text, attachments, origin, reply_audio, lang)`; typed producers pass `"en"`, the phone-voice producer passes the whisper-detected ISO code. So *"¿qué hora es en Japón?"* spoken into the phone gets a Spanish reply in the Spanish voice (`es-MX-JorgeNeural`) — the multilingual capability the project has been wired for since M2, now reachable from the phone. **Live-validated in Spanish.**
- **Locked UX decision — voice-in always returns voice-out.** Set during scoping: pressing the mic ALWAYS yields an audio reply, regardless of the "Speak replies" toggle (which continues to gate phone-*text* only). Simplest mental model — "if I pressed the mic, I want to hear the answer." The server sets `reply_audio` unconditionally for `audio` messages. Less coupling, fewer "why isn't he speaking back?" surprises.
- **Two fixes after the first on-device test (the milestone's real engineering).** v1 shipped working but the first real test surfaced two issues, both fixed in v2:
  1. **The reply audio fell back to the ▶︎ button instead of auto-playing.** Root cause: iOS requires an `<audio>` element to have a *successful gesture-time `play()`* once before it can play from a deferred (reply-arrived-seconds-later) callback. M48.2b's `primeAudio()` only resumes the Web Audio `AudioContext` — it does NOT user-activate the `<audio>` *element*. M48.2c's "zero-tap" worked in the home-screen PWA but the Safari TAB path is stricter. **Fix:** the server generates a ~200 ms silent MP3 once at startup (via PyAV; ~1.2 KB; `None` + graceful ▶︎-fallback if the MP3 encoder is absent) and serves it at `/silence.mp3` (immutable/cacheable); the PWA plays it on the `<audio>` element *inside the mic-start tap gesture* → the element is user-activated → every subsequent reply that session auto-plays. iOS rejects synthetic *WAV* `data:` URLs (`NotSupportedError`, the M48.2b lesson) but accepts MP3 — and we serve a real file, not a base64 `data:` URL, after an embedded-base64 attempt hit a padding bug (the file route is cleaner anyway: no giant string in source, browser-cached). Fired exactly once per mic-start; **no `ended`→re-prime loop** (the M48.2b regression we explicitly designed against).
  2. **The `⏳ Transcribing…` state flashed by invisibly.** v1 reset the mic button to idle when the *upload* finished — but with M36 GPU offload that's ~300 ms, too fast to see. **Fix:** the mic stays in `⏳ Transcribing…` until the server fans the transcribed `user` line (or a `system` line on no-speech) *back* to the phone — THAT is the honest "Jarvis received it, working on it" signal. A 30 s safety timer resets the button if no transcript ever arrives.
- **The iOS permission reality — documented, not fixable.** iOS does **not** persist `getUserMedia` permission across launches — not for a Safari tab, and (surprising, but confirmed on iOS 26.5 / iPhone 17 Pro Max as the test platform) **not even for an installed home-screen PWA**. There is no web API that can change this; permission persistence is entirely the OS's call. The one mechanism that creates a standing grant is the OS setting: **Settings → Apps → Safari → Microphone → "Microphone Access On All Websites" → Allow** (iOS 26 consolidated the old per-site preference into this single global Ask/Deny/Allow toggle). With that set, the prompt is gone. **This is a required one-time setup step for push-to-talk, recorded here and in the README/`.env.example` lineage** — same shape as every other iOS-edge decision in M48 (the audio ▶︎, the reconnect tap-pill): the platform imposes a tax, we document it and move on rather than fighting a wall Apple built (fighting it would mean a native Swift wrapper — the App Store / Xcode tax the project rejected when it chose PWA).
- **What's NOT in it:** no audio level meter while recording (deferred); no voice-activity / silence-based auto-stop (the contract is tap-to-stop — explicit, predictable); no streaming transcription (whisper's `model.transcribe()` is end-of-clip only — not a streaming API); no state-indicator pill on the phone (still the deliberately-deferred cosmetic M48.X follow-on — "walk before we run"). 60 s hard recording cap (longer = two prompts).
- **Validation:** `python -m py_compile main.py jarvis.pyw src/*.py` → PASS; `python scripts/js_parse_gate.py` → PASS (extended with 9 push-to-talk invariants — one of each mic function, the `{type:"audio"}` wire contract, the 60 s cap, the `/silence.mp3` reference, the `unlockAudioElement`/`clearMicTranscribingState` wiring; the anti-regression rule was also re-narrowed from a broad `"SILENT"` substring to the *specific* M48.2b bug patterns — `audio/wav` mime + `ended`→re-prime — so it stops false-positiving on the legitimate `SILENT_MP3`-era naming). Plumbing smokes: `transcribe_blob(b"")` → empty `Transcript`; `on_audio` default stub callable; `set_on_audio` works; `/silence.mp3` route → 200 / 1271 B / `Content-Type: audio/mpeg`. **Live-validated on a real iPhone 17 Pro Max (iOS 26.5), home-screen PWA, 2026-05-19:** tap-to-talk records; `⏳ Transcribing…` visibly holds until the transcript arrives; transcribed line appears; reply text + **zero-tap auto-played reply audio**; Spanish ("¿qué hora es en Japón?") → Spanish reply in the Spanish voice. Existing paths (PC voice, PC console, phone-text, the M48.2a tool boundary) all unaffected.
- **Files:** `src/speech_to_text.py` (`transcribe_blob` public entry + `_decode_audio_blob` PyAV shim + `_as_list` resampler-version normaliser); `src/remote_console.py` (`on_audio` callback + `set_on_audio`; `_dispatch` `audio` branch; `_build_silence_mp3` + `_SILENCE_MP3` module constant; `/silence.mp3` route + `_http_bytes` binary-response helper); `main.py` (`_on_phone_audio` → daemon-thread transcribe → `text_queue`; `text_queue` item is now a 5-tuple carrying `lang`; all three producers + the consumer + the type annotation updated; `ui.add_user_text` uses `lang`); `src/remote_pwa.py` (mic button + row; `#mic` CSS + global iOS button hardening `-webkit-user-select/touch-callout:none; touch-action:manipulation`; `MediaRecorder` state machine — `startRecording`/`stopRecording`/`onRecordingStop`/`blobToBase64`/`setMicUI`; `unlockAudioElement` via `/silence.mp3`; `clearMicTranscribingState` wired to the `user`/`system` message handlers); `scripts/js_parse_gate.py` (9 new invariants + the narrowed anti-regression rule); `CLAUDE.md`; this entry.

**Reusable lessons:** (1) **Reuse the pipeline, don't fork it — adapt at the edge.** Phone audio is a different *container* (mp4/webm) but the same *problem* as mic audio. A `transcribe_blob` shim that decodes-then-delegates to the unchanged `_dispatch_transcription` meant M36 GPU offload, language detection, and the auto-fallback all applied to phone voice for free. A parallel STT path would have been more code AND would have drifted. (2) **iOS `<audio>` element user-activation is per-element, gesture-time, and does NOT transfer from the `AudioContext`.** `primeAudio()` (Web Audio resume) and a successful `<audio>.play()` are *different unlocks*; the deferred-reply path needs the latter. Play a tiny real MP3 on the actual reply element inside a gesture. (3) **iOS does not persist `getUserMedia` permission across launches — not even for an installed PWA.** This was a surprise (the M48.2b "home-screen PWA is materially better" lesson holds for *lifecycle/reconnect* but NOT for *permission persistence* or *audio-gesture rules* — a real refinement). The only fix is the OS-level "Microphone Access On All Websites → Allow"; no web API touches it. Document the platform tax, don't fork into a native app to escape it. (4) **A progress indicator must be tied to the event it claims to indicate.** `⏳ Transcribing…` reset on *upload-complete* was a lie — the upload isn't the transcription. Tie the state change to the *actual* downstream signal (the transcript fanning back), with a safety timeout. (5) **When a gate rule false-positives on legitimate new code, narrow the rule to the real bug pattern — don't delete it.** The `js_parse_gate` `"SILENT"`-substring rule tripped on the legitimate `SILENT_MP3`; the fix was to re-pin it to the *specific* M48.2b regressions (`audio/wav` mime, `ended`→re-prime) — keeping the protection, losing the false positive. A gate you'd disable to ship is a gate that needed sharpening.

## Milestone 49 — WolframAlpha computation tool (`wolfram_query`)

- **What ships:** the sixth M13-pattern client-side data tool — `wolfram_query`, a structural sibling of get_sports_info / get_weather / get_game_info / get_movie_tv_info / get_news. Gives Jarvis precise computation he genuinely lacked: multi-digit / multi-step arithmetic, unit & currency conversion, date/time math, equations, calculus, statistics, and scientific / physical / astronomical data. The first of two capability ideas raised on 2026-05-20 (the "Data & Research" idea) — its WolframAlpha slice, picked as the clean warm-up ahead of the bigger code-execution piece.
- **Why it's a real gap, not a duplicate of Claude.** Claude's mental arithmetic is unreliable for anything multi-digit or multi-step, and it has no live quantitative data. WolframAlpha is *authoritative* for exact computation — the same complementary logic as web_search vs. training knowledge. Live smoke proved the point: `4847 * 219` → exact `1061493`; `distance from Earth to Mars` → `2.208 AU` (live ephemeris Claude cannot know); `days until December 25 2026` → `219 days`.
- **API choice — the Short Answers API (`/v1/result`).** Returns ONE plain-text line, which is exactly what a voice assistant wants (Claude paraphrases it into Jarvis's voice). Rejected: the Full Results API (rich XML "pods" — overkill, we'd just flatten it back to a line) and the Spoken Results API (pre-phrases "The answer is …", which would fight the Jarvis persona Claude supplies). Note for the AppID: WolframAlpha issues ONE AppID per app that works across *all* its APIs — there is no per-API key — so the API choice is purely a code-side decision (which endpoint URL we hit), not a signup decision.
- **Why it deliberately does NOT use `src/http_util` — the interesting decision.** The shared M43 retry helper collapses *every* non-2xx response to `None`. But the Short Answers API returns **HTTP 501** as a *meaningful* response — "Wolfram|Alpha did not understand your input" — not a transport failure. Folding that into `None` would erase the distinction between "Wolfram understood the format but has no answer" (→ Claude should rephrase or answer from its own knowledge) and "the network failed" (→ try again later). So `wolfram.py` makes a direct `httpx` call with explicit status branching (200 → answer, 501 → "couldn't interpret", 401/403 → bad AppID, else/transport → "couldn't reach it"), while still mirroring http_util's one-retry-on-transport-error policy for codebase consistency. **The principle: a shared helper has a contract; when an API's semantics don't fit that contract, make the direct call — don't force-fit.**
- **The system-prompt reconciliation.** The prompt already carried a rule: "Do NOT call tools for things that don't change: **math**, geography, …". Adding a math tool made that line self-contradictory. It was re-narrowed: trivial mental math (2+2, a simple percentage) is still answered directly; *precise or multi-step computation* is the deliberate `wolfram_query` exception. Tool 16 was added to the numbered tool list with explicit "use it when being EXACTLY right matters; don't poach the other tools' territory" routing guidance. Adding to a tool description/prompt is a one-time prompt-cache write, then cached — no recurring cost.
- **Security posture — read-only, so NOT in `_RESTRICTED_DENY`.** WolframAlpha is an external read-only API with no side effects — same risk class as web_search / get_news / get_weather. Phone-origin (M48.2a-restricted) turns keep access to it; it is correctly absent from the deny set. The AppID is read fresh at call time via `os.getenv("WOLFRAM_APP_ID")` (the games.py / tmdb.py pattern — hot-swappable, not in the frozen Config dataclass).
- **What's NOT in it:** no Full Results "pods" parsing (the Short Answers line is enough for voice); no caching of results (computation answers can be time-sensitive — "distance to Mars" — and the free tier's 2,000 calls/month is ample); no `timeout` tuning of WolframAlpha's own compute budget (its default is fine; the httpx 10s ceiling sits above it).
- **Validation:** `python -m py_compile main.py jarvis.pyw src/*.py` → PASS; `python scripts/js_parse_gate.py` → PASS (no PWA change; rerun confirms no drift). No-key smokes: empty query → friendly string; query without AppID → "set WOLFRAM_APP_ID" guidance; registered in `_CLIENT_TOOLS`; absent from `_RESTRICTED_DENY`; system prompt carries the routing. **Live API smoke (real AppID, 6 cases):** exact arithmetic, unit conversion, date math, live Mars distance, forced-metric units, and a gibberish query → the HTTP 501 "couldn't interpret" branch — all correct. **Live voice-routing test 2026-05-20** (from the session transcript): "4,847 times 219" / "how far is Mars" / "days until Christmas" → all `wolfram=yes`, correct answers; "what's 2 plus 2" → answered directly, **no tool call** (`elapsed=2.2s`); a "weather in <city>" query → `weather_tool=yes`, **not** Wolfram. Routing fires on the hard cases, stays silent on trivial math, doesn't poach sibling tools — exactly the win condition.
- **Files:** `src/wolfram.py` (new — `WOLFRAM_TOOL` schema + `execute_wolfram_tool` + `_fetch` direct-httpx + `_app_id`); `src/llm.py` (import; `_CLIENT_TOOLS` entry `wolfram_query`; `WOLFRAM_TOOL` in the `stream_response` tools list; system-prompt tool 16 + the re-narrowed "don't call tools for math" rule); `.env.example` (`WOLFRAM_APP_ID` documented — free non-commercial AppID from developer.wolframalpha.com, 2,000 calls/month); `CLAUDE.md`; this entry. No separate note beyond the repo: the one durable lesson (the http_util-contract decision) is fully captured in `wolfram.py`'s docstring + this entry.

**Reusable lessons:** (1) **A shared helper has a contract; respect it, or don't use it.** `http_util` promises "non-2xx → None". WolframAlpha's 501 is a semantically meaningful answer, not a failure — so it doesn't fit, and `wolfram.py` makes the direct call rather than force-fitting and losing the signal. The rule-of-three that *created* `http_util` (M43) and the judgment to *not* use it here are the same discipline: match the tool to the actual shape of the problem. (2) **Adding a capability can contradict an existing prompt rule — grep the prompt, don't just append.** The "don't call tools for math" line had to be reconciled, not left to fight tool 16. A new tool's prompt work is "add the entry AND fix what it now contradicts." (3) **Pick the API variant that matches your output medium.** Three WolframAlpha APIs could answer; the Short Answers API won because one plain-text line is what a voice assistant + an LLM paraphraser actually want — the Full Results pods and the Spoken API's pre-phrasing were both *more* but *wrong-shaped*. More data is not better data.

## Milestone 50 — code execution: `run_code`, Python in a throwaway sandbox

- **What ships:** the flagship-risk tool — `run_code`, which lets Claude write Python and *execute* it to solve one-off tasks no pre-built tool covers (parsing/transforming data, multi-step algorithmic work, generating structured output). The "Brain & Logic" half of the two capability ideas raised on 2026-05-20; WolframAlpha (M49) was the warm-up and this the proper milestone after a design conversation.
- **The security reframe — why this milestone is mostly about the *boundary*, not the feature.** Every other powerful tool is *allowlisted*: `pc_shell` is 18 fixed verbs, `system_control` a fixed action set. Code execution CANNOT be allowlisted — "run arbitrary code" is the entire point; constrain *what* it does and it stops being a code interpreter. So the security model shifts: you can't constrain what the code does, you constrain **where it runs**. The container IS the security boundary. Least privilege still holds — it is just enforced by *isolation* instead of an allowlist.
- **The sandbox (M50 v1 — "fully isolated"):** an **ephemeral Podman container per call** (`podman run --rm`, destroyed after), **`--network=none`** (cannot exfiltrate / phone home / pip-install at runtime), **no host bind mount** (cannot see, read, or write a single file on the host machine), `--memory=512m` / `--cpus=1` / `--pids-limit=128` + a hard 30s wall-clock kill (a runaway can't starve the host — the M44 OOM arc is why a memory cap on anything running code is non-negotiable), `--security-opt=no-new-privileges`, and a non-root user *inside* the image too. Code goes in on **stdin** (`python -` — no command-line quoting/length traps); stdout/stderr/exit-code come back for Claude to summarize or to read a traceback and iterate.
- **No confirmation prompt — and the reasoning is the interesting part.** The M40 mutating-verb gate exists to guard against unwanted *host* changes. A no-mount, no-network, ephemeral sandbox has **zero host blast radius** — so there is nothing for a gate to guard, and gating it would be security theatre. The **sandbox replaces the confirmation gate**. The code is still written to `jarvis.log` (`[code] running …`, the pc_shell-style audit trail) — transparency, not gating. This cleanly fits the diagnostic-vs-action split: no-mount code-exec is "diag-class". (Scoped host mounts are a deliberate, confirmation-gated v2 — "action-class" — explicitly deferred.)
- **In `_RESTRICTED_DENY` — non-negotiable.** A phone-origin turn (M48.2a) can never trigger code execution, sandbox or not — the principle holds regardless of the isolation. Both M48.2a gates verified on `run_code` (the `stream_response` tools-list filter and the `_execute_client_tool` deny double-check). No `.env` flag: Podman's *presence* is the deliberate opt-in — no Podman, the tool cleanly reports "unavailable".
- **The runtime — Podman for Windows.** Podman 5.8.2; `podman machine init/start` stands up a dedicated WSL2-backed Fedora CoreOS VM, rootless. A custom image (`sandbox/Containerfile` → `jarvis-code-sandbox`) bakes in numpy + pandas: with `--network=none` the image contents are the entire toolbox, so the data-science staples must be pre-baked, not pip-installed at runtime.
- **The stale-PATH post-mortem (the bug that cost a test cycle).** First live run reported "the sandbox is offline" even though Podman, the machine, and the image were all confirmed healthy. Root cause: Jarvis is a long-lived, tray-restarted process — a winget install writes the new directory into the *registry* PATH, but a process already running (or restarted by the tray, which inherits the *old* process's environment) holds a STALE `os.environ['PATH']` and so `subprocess.run(["podman", …])` raises `FileNotFoundError`. The wrong fix is "restart Jarvis differently"; the right fix is to make `code_exec.py` **not depend on PATH at all** — `_resolve_runtime()` tries PATH, then a registry-refreshed PATH, then known install locations, caching the first absolute hit. Proven by running `execute_code_tool` from a shell with *no* `podman` on PATH: the resolver found `C:\Program Files\RedHat\Podman\podman.EXE` and the code ran. A long-lived process must resolve its external binaries, not trust the environment it was handed.
- **The "write code" routing fix.** First voice test: "*use* code to …" ran in the sandbox (`code=yes`); "*write* code to …" did NOT — Claude read "write code" as *"author and show me code"* and emitted a code block as the reply (which TTS then read aloud, line by line — useless on voice). Fix: a system-prompt sharpening on tool 17 — when the request explicitly says "write code" / "use code" / "code it", that IS a request for `run_code`; run it and return the **result**, not the source. Same "trust the stated medium" principle as M43's get_movie_tv_info routing. (A line-wrap bug in the first draft of that prompt edit split `"write\n  code"` so the literal phrase didn't exist — caught by the gate check; rewrapped. **Reusable lessons:** (1) **Arbitrary code can't be allowlisted — so isolate it, don't allowlist it.** When a capability's whole point is "no constraints on what it does", the security model moves from *what* to *where*: a no-mount, no-network, ephemeral, resource-capped container has zero host blast radius. Get the box right and arbitrary code is genuinely safe. (2) **Zero blast radius ⇒ no confirmation gate — gating a contained action is theatre.** A confirmation prompt guards against host effects; if there are none, the prompt is friction with no payoff. Keep the audit log (transparency) and drop the gate. Match the control to the actual risk. (3) **A long-lived process must resolve its external binaries, not trust PATH.** A winget/installer PATH update is invisible to an already-running (or environment-inheriting restarted) process. Any tool that shells out to a separately-installed binary should resolve it itself (PATH → registry-refreshed PATH → known locations) — this will recur for any future "shell out to X" tool. (4) **In a voice assistant, "write code to do X" means "do X, with code" — return the result, not the source.** A code block read aloud is useless; honour the named medium and run it. The trust-the-stated-noun rule (M43) extends from "what medium is this title" to "what tool did the request just name".

## Milestone 46 — hybrid semantic search for the knowledge base (the reserved-conditional follow-on, shipped)

- **What it is:** the embedding/vector layer on M45's `knowledge_search`, reserved since M45 as a *conditional* milestone — "build only if keyword recall proves the real limiter in daily use." Retrieval is now HYBRID: FTS5 keyword search + local-embedding vector search, merged by Reciprocal Rank Fusion.
- **Why it was built now — and the honest nuance.** Recalling facts from the corpus was proving unreliable in daily use; a keyword-only retrieval probe was run against the corpus and showed **4 of 7 natural paraphrased queries mis-hit** ("microphone"≠"mic", "voice recognition"≠"speech-to-text"). That looked like the trigger condition met, and the call was made to build hybrid embeddings rather than do corpus hygiene first. It was built. **Then a post-build probe with hybrid active delivered a humbling, rigorous verdict (see below) — the first probe's signal was thinner than it appeared.** That sequence is itself the lesson, recorded honestly here rather than spun.
- **What ships (the code — correct and validated):**
  - Local embeddings — `sentence-transformers` with `all-MiniLM-L6-v2` (384-dim, ~80 MB), loaded **lazily** (the import pulls torch — already present via M34's ultralytics — far too heavy for module-load; `knowledge.py` is imported on every startup). LOCAL by requirement: the private corpus never leaves the machine.
  - **No vector database.** Embeddings are stored as `float32` blobs in a `vectors` table inside the existing `knowledge.db`; vector search is a brute-force cosine over a numpy array. At personal scale that is microseconds — the same "stdlib/minimal when it suffices" judgement as M45's plain `sqlite3`. No LanceDB, no sqlite-vec.
  - Hybrid retrieval — `_search` runs FTS5 keyword + vector cosine, fuses by **Reciprocal Rank Fusion** (k=60). Keyword search is *kept* because it is better for exact terms (`PlexService`, `ed25519`); vector search adds the paraphrases an inverted index structurally cannot match.
  - **Graceful fallback, proven:** if `sentence-transformers` is absent, `_embed` returns None, the `vectors` table stays empty, and search degrades to *exactly* M45 keyword-only. A smoke run with the dep uninstalled confirmed reindex still succeeds and keyword search still works — M46 never breaks M45.
  - **Corpus hygiene:** `README.md` is now excluded from indexing — it is meta-documentation *about* the knowledge base, not knowledge, and its generic prose was measurably winning on common query words and burying real facts.
- **The post-build probe — the rigorous, humbling verdict.** Re-running the same 7 paraphrased queries with hybrid active: it *fixed* two genuine cases keyword search structurally never could (S2 "movie server"→Plex, S4 "voice recognition"→STT), but it could **not be shown to win in aggregate** — and the reason is decisive. The corpus is **8 chunks**; with `limit=5`, every query returns **5 of 8 chunks**, and the correct chunk was in the returned set for *all 7* queries. Retrieval is not filtering — it returns 62% of the corpus every time; recall is trivially ~100% and the "top-hit" ranking is noise. Worse, ~half the 8 chunks are filler (the file's preamble + four empty "TODO" scaffold sections). **The measured limiter is corpus size and hygiene, not the retrieval algorithm.** This is exactly what was flagged *before* the build ("the corpus is 2 files… M46's value can't manifest at this size") — the probe converted that caution from a guess into a proof. The cheap README/filler exclusion is what would move the needle today; the embedding layer is correct infrastructure for a corpus that does not exist yet.
- **Disposition:** ship M46 as **infrastructure** — the code is correct, graceful, lazily-loaded, costs ~nothing to carry, and is genuinely the right tool the moment the corpus grows. Reverting correct, finished work to rewrite it later is waste. But "shipped" ≠ "demonstrably helping": the honest state is *built and ready, ahead of the corpus*. The real next action is not code at all — grow and clean the corpus repo (fill or delete the four TODO stubs; add many real facts: personal runbooks, homelab/network topology, hardware and printer profiles, curated technical notes); M46's value scales with corpus size.
- **Dependency install gotcha (documented):** the first `pip install sentence-transformers` was run in an unactivated shell and landed in the *global* Python 3.12, not the project venv — diagnosed by import-probing both interpreters (global had `sentence_transformers` but not `anthropic`/`ultralytics`; the venv was the inverse). Reinstalled correctly via the venv's python by absolute path (`venv\Scripts\python.exe -m pip install`). For a venv project, always install through the venv's python explicitly.
- **Validation:** `py_compile` + `js_parse_gate` PASS. Graceful-fallback smoke (dep absent → keyword-only, reindex ok, README excluded → 8 chunks from 1 file). With the dep in the venv: reindex `semantic=on`, `vectors` table built, model loads. Hybrid probe: 2 genuine semantic wins (S2/S4), aggregate inconclusive at 8 chunks (the corpus-size finding above).
- **Files:** `src/knowledge.py` (`_get_embedder`/`_embed` lazy local-embedding layer; `reindex()` builds the `vectors` companion table; `_search` rewritten hybrid — `_vector_candidates` + `_rrf_fuse`; README excluded in `_iter_corpus_files`; module docstring + `KNOWLEDGE_SEARCH_TOOL` description updated to "hybrid"); `requirements.txt` (`sentence-transformers>=3.0` — incremental, torch already present); `CLAUDE.md`; this entry.

**Reusable lessons:** (1) **You cannot evaluate retrieval on a tiny corpus.** At N chunks with `limit ≈ N`, "retrieval" returns most of the corpus — recall is trivially ~100% and ranking is noise. A retrieval probe is only meaningful when the corpus is large enough that the right passage is genuinely *hard to find*. Evaluating on 8 chunks measured nothing. (2) **Decompose a failure signal before acting on it.** The first probe's "4/7 keyword failures" conflated three causes — a real semantic gap, README pollution, and tiny-scale ranking noise. Only the first justifies embeddings; the second is a 6-line fix; the third isn't a problem at all. The disciplined path was: apply the cheap fix, re-measure, *then* decide on the expensive one. (3) **"Infrastructure ahead of need" is a legitimate outcome — but name it honestly.** M46 is correct, graceful, cheap to carry, and genuinely the right tool; it is not wasted. But "built and shipped" is not "demonstrably helping" — the milestone entry must say which, or it lies to every future reader. (4) **`pip install` in a venv project: always install through the venv's python explicitly.** An unactivated shell silently installs to the global interpreter; verify with an import-probe of the *specific* python, don't assume.

## Milestone 51 — conversational follow-up window (+ a sports-routing companion fix)

- **What ships:** the first half of the "barge-in + follow-up window" wish-list item — the conversational follow-up window. After Jarvis answers, the listen loop stays open for ~12 s and accepts the next utterance **without a fresh "Hey Jarvis"**; silence past the window falls back to wake-word mode. Multi-turn conversation, the way the films' JARVIS works — "summon, wait, listen" becomes an actual back-and-forth. (Barge-in — interrupting Jarvis *mid-reply* — is the harder, audio-path half, deliberately deferred to M52: the follow-up window is low-risk and touches no timing-sensitive code, so it was sequenced first — "walk before run".)
- **How it works — a small, contained loop change, zero concurrent work.** `_record_until_silence` / `transcribe_after_wake` gained an optional `max_pre_speech_sec` override (None ⇒ the normal post-wake-word value, so the wake-word path is **byte-identical**); the follow-up path passes a longer value (`_FOLLOWUP_WINDOW_SEC = 12.0`). `listen_loop` carries a `followup` flag: after a real Q&A turn it's set, and the next iteration **skips `wait_for_wake_word`** and goes straight to capture with the longer pre-speech timeout. No speech in the window ⇒ `followup` clears, back to wake-word. The total recording ceiling is `pre_speech + MAX_RECORDING_SEC` on the follow-up path so a slow-to-start follow-up doesn't lose its speech budget. Conversation context carries for free — the M6 in-process history already persists across turns.
- **The dismissal detector (added after the first live test surfaced the wart).** The first live session ended with an explicit sign-off — "Thanks, Jarvis. That is all." — and the follow-up window opened anyway, leaving the mic listening for 12 s *after* the conversation was over. Fix: `_is_dismissal()` — a **deterministic** suffix-matcher (not a Claude-side prompt: the window is a `listen_loop` decision, and asking the LLM to judge "was that a sign-off?" adds a probabilistic layer to something that should be certain). If the normalized transcript *ends with* a sign-off ("that is all", "no thank you", "we're done", "goodbye", …), the follow-up window is not opened. Suffix-matched on purpose: "thanks Jarvis, that is all" fires it, but "that's all I need — what about the Jets?" and "is that all the data you have?" do not. Live-proven both ways in one session — including the sharp case "Thanks Jarvis. Can you also let me know how many Switch 2 were sold…" which *starts* with a thanks but correctly ran as a follow-up.
- **Companion fix — sports-roster tool routing (surfaced during M51 testing; the M48.2b "companion fix" precedent).** A rapid multi-turn sports session exposed a pre-existing prompt defect: the `get_sports_info` system-prompt entry said "**ALWAYS prefer this over web_search for any sports query**" — but `get_sports_info` only does scores/schedules/results. So a roster question ("who's the QB for X") matched no usable instruction (Claude correctly won't call the scores tool for a roster question, and the line steered it *away* from web_search too) → Claude answered from training, giving stale/confabulated NFL starters across the Jan-2026 cutoff. Fixed in two iterations: (a) the prompt entry now says `get_sports_info` is scores/schedules/results **only**, and roster / "who plays for" / current-player questions are TIME-SENSITIVE → `web_search`; (b) after a live miss on a *long-tenured* starter (a five-year incumbent QB — answered from a strong prior with no fetch), a **confidence-trap clause**: "a long-tenured starter is the single MOST likely to have just been replaced in a change your training cannot see — your confidence is the trap, never a reason to skip the search." Measured convergence across three sessions: roster-question tool-fire went 0/4 → 3/4 → 5/6.
- **The honest caveat (recorded, not buried):** prompt-based tool routing is a strong *nudge*, not a hard guarantee — an LLM deciding whether to call a tool is probabilistic. Tuning converged it (0/4 → 5/6) and the residual miss self-corrects gracefully on "double-check that", but it will not be a mathematical 100%. The only thing that *guarantees* a tool fires is a pre-LLM question-classifier that force-sets `tool_choice` — a whole subsystem, disproportionate for narrow cases like NFL rosters. Stop tuning at convergence; do not chase 100% with more prompt edits (that is fitting to noise — the M47/M44.1 discipline).
- **What's NOT in it:** barge-in (M52 — the audio-path half); an audible cue when the follow-up window opens (the blue LISTENING pill is the v1 cue; the behaviour is forgiving — no speech just elapses, and saying "Hey Jarvis" inside the window is harmless, it just becomes part of the captured utterance); a pre-LLM tool-routing classifier (the disproportionate "true 100%" fix, noted above, deliberately not built).
- **Validation:** `py_compile` + `js_parse_gate` PASS; `_is_dismissal` behavioural test (9 sign-offs caught, 6 non-sign-offs — incl. the two tricky "that's all"-containing questions — passed through); the sports-prompt fixes verified present in the assembled system prompt. **Live-validated across four sessions on 2026-05-20:** follow-up windows chain turns with no wake word; the window cleanly elapses on silence; "that is all" ends the conversation with no window (twice); a thanks-prefixed real question still runs as a follow-up; roster questions hit `web_search` (5/6, the previously-failing confident-prior case fixed); score questions still hit `sports_tool`; weather follow-ups still hit `weather_tool`.
- **Files:** `src/speech_to_text.py` (`max_pre_speech_sec` override on `_record_until_silence` + `transcribe_after_wake`; the follow-up path also lifts the total recording ceiling so the longer wait doesn't eat the speech budget); `main.py` (`_FOLLOWUP_WINDOW_SEC`; `_DISMISSAL_PHRASES` + `_is_dismissal`; `listen_loop` `followup` flag — skip wake word / longer capture / clear on silence / clear on a dismissal / clear on an intent turn); `src/llm.py` (the `get_sports_info` system-prompt entry — scores-only scope + roster→web_search routing + the confidence-trap clause); `CLAUDE.md`; this entry.

**Reusable lessons:** (1) **A deterministic loop decision should be made deterministically, not delegated to the LLM.** "Did the speaker sign off?" gates the follow-up window — a `listen_loop` control-flow decision. A suffix-matcher on the transcript is certain and debuggable; routing it through Claude would make a control-flow branch probabilistic. Use the model for judgement, not for plumbing. (2) **Suffix-match a sign-off, don't substring-match it.** A genuine "I'm done" lands at the *end* of an utterance; matching anywhere would false-fire on "that's all I need, now what about X". The shape of the phrase's *position* carries the intent. (3) **A confident training prior is the most dangerous one for a time-sensitive fact.** The model skips the fetch exactly where it feels surest — and a long-tenured incumbent (a 5-year starting QB, a long-serving CEO) is precisely the one most likely to have just changed. Prompts for fetch-first behaviour must say so explicitly: confidence is the trap. (4) **Know when to stop tuning a probabilistic behaviour.** Prompt-based tool routing converges with tuning but has no hard 100%; past convergence, more prompt edits fit noise. Name the structural fix (forced `tool_choice` via a classifier), judge it disproportionate, and stop.

## Milestone 52 — barge-in: interrupt Jarvis mid-reply

- **What ships:** the audio-path half of the "barge-in + follow-up" wish-list item (M51 shipped the follow-up half). While a reply is playing you can cut Jarvis off by saying "Hey Jarvis" — TTS stops near-instantly, the LLM stream aborts, and the listen loop drops straight into capturing the next utterance. The films' JARVIS, who you can always talk over. The single biggest voice-UX gap, now closed.
- **How it works — a wake-word monitor concurrent with TTS, one Event as the whole cross-thread contract.** For a PC-voice turn that speaks aloud, `process_question` spawns a `BargeInMonitor` thread for the duration of playback. It runs openWakeWord on the live mic — a *second* `Model` singleton (`_barge_model`), because the existing one documents a "one consumer thread" invariant and the monitor is a different thread — and on a "Hey Jarvis" detection sets a per-turn `threading.Event`. That Event is polled in three places: `speak_streaming`'s playback loop (stops feeding sentences + cuts the current one), `stream_response` (returns out of the `with client.messages.stream()` block so the HTTP stream closes and Claude stops generating server-side), and `text_producer` (stops pulling the LLM stream). Echo-safety is *why* the trigger is the wake word and not a bare "stop": the mic captures Jarvis's own TTS while the monitor runs, but the wake word cannot self-trigger — Jarvis never says "Hey Jarvis" in a reply. `JARVIS_BARGE_IN=0` is the kill switch.
- **The crash — cross-thread `sd.stop()`, and the fix.** v1 had the monitor call `sd.stop()` directly (via an `on_detect` callback) to cut the audio. The first live barge-in → instant hard process crash, no Python traceback (the log just ended). Root cause: sounddevice on Windows is WASAPI, WASAPI is COM, and COM uses the **single-threaded (STA) model** — an audio stream object is bound to the STA of the thread that created it. `sd.play()` ran on the `listen_loop` thread; calling `sd.stop()` on that stream from the `BargeInMonitor` thread is a cross-STA violation that crashes the process natively. This is the *exact* hazard the project had already documented ("WASAPI fails `sd.play()` from fresh threads"); the M52 blueprint asserted `sd.stop()` was thread-safe and was wrong, and should have been checked against that prior post-mortem. Fix: the monitor now touches **no** audio API — it only sets the Event. `speak_streaming` plays each sentence **non-blocking** (`sd.play(blocking=False)`) and polls a 20 ms loop *on its own (stream-owning) thread*, calling `sd.stop()` itself when the Event fires. Cut latency stays ~100 ms (imperceptible). The `on_detect` parameter was deleted outright — so the monitor structurally *cannot* reach the audio API anymore, not merely doesn't.
- **Companion fix 1 — the drain ate the follow-up.** First post-crash test: barge-in worked, but the follow-up question lost its opening words (spoken "Hey Jarvis, what about the NBA, what are the predictions on that" → captured only "what are the predictions on that"). `listen_loop` runs `session.drain()` at the top of each iteration; after a barge-in the speaker is still mid-sentence (the wake word and the new question come in one breath), and the drain discarded everything buffered between the wake word and capture-start. Fix: a `barged` flag — skip `session.drain()` for the single iteration right after a barge-in. The buffered question survives into capture. (drain stays correct after a *normal* wake word, where the speaker pauses.) Live-validated: follow-ups now captured whole, twice in a row.
- **Companion fix 2 — `'bool' object is not callable` (latent since M48.2).** When the `container_id` 400 below triggered the error-path apology, it crashed with `'bool' object is not callable`. `process_question` had a local `speak = origin != "phone_text"` bool that **shadowed the imported `speak()` function**; the apology called `speak(apology, ...)`. Latent for ~7 milestones — only the LLM/TTS-failure path calls it, so nothing exercised it until M52's testing did. Fixed: the local renamed to `text_only`, `silent` derived straight from `origin`.
- **Companion fix 3 — `_is_dismissal` masked by a trailing courtesy (M51 gap).** Live, a session ended with "That is all. Thank you." — a natural sign-off — but M51's suffix-matcher saw the utterance end in "thank you" (not a registered phrase) and kept the follow-up window open; the bare "That is all" had to be repeated. Fix: strip ONE trailing courtesy ("thank you" / "thanks" / "please", longest-first) and re-test the suffix — chosen over registering bare "thank you" as a dismissal phrase, which would false-trip questions like "how do you say thank you". Bare "thank you" still does NOT close (strips to "" → no match — M51's deliberate "only 'thank you JARVIS', with the name, signs off" choice preserved). 9-case truth table verified.
- **Issue B — the `container_id` 400 (intermittent, pre-existing, NOT M52).** During testing a turn 400'd: *"container_id is required when there are pending tool uses generated by code execution with tools."* Verified not caused by M52 — the interrupt machinery was inert that turn, so `stream_response` ran byte-identically to pre-M52. Cause: newer Claude can do server-side code execution as part of agentic work even though Jarvis declares no such tool; the response `Message` then carries a `container`, and the API requires its id echoed on every subsequent request in the exchange — the agentic loop's re-stream after a client `tool_use` omitted it. Fix: `stream_response` captures `final.container` and threads `stream_kwargs["container"]` through the rest of the loop. Conditional — byte-identical on the common (no-container) path, so zero regression risk. Could not be tested on demand (intermittent — depends on the model choosing code execution that turn).
- **Deliberate v1 scope boundaries:** barge-in is **replies only** — proactive announces stay non-interruptible (barge-in during an armed-mode announce collides hardest with the stutter gate); **PC-voice-origin turns only** — a console-typed reply being barge-able would need the voice thread's AudioSession while it sits in `wait_for_wake_word`, i.e. two concurrent queue readers (documented follow-on); Spanish-accented "HAR-vis" still won't trigger (the same known wake-word limitation, not a regression).
- **The stutter soak — done, PASSED (2026-05-21).** Barge-in deliberately reintroduces the concurrency the armed-mode stutter post-mortem fought: a CPU-inference thread (openWakeWord) running *during* the Python-fed TTS path. A passive soak is the wrong shape (the monitor only runs mid-reply, so real exposure means hours of live conversation judged by ear), so — the M44.3 `leak_repro.py` discipline — an instrument was built: `scripts/barge_stutter_soak.py` runs the *real* `monitor_for_wake_word` concurrent with *real* back-to-back `speak_streaming` and counts `[audio] status: input overflow` events (the post-mortem's instrumented tell of a TTS-path underrun). **30-min run: 90 TTS batches / ~22,625 monitor predicts, 0 monitor false-fires, 0 synth errors, and 1 input-overflow event** — a single, *isolated*, non-recurring blip at t≈510 s with ~22 min of clean concurrency on either side. The post-mortem's stutter signature is *clustering* (a recurring CPU-vs-TTS contention recurs); one event in ~22,625 predict cycles, with the candidate cause present the entire time, is the textbook *non-cluster* — OS-scheduling noise (Windows is not real-time), not the monitor. Verdict: barge-in does not stutter the reply path. The harness conservatively prints "CHECK" on any event > 0 by design (noise-vs-signal is a human call, not the instrument's); the call here is noise. (Scope: the soak isolates M52's *delta* — the monitor during TTS. The armed-mode triple-stack — monitor + YOLO watcher + TTS — is left to normal armed use; pre-M52 armed replies already coexisted with the watcher fine, so the monitor is the only new variable.) `JARVIS_BARGE_IN=0` remains the escape hatch.
- **Validation:** `py_compile` PASS; full-dependency import smoke test PASS; `_is_dismissal` 9-case truth table PASS. **Live-validated 2026-05-21:** three consecutive barge-ins, each follow-up captured in full ("What about the NBA predictions? Like who's predicted to win the playoffs this year?", "What about in the NHL? Are the NHL playoffs going on now…"), no crash, no apology bug, clean drop into listening. The crash, the drain bug, and the apology bug are all confirmed fixed live. **Stutter soak PASSED** (see above — 30 min, 1 isolated-noise event). Residual: Issue B's fix is mechanically correct but couldn't be triggered on demand to confirm live (intermittent).
- **Files:** `src/wake_word.py` (`monitor_for_wake_word` + the `_barge_model` singleton + `_get_barge_model`); `src/text_to_speech.py` (`speak_streaming` gains `interrupt_event` — non-blocking play + 20 ms poll loop, owner-thread `sd.stop()`; a `stop_playback` helper was added then removed once the crash fix moved the cut onto the owner thread); `src/llm.py` (`stream_response` gains `interrupt_event` + the `final.container` capture for Issue B); `main.py` (`_barge_in_enabled`/`_BARGE_IN_ENABLED`; `process_question` gains a `session` param, spawns the monitor, returns `interrupted: bool`; `listen_loop` `barged` flag — skip drain after a barge-in; `speak`→`text_only` rename; `_is_dismissal` trailing-courtesy strip + `_TRAILING_COURTESY`); `scripts/barge_stutter_soak.py` (the stutter-soak instrument); `.env.example` (`JARVIS_BARGE_IN`); `CLAUDE.md`; this entry.

**Reusable lessons:** (1) **Audio APIs are thread-affine — the owning thread does ALL the calls.** WASAPI/COM streams are STA-bound (thread-affine); `sd.stop()` from a non-owner thread is a native crash, not a soft failure. The project already had this documented for `sd.play()`; the blueprint should have been checked against it and wasn't. When a design has thread A signal thread B, the signal is a plain `threading.Event` — never a callback that reaches into B's resources. (2) **A callback parameter hides which thread the work runs on.** The `on_detect` callback made it *look* like the monitor "just calls a function"; it disguised a cross-STA audio call. Deleting the parameter (not just leaving it unwired) made the safe design *structural*. (3) **`drain()` is correct after a pause, wrong after an interruption.** The same buffer-clear is right for a normal wake word (the speaker pauses) and wrong for a barge-in (the speaker is mid-sentence). A "clear stale audio" step must know *why* the audio is there. (4) **A new feature surfaces latent bugs in the paths it newly exercises.** The `speak`-shadowing bug sat dormant ~7 milestones because nothing hit the apology path; M52's testing did. Treat "an old path just ran for the first time in a while" as a place defects hide.

## Milestone 53 — reminders & timers

- **What ships:** Jarvis's first "act at a future time" capability. Everything before this was present-tense — a question in, an answer out. Now "remind me in 8 minutes to take the laundry out" or "set a timer for 2 minutes" schedules a spoken reminder that fires later, on its own, with no further prompting — the single most-missed everyday-assistant primitive, and it had been entirely absent.
- **Three custom tools, not a deterministic intent matcher.** `set_reminder` / `list_reminders` / `cancel_reminder` are M13-pattern tools. The natural-language *time* parsing — "in an hour and a half", "at 6:30", "tomorrow morning" — is exactly Claude's strength; a regex matcher would be brittle. This is the deliberate opposite of M51's `_is_dismissal` (deterministic *because* it gates loop control and must be certain): reminder-setting is a capability, so the model parses. `set_reminder` takes `delay_seconds` XOR `at` (ISO 8601) — relative requests need no clock knowledge (the tool computes from `now()`); absolute ones carry a datetime Claude builds from the date it already has. The system prompt deliberately does NOT carry time-of-day — that would bust the prompt cache every minute.
- **The file is the IPC.** `set_reminder` appends to `%LOCALAPPDATA%\Jarvis\reminders.json`; the scheduler thread re-reads it each poll. Tool and scheduler are fully decoupled — no runtime object threaded through `stream_response` (the tools fit the plain `_ClientTool` `execute(dict) -> str` shape). One module lock in `src/reminders.py` guards every read/write; the write is atomic (temp file + `os.replace`) so a crash mid-write can never corrupt the store. The JSON IS the source of truth and survives a restart.
- **A poll-loop scheduler thread**, M34-watcher style — spawned in `main()` alongside the Announcer, wakes every ~10 s, fires anything due via `_announce`. A poll loop (not N `threading.Timer`s) trivially handles app restart: it polls immediately on start, so reminders that came due while Jarvis was off fire on the first poll — flagged "this was due while I was offline" when >90 s overdue. Reminders fire through `_announce` — a reminder is a proactive announce, so it rides the same WASAPI-safe Announcer path as a security alert (the thread-affinity rule from the M52 post-mortem, applied correctly by reuse this time).
- **Small companion polish:** `_announce` gained a `label` param (the console emoji tag) — the queue tuple went `(text, on_done)` → `(text, on_done, label)`, contained entirely to `main.py`. A reminder shows as ⏰ in the console, not the security 🚨. (The 🚨-for-everything was a pre-existing minor wart — knowledge-reindex and face-enroll announces wore it too; the `label` param fixes the class, defaulting to 🚨 so existing callers are unchanged.)
- **Deliberate v1 scope:** one-shot reminders only — **recurring** ("every day at 7am") is the clean follow-on, and the hook a scheduled "good morning" briefing would build on. Speaks + console only (no Discord/email push on fire — that's a small follow-on). No snooze; edit = cancel + re-set. Available to phone-origin turns (NOT in `_RESTRICTED_DENY`): a reminder just speaks on the PC and touches nothing destructive, so there was no reason to block it.
- **Validation:** `py_compile` PASS; full-dependency import smoke PASS. **16-case headless functional test** PASS — store CRUD, all three executors, every rejection path (past time, delay+at both, neither, empty message, negative delay), `pop_due` atomicity + destructiveness, the belated-vs-normal fire text. **Scheduler-thread test** PASS — the real `run_scheduler` thread polled, fired a due reminder through `announce()`, left a future one untouched, exited cleanly on the stop event. **Live-validated 2026-05-21:** all four intents routed correctly (`reminder_set` ×2, `reminder_list`, `reminder_cancel` — every one `=yes` in telemetry), natural confirmations, the list read both pending items back with times, cancel-by-query worked and Claude noted the surviving reminder. **The decisive result — persistence across a restart:** a reminder set in one session survived a clean shutdown + relaunch and fired in the *next* process (`[reminders] firing r593d25` → `[announce] Sir, a reminder — …`). The cancelled timer correctly never fired. A clean ship — no bugs surfaced.
- **Files:** `src/reminders.py` (NEW — the JSON store with atomic write + module lock, the three tool schemas + executors, the `run_scheduler` poll loop, `_fire_text` with the belated flag); `src/llm.py` (the three tools imported + registered in `_CLIENT_TOOLS` + added to the `tools` list; a "Reminders & timers" system-prompt section, tools 18–20); `main.py` (`run_scheduler` thread spawned by `main()`, `reminder_stop` for clean shutdown; `_announce` gained the `label` param and the announce-queue tuple grew to 3); `CLAUDE.md`; this entry.

**Reusable lessons:** (1) **The file can be the IPC.** Decoupling the tool (writer) from the scheduler (reader) through `reminders.json` itself — instead of threading a runtime object through `stream_response` — kept the tools as pure `_ClientTool` functions and made the design restart-safe for free (the store *is* the persistence). When two components need to share state and one of them must survive a restart anyway, the persistent file is often the cleanest channel between them. (2) **A poll loop beats N timers when restart is in the picture.** One thread that re-reads state each tick handles app restart, overdue-on-startup, and clock changes with no extra code; N `threading.Timer`s handle none of them. (3) **Match the parser to the job.** M51 made `_is_dismissal` deterministic *because* it gates loop control; M53 makes time-parsing Claude's job *because* it's fuzzy natural language. "Use the model for judgement, not for plumbing" cuts both ways — the test is whether the decision must be certain (deterministic) or interpretive (the model). (4) **A capability built once can be foundation.** The scheduler isn't just reminders — it's the machinery proactive homelab monitoring and a scheduled "good morning" briefing will reuse. Building the bounded thing well opened three wish-list items, not one.

## Milestone 54 — recurring reminders

- **What ships:** the M53 follow-on — a reminder can now repeat on a schedule. *"Remind me every weekday at 9 to stand up"*, *"every 30 minutes to check the print"*, *"on the 1st of every month to pay rent."* When a recurring reminder fires it isn't consumed — it re-arms for its next occurrence.
- **Three recurrence kinds, no full calendar engine.** `set_reminder` gained an optional nested `repeat` param; omit it and the M53 one-shot behaviour is byte-identical. The three kinds: `interval` (a fixed period in seconds — "every 30 minutes"), `weekly` (a weekday set + a time-of-day — "every weekday at 9", "every Monday at 6pm", and "every day at 7am" as all seven days), `monthly` (a day-of-month + a time, clamped to the month's last day via `calendar.monthrange`, so day 31 means "the last day of every month"). Between them they cover the realistic 90%; monthly was pulled into v1 rather than deferred — ~15 LOC closed a real gap (monthly bills have no workaround in interval/weekly). Deferred: yearly, "every other Monday", nth-weekday — genuinely rare for a voice assistant.
- **Claude parses, the tool computes.** `set_reminder` takes the structured `repeat` spec (Claude maps "every weekday at 9" → `{kind:weekly, weekdays:[0,1,2,3,4], time:"09:00"}`); `_validate_repeat` normalises + rejects malformed specs with a voice-friendly error; `_next_occurrence(repeat, after)` does the date math for all three kinds. For a recurring reminder the first occurrence is *derived* from the recurrence (no `delay_seconds`/`at` needed). weekly/monthly recompute the wall-clock time each occurrence, so they're DST-correct; interval is for sub-day periods where that's moot.
- **Re-arm, not re-create — and catch-up, not stampede.** `pop_due` became recurrence-aware: a one-shot is removed on fire; a recurring reminder is re-armed *in place* — **same id** (so `list`/`cancel` stay stable across occurrences), `fire_at` advanced. The next slot is computed from `now()`, not the stale `fire_at` — so however long Jarvis was off, a missed recurring reminder fires exactly **once** on restart, then resumes. There is structurally only ever one record per recurring reminder, so a backlog stampede is impossible by construction.
- **Companion fix — `cancel_reminder` reports what remains.** The live test surfaced it: after cancelling the stretch reminder Claude said "the trash reminder remains" — but that one had already fired. Not a tool bug (cancel worked) — Claude *inferred* "what's left" from a stale earlier list in the conversation. Fix: `cancel_reminder` now appends the actually-still-pending reminders to its result, so Claude states what remains from fact, not memory.
- **Validation:** `py_compile` PASS; import smoke PASS. **29-case headless functional test** PASS — every `_validate_repeat` path (all three kinds + each rejection), `_next_occurrence` for all three including the monthly clamp (day 31 → April 30, → Feb 28) and weekly's already-passed-today handling, `_describe_repeat`, set + list with recurrence, and the critical `pop_due` re-arm (recurring reminder kept its id with a future `fire_at`, one-shot removed). Plus a targeted test of the cancel-reports-remaining fix. **Live-validated 2026-05-21:** *"remind me every two minutes to stretch"* → routed to `set_reminder` with the right `repeat` spec, confirmed "every two minutes"; `list_reminders` read it back as "stretch every two minutes"; and the decisive result — **the reminder fired twice with the same id `r81c539`** (`[reminders] firing r81c539: stretch` … `[reminders] firing r81c539: stretch`), the re-arm working in production; *"cancel my stretch reminder"* stopped it (no further fires). A one-shot from a prior session fired once and was gone. Clean ship.
- **Files:** `src/reminders.py` (`_parse_hhmm`, `_human_time`, `_validate_repeat`, `_next_occurrence`, `_describe_repeat`; `add` takes a `repeat` kwarg; `pop_due` re-arms recurring reminders; `execute_set_reminder` handles `repeat`; `execute_list_reminders` describes recurrence; `execute_cancel_reminder` reports what remains; `SET_REMINDER_TOOL` schema gains the nested `repeat` object); `src/llm.py` (the system-prompt tool entry updated for recurrence); `CLAUDE.md`; this entry. `main.py` untouched — the scheduler already calls `pop_due`, now recurrence-aware internally.

**Reusable lessons:** (1) **A small fixed taxonomy beats a general engine.** Three recurrence kinds — interval / weekly / monthly — cover the realistic 90% of "remind me regularly" in ~120 lines; a full RFC-5545 / cron engine would be far more code for cases (nth-weekday, "every other week") a voice assistant rarely hears. Build the taxonomy people actually speak. (2) **Re-arm in place to keep identity stable.** A recurring thing that's deleted-and-recreated each cycle gets a new id every time, breaking "cancel the X reminder" between fires. Advancing the existing record (same id, new time) keeps every handle the caller and the LLM hold valid across occurrences. (3) **Compute the next slot from `now`, not the last scheduled time.** That single choice is what turns "Jarvis was off for a day" from a stampede of missed fires into one clean catch-up — the difference between a backlog and a resume. (4) **A tool should return the facts the model will be tempted to guess.** Claude narrated "the trash reminder remains" from a stale earlier turn because the cancel result didn't say. Returning the current still-pending set with the result removed the temptation — when a tool's caller will editorialise about adjacent state, hand it that state.

## Milestone 55 — the "good morning" briefing

- **What ships:** "Jarvis, good morning" → one composed spoken reply — today's weather, sports + gaming headlines, anything the security watcher caught overnight, and the reminders due today. The films' JARVIS handing Tony the state of his world before coffee. The single most "it's really Jarvis" moment in the project so far, and it works through the phone.

## Milestone 56 — proactive homelab monitoring

- **What ships:** Jarvis's first *unprompted heartbeat*. A background thread watches the homelab and speaks up ON ITS OWN when something breaks — the Plex laptop goes unreachable, Plex Media Server stops responding, or a disk runs low — and again when it recovers (*"Plex is responding again, sir."*). Plus an on-demand `homelab_status` tool ("Jarvis, how's the homelab?"). Every milestone before this was *reactive* — you speak, he answers; even the M55 briefing only fires when asked. M56 is the reactive → proactive jump: Jarvis now notices things and reports them. The films' JARVIS flagging a problem before Tony asks.
- **Architecture — almost entirely recombination.** New module `src/homelab_monitor.py`, a near-copy of patterns already trusted: thread model = `reminders.run_scheduler` (one defensive daemon poll loop, a stop `Event`, every poll wrapped so a bad check can't kill the thread); lifecycle/opt-in = `SecurityWatcher` (`activate()`/`deactivate()`/`is_active()`, a tray toggle, an `.env` flag, default OFF); remote reach = the existing `PlexLaptopClient` — its `run()` is already lock-serialised, so the monitor thread *shares the one SSH connection* the tool path uses, no new auth surface; voice out = `main.py`'s `_announce` (the WASAPI-safe Announcer path), tagged 🖥 to read distinctly from 🚨/⏰; phone push = a new `notifications.send_discord_message` (the generic, no-attachment counterpart to the deterrent-hardwired `send_discord_alert`).
- **The interesting part — the alert state machine.** A monitoring tool lives or dies on *alert hygiene*: the naive version polls every minute and, while Plex is down, says "Plex is down" *every minute* — alert fatigue, the thing that makes people mute their monitoring. The fix is three classic ideas, each a handful of lines, all in `_CheckTracker` (deliberately isolated from all I/O so it is trivially unit-testable):
  1. **Flap damping / hysteresis.** A single failed poll is noise (a dropped packet, a GC pause). A check must fail `JARVIS_HOMELAB_FAIL_THRESHOLD` polls IN A ROW (default 3) before OK → DOWN. This is Nagios's soft-vs-hard state (`max_check_attempts`); it is a Schmitt trigger — don't let a sensor chatter on the boundary.
  2. **Edge-triggered, not level-triggered.** The alert fires ONCE, on the transition; stay-down polls are silent. Recovery (DOWN → OK) is its own edge and fires one "it's back" — closing the loop matters.
  3. **Dependency suppression.** `plex` and `disk` declare `depends_on="host"`. If the laptop itself is unreachable, those two checks are skipped (and their trackers reset) rather than each firing — you get ONE "laptop is down", not three. Nagios parent/child host dependencies: don't page for fifty services when the router they sit behind is what died.
- **What it watches (v1):** host reachability (TCP connect to :22 — no ICMP, no admin, no subprocess), Plex liveness (`GET /identity` — 200 + XML, no auth token), and disk space on the laptop (worst fixed drive < `JARVIS_HOMELAB_DISK_MIN_PCT` free, default 10%). Built on an extensible check registry — a check is one function. The homelab has exactly one monitored host, so v1 is MEDIA-HOST-only by design, not by omission.
- **A clean seam, not a parsed display string.** The disk check needed structured numbers; `execute_plex_laptop_health(..., "disk")` returns a voice-*formatted* string. Rather than regex a display string back apart, added a public `plex_laptop.fetch_disk_usage(client)` → `[{id,total,free,pct_free}]` that reuses the exact same `_HEALTH_DISK_PS` script — the right seam, ~30 LOC, robust to nothing.
- **`homelab_status` tool (the free "status report" down-payment).** Param-less custom tool; probes everything fresh and returns a short per-check roll-up. A *fresh-state* request like the briefing — the prompt entry says run it every time, never answer from an earlier check. NOT in `_RESTRICTED_DENY` (read-only, touches nothing — the phone may ask). Reaches the live monitor via a module-global set in `HomelabMonitor.__init__` — the same tool/runtime decoupling `reminders.py` gets from its JSON file, via an object here since this state is in-memory, not persisted.
- **Demo-safe by construction.** Default OFF; opt-in via `JARVIS_HOMELAB_MONITOR` or the tray's "Homelab monitoring" toggle (the Security-mode pattern, exactly). Doesn't touch the listen loop. Nothing else in the system depends on it and nothing can be destabilised by it — least-privilege, opt-in ("Jarvis stays Jarvis").
- **Validation:** `py_compile` PASS (full close-out gate). `_CheckTracker` unit test — `scripts/homelab_alert_test.py`, an asserting harness in the `leak_repro.py`/`barge_stutter_soak.py` instrument tradition — **16/16 PASS**: clean stream silent, 2-fail blip damped, 'down' on exactly the 3rd, stay-down silent, one 'recovered', no phantom recovery, re-down after recovery, counter resets on any OK (consecutive not cumulative), `reset()`, threshold-1. Import + wiring smoke PASS (`homelab_status` registered in `_CLIENT_TOOLS`, correctly absent from `_RESTRICTED_DENY`). **Live-tested against the real MEDIA-HOST: all three checks ran true** — host reachable (TCP :22), Plex responding (`/identity` 2xx), disk healthy (worst drive 27% free); `status_report()` and `execute_homelab_status({})` returned identically.
- **Deliberate v1 scope:** on-demand status + background monitor. Not built: a stay-down *re-reminder* cadence (one alert per edge for now); CPU/RAM sustained-high checks (noisier — disk/up-down is the high-signal set); email push (Discord is the instant-phone channel; email is M38's security path). A console "🖥 monitoring" indicator was deliberately skipped — the tray checkmark is the indicator, less UI surface = lower risk.

- **Live-test fix (same session, 2026-05-22) — dependency suppression must FREEZE the tracker, not reset it.** The first live test ran the exact scenario that exposed it: stop Plex (→ "Plex stopped responding"), then take the whole host down (→ "MEDIA-HOST unreachable"), then bring the host back (→ "MEDIA-HOST back online"). The missing line: there was never a "Plex is responding again". Cause: while the host was DOWN, `_poll_once` skipped the dependency-suppressed `plex` check AND called `tracker.reset()` on it every poll — erasing the fact that Plex was DOWN. So when the host recovered and Plex was up, the tracker saw OK→OK (no edge) instead of DOWN→OK, and stayed silent. The host outage *swallowed* the child recovery — an alert that opened and never closed (and, symmetrically, a still-down child would have re-fired a duplicate DOWN). Fix: in the suppression branch, FREEZE the tracker — just `continue`, don't `reset()`. A pre-existing DOWN verdict is *real*, not stale; preserving it means a genuine child recovery still fires its DOWN→OK edge once the parent is back. One line removed. `reset()` remains, still called by `activate()` (a fresh arm should not inherit a stale verdict) — so the 16/16 `_CheckTracker` test is unaffected, and the fix simply makes `_poll_once` rely on the already-tested `down → OK → 'recovered'` path (test 5). `py_compile` + 16/16 re-confirmed.
- **Files:** `src/homelab_monitor.py` (NEW — `_CheckTracker`, `Check`, `HomelabMonitor`, `HOMELAB_STATUS_TOOL` + `execute_homelab_status`, the tunables; the live-test freeze fix in `_poll_once`); `src/notifications.py` (`send_discord_message` — generic plain-text webhook push); `src/plex_laptop.py` (`fetch_disk_usage` — public structured-data seam over `_HEALTH_DISK_PS`); `src/config.py` (`homelab_monitor_enabled`); `src/llm.py` (`homelab_status` registered + system-prompt entry #22); `main.py` (construct always, `activate()` on the flag, tray wiring, `shutdown()`); `src/ui.py` + `src/tray.py` (the "Homelab monitoring" tray toggle, the Security-mode pattern); `.env.example` (`JARVIS_HOMELAB_*`); `scripts/homelab_alert_test.py` (NEW); `CLAUDE.md`; this entry.

**Reusable lessons (M56):** (1) **A monitoring tool's hard part is alert hygiene, not the probe.** Connecting a socket is trivial; *not* crying wolf is the engineering. Flap damping + edge-triggering + dependency suppression are the difference between a tool you keep on and one you mute in a week — and they're the textbook ideas (Nagios soft/hard state, parent/child dependencies, the Schmitt trigger), worth naming. (2) **Isolate the decision from the I/O so the decision is testable.** `_CheckTracker` has no sockets, no threads — just `observe(ok) -> edge`. That let a 16-case asserting harness pin down the exact-once-per-edge behaviour that's otherwise only observable by taking Plex down in production. (3) **Add a seam, don't parse a display string.** `fetch_disk_usage` reuses the same PowerShell script as the voice-formatted health tool but returns structured data — a program acting on numbers should get numbers, not regex prose meant for a human ear. (4) **The powerful feature was a recombination.** M56's reach is the M24 SSH client, its push is the M38 webhook, its thread is the M53 scheduler shape, its lifecycle is the M34 watcher — the new code is mostly the alert state machine. A well-factored codebase makes the big new capability small.
