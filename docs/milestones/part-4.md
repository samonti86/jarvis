## Milestone 58 — acoustic awareness (the audio twin of M34 vision security)

- **What ships:** Jarvis hears the non-speech world. A background classifier listens on its own mic stream and speaks up unprompted on a doorbell, knock, smoke / fire alarm, glass breaking, phone ringing, kitchen timer, or a sink left running. The reactive→proactive jump for the AUDIO channel — he sees (M34/M30) and now he hears. Same dual-channel as homelab alerts: spoken via the WASAPI-safe Announcer (tagged 🔔) + Discord push to the phone.
- **The risk that mattered most — the model-sourcing de-risk.** Initial pick was AST (Audio Spectrogram Transformer) via the existing `transformers` pipeline — strongest AudioSet model, zero new deps, looked perfect on paper. **Measured early: ~3.5 s steady-state CPU inference**, far too slow for a 1 Hz alert loop (the queue would back up forever and a doorbell alert would arrive 7 s+ late). Pivoted to PANNs Cnn14 via `panns_inference` (~325 MB checkpoint from Zenodo, one-time download). **Measured again: ~0.20 s steady-state** — 17× faster, comfortably real-time. The lesson re-cashed: *measure latency before you ship, not in production*.
- **A bundled-downloader landmine.** `panns_inference` shells out to `wget` for its labels CSV and the checkpoint — broken on Windows (no `wget`). Wrote `_ensure_files()` to pre-place both via the project's existing `httpx`, atomic-write (temp + `os.replace`) so a partial download can't poison the next run. The import-time `from panns_inference import …` now Just Works.
- **Architecture.** New module `src/sound_detector.py` with a `SoundDetector` class (modeled on `SecurityWatcher`/`HomelabMonitor`). Owns its **own** `sounddevice.InputStream` at 32 kHz mono (PANNs' training rate) — the existing `AudioSession` is single-reader-by-design (the wake-word loop owns it, the M52 barge-in monitor takes over during TTS), so adding a third concurrent reader would race; M58 captures independently, supported on Windows/WASAPI. Audio callback accumulates 2 s windows; inference worker pulls from a bounded queue and applies per-class alert hygiene (the M56 `_CheckTracker` discipline, generalised to add a wall-clock cooldown). 7 classes, 14 AudioSet label aliases — **all aliases matched the model's 527-class label set, zero missing**, verified during the de-risk.
- **The continuous-water-source mitigation — a volume guard.** Surfaced at design time: the deployment environment contains a continuous low-level household water source running at room-ambient level. Without a guard, the `running_water` class would fire 24/7. So that one class is gated on **both** (a) classifier confidence and (b) audio RMS above a calibrated floor (`JARVIS_ACOUSTIC_WATER_RMS_FLOOR`, default 0.025) — a continuous low-level trickle sits well below the floor; a sink left on full sits comfortably above it. The other six classes are sharp transients naturally above ambient, no guard needed. Plus a **per-class kill switch** (`JARVIS_ACOUSTIC_DISABLE=running_water,...`) so any single class can be muted in `.env` without disabling the whole feature — the right escape hatch for an experimental class.
- **Live-test PASS — 2026-05-26.** First arm logged `model loaded in 5.7s — 7/7 rules resolved` (model cached from the de-risk download). Three test events were triggered; ALL three fired correctly, ZERO false positives:
  - `FIRE doorbell (score=0.80 rms=0.049)` → *"Sir — that sounded like the doorbell."* + Discord HTTP 204
  - `FIRE phone_ringing (score=0.27 rms=0.016)` → *"Sir — your phone is ringing."* + Discord HTTP 204
  - `FIRE knock (score=0.29 rms=0.107)` → *"Sir — there's someone at the door."* + Discord HTTP 204
  A single `[audio] status: input overflow` at the moment the second `InputStream` started concurrent with the wake-word session — a one-shot cosmetic bootstrap blip, no clustering (the speech-gate starvation signature is *recurring* overflows over time, not a single startup line) and no missed events.
- **Same-session enhancement — couple acoustic awareness to security mode.** The design shipped the two as independent toggles (the argument: acoustic has value while the machine is attended too — a doorbell you'd otherwise miss, a smoke alarm anytime). Real use flipped that within an hour: the operating mental model is `armed = unattended = listen to everything`, so acoustic sensing should follow the arm state. Wired in one chained callback: `security_watcher.set_on_armed_changed(...)` now both updates the UI indicator AND `sound_detector.activate()`/`.deactivate()`. The coupling is one-way (security drives acoustic, never the reverse); the independent tray toggle still works for the attended case; `activate()`/`deactivate()` are idempotent so a manual flip followed by a coupled flip never double-fires. Voice "activate security" and the tray toggle both now flip BOTH.
- **Validation:** `py_compile` PASS (all `src/*.py`); `_ClassTracker` unit test **12/12 PASS** (`scripts/acoustic_alert_test.py`); import smoke OK with all 7 rules; **PANNs steady-state ~0.20 s/inference measured directly** in the de-risk harness. End-to-end live-validated 2026-05-26: 3 distinct events fired correctly, 0 false positives, the security-coupling lands cleanly.
- **Deliberate v1 scope:** the seven confirmed classes only. Not built: more classes (alarm clock, dog barking — listed as optional in the design Q+A but scoped out of v1); per-class threshold env override (currently only the volume floor is tunable); a "Jarvis, what did you just hear?" tool (would need to expose recent classifier scores to the LLM — a clean v2). And the volume floor (`0.025`) is a guessed-conservative starting value, not a calibrated one — the M44.1 lesson — expect to tune it against the actual continuous water source after a few real days.
- **Files:** `src/sound_detector.py` (NEW — `SoundDetector` + `_ClassTracker` + `ClassRule` + `_DEFAULT_RULES` + `_ensure_files()` + the inference loop; the volume guard for running_water; PANNs Cnn14 via `panns_inference`); `requirements.txt` (`panns_inference>=0.1`); `src/config.py` (`acoustic_monitor_enabled`); `main.py` (construct always, `activate()` on the flag, tray wiring, shutdown, **the security-acoustic coupling**); `src/security.py` (`set_on_armed_changed` — small public setter for the coupling); `src/ui.py` + `src/tray.py` ("Acoustic awareness" tray toggle, the M56 pattern); `.env.example` (`JARVIS_ACOUSTIC_*`); `scripts/acoustic_alert_test.py` (NEW); `CLAUDE.md`; this entry.

**Reusable lessons (M58):** (1) **Measure latency before you ship, not in production.** AST looked perfect on paper but was 17× too slow on this CPU. A 10-line smoke test (model + 6 inferences) saved the milestone from a broken-on-launch outcome. (2) **A bundled downloader is a Windows landmine.** `wget` is a Linux-ism; the `httpx` already in the project replaces it cleanly with atomic writes. Always check first-run-on-Windows for any package that fetches its own assets. (3) **Real use beats design-time reasoning.** The design argued for independent toggles; the first day of real use flipped it within an hour. Designs are hypotheses, real use is the experiment — keep coupling/decoupling easy so the UX can be adjusted in one line. (4) **A known environmental constraint is gold.** The continuous-water-source constraint was known before a line of code was written; the volume-guard mitigation exists *only* because of it. Always characterise the room before you trust a classifier.

## Milestone 59 — scheduled briefing (the M54 × M55 hook, finally cashed)

- **What ships:** *"Brief me every weekday at 7"* now works. The M54 recurring-reminder scheduler can fire the M55 `get_briefing` composition at its slot instead of speaking a static message string. A single new field — `action="briefing"` on a reminder — bridges the two existing subsystems. `set_reminder(message="morning briefing", repeat={kind:"weekly", weekdays:[0,1,2,3,4], time:"07:00"}, action="briefing")` is the canonical call.
- **Architecture — a one-field extension, not a new subsystem.** `add(message, fire_at, repeat, action=None)` gains the optional field; storage is forward-compatible (existing reminders without `action` behave unchanged). The scheduler's poll loop sniffs `rec.get("action")`: `None` → the existing synchronous `_fire_text` + `announce` path (cheap, a string); `"briefing"` → a new `_fire_briefing()` that **dispatches the composition on a throwaway worker thread**. The composition takes 5–10 s (fetches weather + news + reads the security event dir + the reminders store), so running it on the scheduler thread would block the poll loop for that whole window — the worker pattern keeps reminders snappy and the briefing slow-but-out-of-band.
- **Time-of-day greeting.** A briefing scheduled for 6 pm shouldn't be greeted with *"Good morning, sir."* Added `_greeting_for(hour)` — morning before noon, afternoon up to 17:00, evening after. Tiny, but the alternative would be a tone-deaf evening "good morning."
- **Briefings are reminders.** Listed by `list_reminders` with a `"(briefing)"` tag, cancelled by `cancel_reminder` exactly like any other. Many can coexist — *"brief me weekdays at 7 AND every evening at 6"* — they're all just reminders with the action set.
- **System prompt teaches the new field.** `set_reminder`'s entry now says: *"if asked to be briefed on a schedule, call set_reminder with `action='briefing'` AND a `repeat` spec — the reminder triggers the get_briefing composition at fire time."*
- **Unknown actions are rejected early.** A typo (`action="brefing"`) gets a voice-friendly *"I don't know the 'brefing' action, sir — only 'briefing' is supported right now"* rather than a silent never-fires-as-expected outcome. Forward-compatible at the storage layer (unknown values stored verbatim and treated as no-op by the scheduler) but strict at the tool boundary (the LLM's input is validated).
- **Validation:** `py_compile` PASS; new regression test `scripts/scheduled_briefing_test.py` PASS — covers schema field present, `add(action=...)` storage, `_greeting_for` returns morning/afternoon/evening correctly, unknown action rejected at the tool boundary.
- **Deliberate v1 scope:** only one action (`briefing`). Other actions (a "good night wrap" — the symmetric end-of-day counterpart from the M58+ wish list, or fire arbitrary tools) are easy follow-ons but the design says ship the one we promised first. The action enum + the dispatch switch make adding a second action a few-line change.
- **Files:** `src/reminders.py` (`add(action=...)`, `SET_REMINDER_TOOL` schema, `execute_set_reminder` validation + path, `_fire_briefing` + `_greeting_for` helpers, scheduler dispatch, `execute_list_reminders` tag); `src/llm.py` (system-prompt addendum on `set_reminder`); `scripts/scheduled_briefing_test.py` (NEW regression); `CLAUDE.md`; this entry.

**Reusable lessons (M59):** (1) **Two existing subsystems + one bridging field = a feature.** The M54 scheduler and the M55 composition were both already there; M59 is a single new field on the existing record and a single conditional dispatch in the existing loop. The smallest milestones are the ones where you find the right *bridge*, not where you build new infrastructure. (2) **Slow side-work belongs on a worker thread.** The scheduler's job is to be on-time, not to *do* the work. When the work is slow (5–10 s composition), dispatch it; keep the poller free for the next slot. (3) **Reject unknown values at the tool boundary, store them forward-compatibly underneath.** Strict at the LLM-facing edge keeps "did the model typo it?" obvious; lenient at the storage layer keeps a v2 from needing a migration. The two postures are not the same.

## Milestone 60 — self-status report ("Jarvis, are you healthy?")

- **What ships:** `status_report` — Jarvis's own subsystem roll-call. *"Jarvis, status report"* → one line per subsystem (security, acoustic awareness, homelab monitor, Plex MCP, Plex laptop SSH, remote console, STT backend, reminders, process memory) plus a count of concerning lines in this session's log. The broader companion to M56's `homelab_status` (which is the homelab-only view).
- **Why this matters:** subsystems degrade *silently* by design (the project-wide fail-soft contract). The GPU STT server might be down, Plex MCP might never have connected, the remote console might be off — and Jarvis just keeps running. That's correct behaviour, but it means a quiet failure can persist for days. `status_report` makes the quiet state legible on demand.
- **Architecture — a registry, not a god object.** New module `src/self_status.py` with `register(name, getter) → ONE status line`. Each subsystem registers a closure in `main.py` at startup (after every dependency is constructed, so each getter captures the live local). The tool iterates the registry in insertion order, joins the lines. Same module-singleton pattern M56 uses for the live monitor — no subsystem refs threaded through `stream_response`; the tool simply reads what main.py has registered. **Order is display order**: security first (the most-checked state), then the M58/M56/M48/STT subsystems, then telemetry (reminders / memory / errors).
- **Concerning lines in `jarvis.log`.** `count_session_errors()` scans from the most recent `--- Jarvis started …` session marker forward, counting matches of `\b(failed|raised|tripped|traceback|panic|exception)\b` — patterns observed in real Jarvis logs (`[homelab] poll failed`, `[security] MEMORY WATCHDOG TRIPPED`, `[acoustic] inference call failed`, plus Python's `Traceback:` / `Exception:`). The word "error" itself is deliberately excluded — too noisy (`"no error"`, `permission_error` in arg names). Returns `(count, context)` so the report line can say "since session start" vs. "in recent log tail" (the fallback when no session marker exists, e.g. after log rotation). Bounded by jarvis.log's 5 MB rotation cap — the whole-file read is cheap.
- **Defensive end-to-end:** an individual getter that raises is logged and renders as `"name: error reading (RuntimeError)"`; the rest of the report continues. Never one bad subsystem breaks the whole roll-call.
- **Prompt teaches concision.** The `status_report` entry tells Claude to read the result back *concisely* — *"if everything is healthy, say so in one sentence ('all systems nominal, sir'); only enumerate the problem subsystems unless a full report was explicitly asked for."* Same fresh-state discipline as the briefing and homelab_status — re-run every time.
- **NOT in `_RESTRICTED_DENY`.** The phone may ask "are you healthy?" — it's read-only, exposes no secrets, touches nothing. Consistent with `plex_laptop_health` and `homelab_status`.
- **Validation:** `py_compile` PASS; new regression test `scripts/status_report_test.py` PASS — **7/7**: empty registry returns a clear message; getters render in insertion order; a raising getter renders as `error reading` and the report continues; `count_session_errors` scans correctly across the *most recent* session marker (older session's errors are excluded — proven with two consecutive markers and verified the count is 3, not 6); fallback to the recent-tail when no marker; missing log file is fail-soft `(0, 'no log file yet')`; tool schema is well-formed. Import smoke confirms `status_report` is in `_CLIENT_TOOLS` and correctly absent from `_RESTRICTED_DENY`.
- **Deliberate v1 scope:** the 10 subsystems registered are the ones Jarvis has *as of M60*. Future subsystems should register themselves alongside their construction — one `register("My subsystem", lambda: …)` line in main.py is the contract. NOT built: a "Discord push the status on schedule" thing (a scheduled briefing already covers that role); per-subsystem severity (green/yellow/red); a `last_event_age` field for each subsystem (e.g. "homelab last alert: 14 minutes ago") — clean v2 additions on top of the registry.
- **Files:** `src/self_status.py` (NEW — `_REGISTRY`, `register()`, `count_session_errors()`, `process_private_mb()`, `STATUS_REPORT_TOOL`, `execute_status_report()`); `src/llm.py` (import + `_CLIENT_TOOLS` + tools list + system-prompt entry #23); `main.py` (the registration block — 10 getters registered after every subsystem is constructed); `scripts/status_report_test.py` (NEW 7/7); `CLAUDE.md`; this entry.

**Reusable lessons (M60):** (1) **A registry beats a god object.** Instead of one big `status_report` function that hardcodes every subsystem it knows about, each subsystem registers its own getter. Adding a new subsystem is one line at its construction site; no central file to "remember" to update. The Open/Closed principle in 30 lines of Python. (2) **Be specific about your error patterns.** `\b(failed|raised|tripped|traceback)\b` catches real Jarvis log lines; matching the bare word `"error"` would have buried the signal in routine `permission_error`-style false positives. *Know the patterns of the system you're scanning.* (3) **Fresh-state requests deserve a re-run, every time.** The briefing (M55), homelab status (M56), and now status_report all share this — the prompt entry says "re-run every time, never answer from an earlier call." Three milestones, one pattern; once you have it, nail it everywhere.

## Milestone 61 — `knowledge_remember` (the LLM-facing knowledge-base WRITE tool)

- **What ships & why:** a natural spoken request to durably remember a personal fact ("I want you to remember the names of my pets") got the reply *"I don't have a write tool for the knowledge base, sir."* That gap is closed. `knowledge_remember` is the LLM-facing companion to M45's `knowledge_search` — Claude can now write a durable fact to the corpus on any natural "remember this for me" phrasing.
- **Why the gap existed.** The M45 voice-intent path (`_REMEMBER_INTENT_RE`) deliberately requires a permanence adverb — *"remember this **permanently**: …"* / *"forever"* / *"for good"* — to disambiguate from episodic *"remember when we…"* (a different store). A natural phrasing like *"I want to remember"* has no adverb, so the regex didn't fire, and Claude had no Anthropic tool to fall back on. The two paths are intentional: the regex captures the unambiguous "do this NOW without involving the LLM" case; the tool covers everything else.
- **Implementation — a one-tool add.** Schema (`KNOWLEDGE_REMEMBER_TOOL`) + executor (`execute_knowledge_remember`) live in `src/knowledge.py` next to their search siblings; the executor wraps the existing `remember_fact()` so behaviour is byte-identical to the voice-intent path (one dated `.md` per fact, atomic write, reindex on success, voice-ready confirmation, never raises). Wired in `src/llm.py`: import, `_CLIENT_TOOLS`, the `tools` list, and the system-prompt knowledge section is split into 14 (read) and 14b (write) with clear "use this when" / "don't use this for" guidance — episodic memory and `set_reminder` are explicitly named as different stores to keep the LLM's mental model crisp.
- **NOT in `_RESTRICTED_DENY`** — consistent with `set_reminder` (the other mutating-user-data tool the phone is allowed to use). The corpus is its own git repo pushed offsite, so any spam from a compromised phone is fully reversible. The least-privilege ladder can be tightened later if it ever bites.
- **Validation:** `py_compile` PASS; new regression test `scripts/knowledge_remember_test.py` **9/9 PASS** — schema name + description + required field; empty-fact returns voice-friendly error AND writes no file; real fact writes exactly one `.md` file containing the fact text (verified by reading the file body back — both distinctive tokens of the fact present); reindex ran (the M46 semantic-search pipeline loaded all-MiniLM-L6-v2 + indexed 1 chunk); the tool is registered in `_CLIENT_TOOLS` and correctly absent from `_RESTRICTED_DENY`. Uses `JARVIS_KNOWLEDGE_DIR` + a `tempfile.TemporaryDirectory()` so the real corpus isn't littered.

**Reusable lessons (M61):** (1) **Intent-regex vs. LLM tool: pick BOTH, not either.** A strict regex captures "definitely do X" deterministically; a tool covers every conversational variation the regex won't. They're complementary, not redundant — the regex bypasses the LLM (faster, certain), the tool gives the LLM the same verb when the phrasing is more natural. Most "remember this" features should ship both, with the regex requiring an unambiguous keyword and the tool taking everything else. (2) **A gap surfaced by real use is data, not noise.** The exact failing transcript becomes the regression test case. Capture it, run it through the new path, ship.

## Milestone 62 — Outlook calendar awareness (read-only, Microsoft Graph)

- **What ships:** the morning briefing gains *today's calendar events*, and Claude can answer *"what's on my calendar?"*, *"do I have anything later?"*, *"what's tomorrow looking like?"*, *"am I free at 3pm?"* via a new `get_calendar_events` tool. Personal Microsoft accounts (outlook.com / hotmail.com / live.com) in v1; work/school accounts are mechanically the same but need different Azure tenant config + potentially IT admin consent, deferred. Read-only by hard contract — `Calendars.Read` scope, no create/modify capability.
- **Architecture — MSAL + Graph, two paths separated by design.** The interactive OAuth and the runtime queries are deliberately on different code paths:
  - **One-shot interactive setup:** `scripts/outlook_auth.py` runs the MSAL device-code flow. Prints a code + URL, entered at microsoft.com/devicelogin; refresh token saved to `%LOCALAPPDATA%\Jarvis\msal_cache.bin`. Runs ONCE.
  - **Silent runtime:** every tool / briefing call uses `acquire_token_silent()` — fast, no user interaction, MSAL auto-refreshes before expiry. If the cache is missing or revoked, the tool returns a clear *"run `python scripts/outlook_auth.py` to re-authorise"* message rather than blocking on an interactive prompt. **A voice assistant cannot usefully run device-code in the middle of a tool call** — it would block Claude's reply for up to 15 minutes. Separating the paths is the key UX call.
- **Graph endpoint: `/me/calendarView`**, NOT `/me/events`. `/calendarView` expands recurring events into instances — so "today's events" correctly includes the Nth occurrence of a weekly recurring meeting, which `/events` would miss (it returns only series masters + exceptions). Times come back in UTC by default (no `Prefer: outlook.timezone="…"` header — avoids the Windows-vs-IANA timezone-name compatibility headache); we convert to local on display so the wall clock reads correctly.
- **Briefing integration.** New `_calendar_section()` in `src/briefing.py` slots between security and reminders — the logical position for "the day's schedule" in the morning briefing. **Three states, each handled distinctly:** (a) `OUTLOOK_CLIENT_ID` unset ⇒ section silently omitted (no nag when calendar was never configured); (b) configured but auth expired / Graph erroring ⇒ section SURFACES the error verbatim (silent failure here would mean a missed meeting); (c) configured + working but no events ⇒ "Calendar: nothing scheduled today." (positive empty-state).
- **Honest about the setup required.** Unlike most milestones this one needs a real ~10-minute Azure app registration before it works. The full step-by-step lives in `.env.example` — portal.azure.com → AAD → App registrations → New (Personal Microsoft accounts only) → enable public client flows → add Calendars.Read delegated permission → copy Application ID into `.env`. Then `python scripts/outlook_auth.py` for the one-time OAuth. After that, transparent.
- **NOT in `_RESTRICTED_DENY`.** Read-only, exposes only the account's own calendar (already on the phone via the Outlook app). Phone may ask "what's on my calendar?" — consistent with how `homelab_status` and `status_report` are phone-allowed.
- **Validation:** `py_compile` PASS; `scripts/outlook_calendar_test.py` **20/20 PASS** — schema well-formed; the unconfigured path produces a voice-friendly setup message; invalid timeframe enums rejected with the valid options named; `_window_for` resolves all 4 timeframes correctly (`today`/`tomorrow`/`this_week`/`next_24h`); `_parse_graph_dt` handles Graph's ISO 8601 quirks (naive UTC, trailing 'Z', 7-digit fractional seconds — the `.0000000` Python's `fromisoformat` chokes on); `_normalise` gracefully handles missing optional fields + malformed dates (returns None, doesn't raise); `_format_events` covers empty / one / multi-event / with-location / all-day cases. **Live end-to-end pending the Azure registration + first OAuth** — the test deliberately doesn't make a live Graph call (would need a token + a test tenant).

## Milestone 62.2 — pre-event proactive calendar reminders

*(2026-05-28)*:

- **What ships:** Jarvis watches the same Outlook feed M62 reads on-demand and announces an event a fixed lead time before its start: *"Sir — your 2 pm meeting in 15 minutes."* The reactive→proactive jump for the CALENDAR channel — the same jump M56 made for the homelab, M58 for the audio world. The natural close on the M62 calendar arc; the M62 entry explicitly listed this as the v2 follow-on.
- **Architecture — daemon poll thread + pure decision function + persisted dedupe.** `src/calendar_monitor.py` (NEW) follows the M56 shape exactly: a daemon thread polls every `_POLL_SECONDS` (default 60, min 30), wrapped so a single bad poll can never kill the thread. On each tick: fetch via the new `outlook_calendar.fetch_events_in_window(start_local, end_local)` (a tight `[now, now + lead + 5min]` window — anything starting later than that can't possibly be due in this poll, so no point pulling a full day), then run `_should_announce(ev, now, lead_min, announced)` per event. That decision function is **pure** (no I/O, no module globals, no `time.time()` dependency) — given an event, the current time, the lead window, and the set of already-announced IDs, return `(should_fire, mins_to_start)`. The whole interesting core isolated for testing.
- **The firing rule** (in order, exact contract): (a) all-day → never fire (the morning briefing already surfaces these, and "in N minutes" is meaningless for them); (b) already started (secs ≤ 0) → never fire (no late nag — announcing a meeting we missed is just noise); (c) outside the lead window (rounded minutes > lead_min) → not yet (re-evaluate next poll); (d) already announced → suppress; (e) else → fire. Each rule is one test in `scripts/calendar_monitor_test.py`.
- **Event ID = `(subject, start_local.isoformat())`.** Deliberate: a rescheduled meeting (same subject, new start) gets a NEW id and (correctly) fires a fresh announce — a moved meeting IS news. The alternative — using a stable server-side UID — would silently swallow reschedules.
- **Dedupe persisted to disk** (`%LOCALAPPDATA%\Jarvis\calendar_announced.json`). Without persistence, a Jarvis restart between the 15-min announce and the meeting itself would re-announce. `DedupeStore` (also testable in isolation) handles load + mark + save with atomic temp+`os.replace` writes, pruned to entries < 24h (an old event ID can't recur — start_local is part of the ID — so retaining longer just bloats the file). Corrupt JSON / non-dict shape / bad timestamps all degrade to empty, never crash.
- **Default ON when calendar is configured** — different from M56 (homelab, default OFF, opt-in) and M58 (acoustic, default OFF, opt-in). Configuring `OUTLOOK_ICAL_URL` or `OUTLOOK_CLIENT_ID` is itself the opt-in; the proactive layer IS the value-add. Kill switch is `JARVIS_CALENDAR_REMINDERS=0`. The mental-model split: M56/M58 are sense-the-world capabilities that can be intrusive (network calls, continuous audio capture), so opt-in is the right ergonomic; M62.2 is "act on what was already configured," so default-on is friendlier.
- **Voice tagged 📅** (distinct from 🚨 security / 🖥 homelab / 🔔 acoustic / ⏰ M53 reminders). Discord push runs on a throwaway daemon so a slow POST never delays the next poll — same shape as M56's `_emit`.
- **Self-status registration** — registered with the M60 registry as "Calendar reminders: active/off". The status_report tool description updated to include it in the named subsystems.
- **Validation:** `py_compile` PASS; `scripts/calendar_monitor_test.py` **25/25 PASS** (3 event-id tests covering reschedule-as-new-id + 11 firing-rule tests covering every branch + edge cases like exact-lead-edge / 30 s-future / TBA-dated all-day + 11 DedupeStore tests covering fresh-load / mark+save / re-construct / snapshot-isolation / retain-hours-prune / corrupt-JSON / list-shaped-JSON / bad-ISO-timestamps). Tests deliberately don't fire a real fetch — that's the live path exercised every morning.
- **Files:** `src/calendar_monitor.py` (NEW); `src/outlook_calendar.py` (added public `fetch_events_in_window`); `main.py` (construct + activate + self-status register + shutdown — mirrors the M56 block); `.env.example` (new section documenting `JARVIS_CALENDAR_REMINDERS` / `JARVIS_CALENDAR_LEAD_MIN` / `JARVIS_CALENDAR_POLL_SECONDS`); `scripts/calendar_monitor_test.py` (NEW); `CLAUDE.md`; this entry.

**Reusable lessons (M62.2):** (1) **A pure decision function is the cheap version of an alert state machine.** M56 needed `_CheckTracker` because alert hygiene (flap damping, dependency suppression) is itself the hard part. M62.2 needed nothing more than `_should_announce(ev, now, lead_min, announced) -> (bool, int)` — same testing leverage, far less surface. Match the abstraction to the problem; the M56 pattern is overkill for a simpler version. (2) **The event id is a design decision, not a detail.** `(subject, start_local)` makes a reschedule = new announce; `event.uid` would make it = silent. Both can be right; pick the one that matches the desired behaviour ("a moved meeting is news"). (3) **Default-on vs default-off depends on what was already opted into.** M56/M58 are intrusive (continuous network probes / audio capture) → opt-in. M62.2 acts on an already-configured upstream → default-on. The pattern: if configuring the *upstream* is itself opt-in, the proactive layer can default-on without surprise.

## Milestone 64 — self-update ("Jarvis, update yourself")

*(2026-05-28)*:

- **What ships:** `update_jarvis` tool — Claude pulls the latest code from origin and restarts Jarvis. *"Jarvis, update yourself"* / *"pull the latest"* / *"self-update"* / *"check for updates"*. The deployment leg of today's "deployment + reliability" pair (M65 is the reliability leg). Listed on the wish list as "tiny" — and it is, ~150 LOC + tests.
- **Confirmation-gated** via a `confirm: bool` param (mirroring `system_control`'s mutating-verb pattern). Without `confirm`, the tool returns a description of what will happen so Claude can ask first. With `confirm=true`, the tool actually pulls + restarts. The two-call shape is load-bearing: pulling + restarting are not reversible from inside the session, so the gate is a real safety check, not procedural — see M64.1 for the natural follow-on that made the gate genuinely informed.
- **Refuses on a dirty working tree.** `git status --porcelain` non-empty ⇒ abort with the porcelain output surfaced verbatim. Don't lose local changes; `git stash` or commit first. We could `git stash` ourselves but that's silent state mutation nobody expects ("Jarvis stashed my work and didn't tell me" = bad).
- **Fast-forward only.** `git pull --ff-only` — a divergent local commit needs human attention, not an auto-merge inside Jarvis. Fails loudly with a voice-friendly message ("The pull isn't a fast-forward, sir") rather than silently producing a merge commit.
- **Tri-state working-tree check.** `_working_tree_status()` returns `"clean"` / `"dirty"` / `"unknown"`. The third state matters: if git itself is broken (binary missing, repo corrupt, status command times out), we ABORT — never proceed-assuming-clean. The "unknown" path was caught by the test harness (a stubbed `git status` rc=-1 was previously falling through to pull); the fix was promoting `_working_tree_dirty -> bool` to `_working_tree_status -> Literal["clean","dirty","unknown"]` so the caller branches explicitly.
- **Restart via callback, with a 5-second delay** so Claude has time to speak the confirmation before the UI tears down. The tool's success message ("Update successful, sir — \<commit subject\>. I'll restart in a moment.") is returned synchronously; a daemon worker thread does `time.sleep(5.0)` then fires `_restart_callback()` (which is `ui._handle_restart`, wired by main.py via `register_restart_callback`). The TTS player is single-track, so the spoken line completes BEFORE the delay elapses — voice plays clean, then the UI shuts down → M32 relaunch path takes over.
- **In `_RESTRICTED_DENY`.** The phone PWA must NEVER be able to pull code onto the desktop + force a restart — that's the M48.2a least-privilege boundary at its most extreme. A phone-driven self-update IS arbitrary code execution by another name (whatever's on origin's HEAD becomes running code), and the M50 lesson applies: when a capability's point is "no constraints," the gate has to be at the surface (block from phone entirely), not at the action (the action would be too late). Server-side enforced via the two-gate pattern (tools-list filter in `stream_response` + `_execute_client_tool` deny double-check; never prompt-only).
- **Validation:** `py_compile` PASS; `scripts/self_update_test.py` **22/22 PASS** (4 schema + 3 no-confirm describe-path + 3 dirty-tree refuse + 2 already-up-to-date + 1 no-callback-wired honest message + 4 real-update-with-callback-fires + 3 pull-fails + 2 git-binary-missing). Live-validated: a spoken *"update yourself"* routed correctly to `update_jarvis` (telemetry: `self_update=yes`, `iters=2`), surfaced the describe text, the confirmation was declined, Jarvis stood by. The flagship-risk path (an unsafe pull, a bad restart hand-off) was the confirmation gate, which worked on the first try. The actual confirm=true → pull → restart path remains unverified live (it fires on the next real push), but the 22/22 mechanical coverage hits every branch.
- **Files:** `src/self_update.py` (NEW); `src/llm.py` (import + `_CLIENT_TOOLS` + tools list + `_RESTRICTED_DENY` + new system-prompt item 26); `main.py` (`register_restart_callback(ui._handle_restart)` one-line wire-up); `scripts/self_update_test.py` (NEW); `CLAUDE.md`; this entry.

**Reusable lessons (M64):** (1) **Tri-state where bi-state hides a meaningful third case.** A `bool` for "is the working tree dirty" is wrong — it conflates "no changes" with "couldn't tell" (git broken). Three values (`clean` / `dirty` / `unknown`) force the caller to branch explicitly, and the test that found the bug exists *because* the third case has its own visible name. Promote a flag to an enum the moment a flag swallows a meaningful third path. (2) **Match the confirmation gate to the irreversibility of the action.** Read-only tools don't need confirmation (M56 `homelab_status`, M62 `get_calendar_events`, M60 `status_report`). Code execution in an isolated sandbox doesn't need confirmation (M50 `run_code`; the container IS the boundary, zero host blast radius). Pulling code + restarting needs confirmation (M64; non-reversible from inside the session; pulled code immediately becomes running code). The gate isn't a property of "mutating" vs "read-only" — it's "can I undo this from where I'm sitting?". (3) **Delay the restart, don't race the speech.** The TTS player is single-track and queued; returning the success string and then immediately tearing down the UI would cut off the spoken line. Scheduling the restart 5 s later via a daemon thread is the simplest correct sequencing — no need for a "TTS finished" hook, just exceed the worst-case render time of one short sentence.

- **M64.1 — pre-pull commit preview** *(2026-05-28, same session)*:
  - **The UX gap from M64's live test:** the describe path returned a generic *"this will pull and restart, shall I?"* — with no indication of WHAT was about to be pulled. ## Milestone 65 — crash-resilience watchdog

*(2026-05-28)*:

- **What ships:** `jarvis_watchdog.pyw` — a new optional production launcher that supervises `main.py` and respawns it on crash. The reliability leg of today's "deployment + reliability" pair (M64 is deployment). Until M65, `jarvis.pyw` was launch-and-pray: if main.py crashed hard (an uncaught exception in a daemon thread's parent, a torch / dlib / cv2 native fault), the process died and nothing revived it — the failure was only noticed when Jarvis stopped responding. As the surface keeps growing (M58 audio classifier, M62.2 calendar polling, M56 homelab probing — all background threads), an unnoticed crash gets more expensive.
- **Architecture: exit-code-as-IPC.** The watchdog spawns `python jarvis.pyw` (NOT main.py — see the M65 spawn-target bug below) and `wait()`s on it. Three exit-code dispatches:
  - **0** — clean quit (Quit clicked). Watchdog exits 0 too. Supervision ends by request.
  - **42** — restart requested. M32 tray-restart and M64 self-update both set `ui.relaunch_mode = "normal"`. With the watchdog in the chain, main.py's relaunch block checks `JARVIS_WATCHDOG=1` (set by the watchdog in the child env) and instead of spawning a detached new process, exits with code 42 — the watchdog parent sees it and respawns. **The watchdog is the SOLE spawner of main.py** under this mode, so the old detached-spawn doesn't race the watchdog's respawn for the audio device.
  - **anything else** — crash. Respawn with a 2-second backoff + a rapid-restart cap (3 crashes in 60 s → give up, log fatally, exit 1).
- **The elevated-restart limitation (documented, accepted):** M41's "Restart Jarvis (Administrator)" uses `ShellExecuteW("runas")` which spawns the new elevated process independently and outside the watchdog's process group. The watchdog can't supervise the elevated child (you can't elevate a child of a non-elevated parent through Popen; UAC requires the shell verb). Main.py's relaunch block handles this case by always exiting 0 on `elevated` mode (watchdog gives up watching; the elevated child is unwatched). Acceptable since elevated mode is rare and interactive — someone is actively at the keyboard accepting UAC, not setting-and-forgetting.
- **Rapid-restart cap.** A bug that crashes Jarvis at startup would otherwise spin forever (each respawn crashes immediately, watchdog respawns, etc.). `_is_crash_looping(history)` is a pure function: if the most recent N restart timestamps are ALL within the cap window (default 3 in 60 s), give up. Cap counts ONLY real crashes, not user-driven restart-42s — alternating crash + restart was the test case that proved this (Scenario F in `watchdog_test.py`: 3 crashes with 2 restarts mixed in still hits the cap on the third crash).
- **Logs to jarvis.log via the same redirect.** `jarvis_watchdog.pyw` mirrors jarvis.pyw's startup: re-exec under venv pythonw if needed, redirect `sys.stdout`/`sys.stderr` to `jarvis.log` in append mode. Its own lines prefixed `[watchdog]` for grep. Both processes appending to the same log file is fine on Windows (`O_APPEND` semantics; line-buffered; short writes are atomic).
- **Additive, not replacing.** `jarvis.pyw` is unchanged and still works standalone — supervised mode is opt-in. **Same-session follow-on:** `src/autostart.py:_LAUNCHER` was flipped from `jarvis.pyw` → `jarvis_watchdog.pyw` after the live test confirmed the watchdog works, so the autostart `.lnk`, the desktop shortcut, and `autostart.relaunch()`'s tray-restart-when-not-under-watchdog path all default to supervised mode. The "additive" property holds — running `pythonw jarvis.pyw` directly is still untouched and works exactly as before; the change is only "what does the autostart machinery emit". Existing `Jarvis.lnk` shortcuts in `%APPDATA%\...\Startup\` need a one-time manual update (right-click → Properties → change `jarvis.pyw` to `jarvis_watchdog.pyw` in Target) OR a toggle of the tray's "Start with Windows" checkbox off then on (which calls `enable()` → re-writes the shortcut from the new `_LAUNCHER` constant).
- **Side effects moved into `main()`** so the module is importable for tests. The original draft ran `_ensure_correct_interpreter()` + `_redirect_to_logfile()` at module top-level; importing for tests would re-redirect stdout. Refactored to a `main()` entry that only runs under `if __name__ == "__main__"`.
- **The M65 spawn-target bug (live-test post-mortem).** First version spawned `python main.py` directly. Live test showed only the watchdog's own two lines in jarvis.log — main.py's prints were vanishing. Root cause: under `pythonw`, `sys.stdout` is None (no console attached); main.py's `print()` calls either crash or silently no-op. The watchdog's parent-process stdout redirect (Python-level only — sys.stdout reassigned, but fd 1 unchanged) doesn't propagate to the child's Python-level sys.stdout. Fix: spawn `jarvis.pyw`, NOT `main.py`. `jarvis.pyw` does its OWN stdout/stderr → file redirect *inside the child process*, so prints work. Bonus: the `--- Jarvis started ---` session marker (which M60's `count_session_errors` uses) is preserved. The `watchdog_test.py` harness uses synthetic `_FakeChild` objects, which is why this wasn't caught structurally — the test exercises the loop's exit-code dispatch, not the actual launcher chain. Live test caught it on first run.
- **Validation:** `py_compile` PASS; `scripts/watchdog_test.py` **17/17 PASS** — pure-function tests for `_is_crash_looping` (empty / single / N-1 / N-within-window / N-outside-window / mixed) + end-to-end scenarios for the loop's exit-code dispatch (rc=0 clean / rc=42 then rc=0 / crash + clean / 3 crashes cap / 100 user-restarts not counted / alternating crash + restart hits cap). All scenarios monkeypatched: synthetic `_FakeChild`, stubbed `_spawn_child`, no-op `time.sleep`. Live-validated the same session: launched `pythonw jarvis_watchdog.pyw`, log shows the three-line startup signature (watchdog → spawn → child started), full Jarvis ran nominally, clean quit exited watchdog cleanly (`[watchdog] child exited cleanly (user quit) — done`).
- **Files:** `jarvis_watchdog.pyw` (NEW); `main.py` (relaunch block reads `JARVIS_WATCHDOG=1` and exits 42 instead of spawning when set + "normal" mode); `scripts/watchdog_test.py` (NEW); `CLAUDE.md`; this entry.

**Reusable lessons (M65):** (1) **Exit codes are the cheapest IPC.** Two genuinely separate concerns — "the supervised process voluntarily asks for a restart" and "the supervisor decides whether to comply" — communicate through the OS's narrowest channel. No shared file, no socket, no pipe. The crash path (any non-zero exit other than 42) routes through the same code, so "crashed" and "voluntarily exited for restart" are the same shape to the watchdog, differentiated only by the integer. (2) **pythonw silently breaks `print()` in the child.** Under pythonw the process has no console; `sys.stdout` is None (or a silent stub). A subprocess spawned from pythonw inherits the parent's file descriptors but NOT the parent's Python-level `sys.stdout` object. If you reassigned the parent's `sys.stdout` to a file (the standard "logging redirect" pattern), the child still has its default sys.stdout (i.e. None). Fix: have the child do its own redirect *inside the child process* (jarvis.pyw does this). Spawn the .pyw, not main.py, under pythonw — main.py assumes a console, jarvis.pyw doesn't. (3) **Synthetic test harnesses miss launcher-chain bugs.** `watchdog_test.py`'s `_FakeChild` exercises the loop's decision logic perfectly — every branch of "what to do given exit code N." It does NOT exercise the actual spawn-and-run chain. The spawn-target bug was structurally invisible to that harness; only the live test could catch it. Synthetic harnesses are still worth writing (they catch the *decision* bugs cheaply), but they aren't sufficient — a launcher is a process-boundary thing and crossing the boundary IS the test.

## Milestone 66 — TMDB person filmography

*(2026-05-28)*:

- **What ships:** new `get_person_info` tool — *"What has Pedro Pascal been in?"* / *"What's Tom Hanks's next movie?"* / *"What films has Wes Anderson directed?"* / *"Who is X?"* (as a person). Returns the person's credits across film + TV combined, sorted by release date most-recent-first. The latent TMDB capability the M43 module deliberately deferred (the original M43 module docstring explicitly said *"a 'what has X been in' feature is deliberately out of scope"*).
- **Architecture: sibling tool, same module.** Deliberately a separate tool (`get_person_info`), NOT a 5th mode of `get_movie_tv_info`. The existing 4 modes are about TITLES (`query` = title; `media` filter movie/tv applies); a `person` mode would have made `query` polymorphic — title for some modes, person name for others, with Claude needing to disambiguate every call. Two tools, one description each, ZERO ambiguity in routing. Implementation lives in `src/tmdb.py` (shares `_api_key()`, `_http_get_with_retry`, the never-raises contract, the `_title` / `_media_label` / `_date_str` helpers).
- **Two-hop API call.** `/search/person?query=<name>` → top match by popularity (explicit re-sort to defend against TMDB's default ever changing — also disambiguates homonyms so the famous namesake wins over an obscure one); `/person/{id}/combined_credits` → cast (acting roles) + crew (directing / writing / production / etc).
- **Department filter** (`acting` default / `directing` / `writing` / `all`). Acting routes to the `cast` array. Directing/writing filter the `crew` array by job/department. `all` mode merges both with dedup-by-`(title, year, job)` — so a film someone wrote AND directed shows as TWO entries (different jobs — those ARE distinct contributions) but never duplicates within a single job. Unknown department falls back to `acting`.
- **Sort by release date desc, TBA last.** `_credit_sort_key()` returns the full `release_date` or `first_air_date`; empty string for unreleased entries sorts last when we reverse — correct UX ("upcoming, no date set" reads better AFTER the dated entries). Cap at 8 visible credits + overflow tag `(+ N more)`; voice replies should be short.
- **Format chosen for spoken legibility.** Acting: `(2023) The Last of Us (TV) — as Joel`. The character is what makes an actor's filmography legible — *as Joel* anchors recognition; without it, a list of titles is just titles. Crew: `(2024) The Phoenician Scheme (Movie) — Director`. The job is what was asked about.
- **System prompt** gains item 4b (paired with item 4 since they're sibling tools) — explicit title-vs-person disambiguation: *"For 'who directed X' or 'who starred in X' (a question ABOUT a specific title's cast/crew) call `get_movie_tv_info` with mode=details — the answer is in the credits field of THAT title, not in the director's filmography."* This is the probabilistic-routing discipline: claim *exactly* the tool's coverage. Calling out the other tool by name in the description nudges routing without over-claiming.
- **Validation:** `py_compile` PASS; `scripts/person_info_test.py` **29/29 PASS** — 4 schema; 1 missing API key; 2 missing/blank name; 1 person not found; 1 transport failure; 2 homonym disambiguation (lower-popularity homonym listed first in fixture, executor picks the higher-popularity one); 6 acting filmography (default mode) including TBA-last sort + crew-credits-excluded-from-acting; 4 directing filter (header / Director appears / acting excluded / Producer excluded); 3 writing filter; 3 all-mode dedup (Some Doc appears exactly twice — Director and Writer, different jobs); 1 department fallback (unknown → acting); 1 empty-credits friendly message. **Reusable lessons (M66):** (1) **Sibling tools beat polymorphic modes when the input shape differs.** Adding a `person` mode to `get_movie_tv_info` would have meant a `query` field that's a title for 4 modes and a person name for 1. That's two tools wearing one tool's clothes; Claude would have to disambiguate the mode every call. Two separate tools with separate schemas — `query` (title) vs `name` (person) — make routing unambiguous AT THE SCHEMA, not at the prompt. Polymorphism is fine for OUTPUTS (e.g. movie vs TV details share the same dataclass); it's expensive for INPUTS. (2) **Disambiguating descriptions call the other tool by name.** Item 4b's description ends with *"For 'who directed X' use get_movie_tv_info with mode=details"* — explicit, by-name, with the alternative mode also named. This is more reliable than abstract framing like *"for questions about specific titles"* — naming the alternative is what makes the routing rule deterministic-feeling. Same discipline as M51's confidence-trap clause. (3) **Sort key for "unreleased" matters.** TMDB returns `""` for unannounced dates. Naive `sort(..., reverse=True)` would put empty strings FIRST (lexicographic) — which means a TBA title would lead the filmography. Wrong UX: dated entries should lead. Empty-string-sorts-LAST is correct because `"".compare("2023-01-15") < 0` and `reverse=True` flips it — the string-comparison default Does The Right Thing here, but only by accident. Worth a one-line comment so future-you doesn't "fix" it.

## Milestone 67 — armed-stutter regression fix (acoustic speech-gate) + mic device pin

*(2026-05-28)*:

- **Trigger:** the armed-mode TTS stutter was reported *back*, alongside a switch to a new dedicated mic (MOVO MC1000). jarvis.log showed `[acoustic] stream status: input overflow` + `[audio] status: input overflow` clustering *continuously* the instant security armed — the exact signature the 2026-05-19 cooperative-speech-gate post-mortem identified as the input-side tell of a TTS output underrun.
- **Root cause — a gate that M58 silently outgrew.** The 2026-05-19 gate makes the SecurityWatcher's heavy CPU/GIL bursts (camera grab, YOLO, gc, face encode) mutually-exclusive-in-time with TTS via the shared `announce_speaking` Event. It was designed + validated *before M58 acoustic awareness existed*. M58 then (a) added a SECOND continuous CPU load — PANNs Cnn14 inference every ~2 s in `SoundDetector._infer_loop` — that **never received `announce_speaking`** (see the old `main.py` construction: no `speaking_event` passed), and (b) coupled acoustic to security (`armed = acoustic on`), so the two now ALWAYS run together. Result: during every proactive announce, the ungated PANNs loop kept hammering the CPU and starving the Python-fed TTS path → underrun → stutter. The regression was latent from M58 (2026-05-26); it surfaced the first time security was armed after the coupling shipped.
- **A second, stale assumption.** `security.py`'s torch-cap comment claimed *"YOLO is the only torch consumer."* False since M58 — PANNs is a torch consumer too. The global `torch.set_num_threads(1)` from YOLO only caps PANNs when security is ALSO armed; acoustic-while-attended (the independent tray toggle) ran PANNs uncapped, a second path to the same starvation.
- **Fix (mirror the proven pattern, don't invent a new one):** (1) `SoundDetector` now takes `speaking_event`; `_infer_loop` DROPS the dequeued window (skips the PANNs burst) whenever `_is_announcing()` — same bounded "deaf for the ~1-3 s an announce plays" tradeoff the watcher already accepts, and the bounded input queue means we resume on recent audio, not a stale backlog. (2) PANNs caps its own torch threads at load (`JARVIS_ACOUSTIC_THREADS`, default 1) so acoustic-while-attended doesn't starve audio either. (3) Corrected the false `security.py` comment. (4) `main.py` passes the shared `announce_speaking` into the detector.
- **Mic device pin (`JARVIS_MIC_DEVICE`).** New optional config: a device-NAME substring (case-insensitive, e.g. `MC1000`) or an integer index, resolved ONCE at startup by `audio.resolve_input_device()` and threaded into BOTH input streams (the main `AudioSession` and `SoundDetector`). Blank ⇒ Windows default (legacy behaviour, fully backward-compatible). The right design for a *dedicated* mic: pin Jarvis to it so the mic need not be the system default (leaving other capture devices free) and a USB re-enumeration can't silently reroute capture (relevant given the known KVM-audio gotcha). A name that matches nothing logs a warning and falls back to default — never fails to capture. The resolved device is logged so the binding can be confirmed.
- **Live finding — marketing name ≠ enumerated name.** `sd.query_devices()` on this box shows NO device containing "MOVO" or "MC1000"; the current Windows default (what the successful across-the-room test actually used) is `Microphone (3- PDP Audio Device)`. Budget USB mics rebrand OEM hardware and enumerate under a generic firmware string. Conclusion: don't pin to a guessed name — identify the device by an **unplug-diff** (snapshot device list, unplug, re-snapshot, the entry that disappears IS the mic) and pin to a substring of the REAL name. PENDING the unplug-diff.
- **Validation:** `py_compile` PASS (full gate); `scripts/acoustic_alert_test.py` **12/12 PASS** (the `_ClassTracker` logic is untouched — expected clean). `resolve_input_device` verified against the live device list (correctly enumerates inputs; correctly finds NO MC1000 match → would fall back to default, as designed). **Live-validation of the stutter fix PENDING** — arm security, trigger a few announces, confirm `input overflow` no longer clusters during speech + clean by ear. **Diagnostic ladder if residual:** the only two new M58 variables in the armed path are the PANNs loop (now gated) and the second 32 kHz InputStream; if a residual stutter remains after this, the stream coexistence is the culprit and the next lever is decoupling acoustic from auto-arming or sharing one capture.

**Reusable lessons (M67):** (1) **A cooperative gate is only as complete as the set of consumers wired into it — adding a new heavy consumer silently re-opens the bug.** The 2026-05-19 gate was *correct* and *validated*; M58 didn't break it, it added a new CPU load OUTSIDE it. The gate is a contract; new threads must opt in. (2) **A code comment that asserts an environmental fact ("X is the only torch consumer") is a landmine the moment the environment changes.** It read as true and authoritative for two milestones after it went false. Prefer comments that state intent ("cap torch so inference can't starve audio") over comments that state a census of the codebase ("YOLO is the only consumer") — the former stays true, the latter rots silently. Same "measure, don't assume" discipline as the M44 leak post-mortems.

- **The harness could NOT reproduce it — and that was the clue.** Gate-off (ungated PANNs), uncapped torch, full stack, 5 min per rung: **0 overflow every time.** The PANNs inference alone (~0.2 s / 2 s window) doesn't saturate this 4-core Ryzen enough to starve the audio callback. A non-reproducing control means the instrument lacks power, so per the `leak_repro` discipline its all-clear is untrustworthy — which forced the live test (exactly the harness's value: it ruled out the announce path and *forced* the real test).
- **The live test reproduced it instantly.** Armed + a once-per-minute test reminder → **stutter every 5–6 s, immediately.** The `jarvis.log` named the culprit: the stutter was on the **reminder-confirmation TURN REPLY** (`[user] remind me… → [jarvis] Done…`), not a proactive announce. Zero `input overflow` had ever wrapped a *proactive* announce in the broken session; the cluster was on the *turn reply*.
- **Root cause.** The cooperative speech gate `announce_speaking` has existed since 2026-05-19, but it is only ever SET by the **Announcer** thread (proactive announces, `main.py` `_build_announcer`). A **turn reply** runs `TurnRunner → speak_streaming` directly and set only `pc_speaking` (the 2026-05-29 mic-echo gate), **never `announce_speaking`**. So while armed, PANNs *and* the YOLO watcher (both gate consumers) ran straight through every spoken answer and starved it. The 2026-05-19 gate and M67 both only ever covered the *announce* path; turn replies — the most common TTS of all — were never gated for CPU. (Pre-M58 this was latent: YOLO alone during a turn reply wasn't enough to starve audio; M58 added PANNs as a *second* ungated load and tipped it over.)
- **The fix (`main.py`, four edits).** Thread `announce_speaking` into `TurnRunner` (ctor param → `self._announce_speaking`) and `set()`/`clear()` it around the spoken portion of the turn, guarded by `speaking_aloud`, in the SAME `if`/`finally` that already manages `pc_speaking`. Threaded through `listen_loop` (new kwarg) from the Announcer's Event in `main()`, so both paths share the one gate. The apology-on-error path is inside the same `try`, so it's covered too (the `finally` clears after it). Silent/phone turns never set it. **Exactly mirrors the 2026-05-29 omni-mic echo fix** — that extended `pc_speaking` from announce-only to both paths; this extends `announce_speaking` the same way. The mic-capture gate and the CPU gate are now symmetric: both cover all PC TTS.
- **Validation.** `scripts/turn_runner_test.py` Test 4c (audible turn SETS `announce_speaking` while speaking + CLEARS after; silent turn never sets it) → **35/35**; full regression gate **16/16**. **Live-validated:** re-ran the every-minute armed reminder → **zero stutter by ear**, and the fresh `jarvis.log` shows **zero `input overflow` wrapping any turn reply** (the patched path is clean).
- **Harness upgraded to a real regression instrument.** The first cut modeled only the *announce* path (it raised the gate around its own TTS), so it gated YOLO and never saw the bug. Reframed: PANNs + the YOLO co-load are wired as permanent gate consumers in both arms, and `--gate` now toggles only whether the *speaking path* raises the gate — `--gate off` = the pre-fix turn-reply path. With `--coloads full --gate off` it now reproduces (4 overflow / YOLO ticks **139** through the TTS) vs `--gate on` clean (0 / ticks **2**). The reproduction needs **both** PANNs+YOLO ungated — `--coloads none` (PANNs only) stays clean, the empirical proof that the live bug was the *combined* ungated load. The harness under-represents the live *severity* (single-digit overflow vs hundreds live) because it lacks the full live process (elevated priority, the Tk mainloop, all the monitors, LLM-streamed TTS) — documented as a known limit; the live full process is the severity gold standard.
- **Two residuals noted (neither audible, neither a regression).** (1) ~15 `input overflow` per *proactive announce* — pre-existing (the announce path is unchanged), input-side only, not audible. (2) `input overflow` during STT capture while armed. **An earlier write-up in this entry attributed this to "transcription degradation: the ungated PANNs/YOLO loops starve the capture stream → dropped frames → garbled transcripts." That attribution is RETRACTED — it was an over-attribution, withdrawn the same day once the missing fact surfaced.** The garbled transcripts cited (log lines L72/L86) were **background media audio bleeding into the open omnidirectional mic**, not audio corrupted by frame-drop — confirmed by the log itself (the "garbled" line at L86 is Whisper mishearing a spoken remark that the noise was *just a video playing in the background*; Jarvis replied *"background noise bleeding through"*, correctly diagnosing it in the moment). With that confound present, the garble is **zero evidence** for frame-drop. The capture-stream overflow is real and the loops demonstrably *can* starve audio (proven for the *output* path), but "real mechanism" ≠ "real harm": STT is remote (GPU) + robust to small gaps, the overflow counts were low, and no *clean* armed command has ever come back garbled. **Disposition: likely a false positive; do NOT chase it** (iterate-on-real-usage). The genuine, mundane phenomenon is just an always-on omnidirectional mic hearing the room — expected, and Jarvis handled it correctly (asked to clarify, accepted the correction). If a clean spoken command in a *silent* room ever returns garbled while armed, that's the signal — a 5-min controlled test (armed, silent, one clean command, watch for capture-window overflow) settles it.
- **Files:** `main.py` (TurnRunner ctor + audible-turn set/clear + `listen_loop` kwarg + `main()` wiring); `scripts/turn_runner_test.py` (Test 4c + the announce-gate observation slot); `scripts/acoustic_stutter_soak.py` (NEW — the fidelity-ladder soak instrument); `CLAUDE.md`; this entry.

**Reusable lessons (M68):** (1) **A cooperative gate has TWO sides.** M67's lesson was "every CONSUMER must opt in." M68 adds the dual: **every PRODUCER — every speaking path that plays audio — must RAISE the gate.** A gate set by only one of N speaking paths protects only that path; the most common path (turn replies) was the unprotected one. When you add a gate, enumerate *both* the consumers that must yield AND the producers that must signal. (2) **A non-reproducing control is information, not failure.** The harness couldn't reproduce the bug — which, rather than "the fix works," correctly meant "the instrument is too weak to certify, go find a stronger test." It forced the live run that found the truth. Trust the `leak_repro` rule: if the control can't show the bug, don't trust its all-clear. (3) **A synthetic harness can under-reproduce a soft-real-time scheduling bug.** Audio underrun is emergent from the *whole* live process (scheduler priority under elevation, the GUI mainloop, every background thread) — not a single isolable component like the M52 monitor or the M44.3 allocation. For this class, the live full process is the gold standard and the harness is a directional aid, not the verdict. (4) **The log is the real instrument.** The verbal report ("stutters every 5–6 s") plus the `jarvis.log` interleaving (overflow on the *turn-reply* line, not the announce) pinned the path in minutes — far faster than any amount of harness theorizing. Grep `-a` always (jarvis.log trips grep into binary mode). (5) **Do not write a plausible UNmeasured cause into the record as fact — the M44.3 trap, committed again here.** `input overflow` was observed co-occurring with garbled transcripts and "frame-drop degrades transcription" was written into this very entry as a finding — but a confound (background media audio in the open mic) explained the garble entirely, making the overflow *zero evidence* for it. This is the same correlation-causation error that blamed ultralytics for the M44 leak for two milestones. The fix is cheap discipline: when two things co-occur, ask "what else explains the *effect* on its own?" before claiming the *cause* — and label unproven hypotheses as hypotheses, not findings. The claim was retracted same-day once the missing fact surfaced.

## M69 — Speaker identification (Phases 1-4; P1-3 live-validated, P4 gate live-pending)

*(2026-06-01)*

- **What:** per-turn "who is speaking" from the same audio STT already captured, via Resemblyzer voice embeddings (256-d d-vectors, cosine similarity). The voice analog of M39 face auth — mirrors its shape (lazy-import `AVAILABLE` sentinel, enroll-average-N, defensive "never raise into the loop" contract) but differs two ways: **multi-user** (a registry of named speakers, not one encoding; `identify` returns the best match) and **cosine** not Euclidean (d-vectors are L2-normalized; HIGHER = more similar, the opposite sense to face distance). Two payoffs: an opt-in **"voice lock" gate** (answer only enrolled voices, ignore the rest — the fix for the open-omni-mic contamination, background media transcribed as spurious input) and a hook for per-speaker language / a future armed-mode "unknown voice" security signal.
- **De-risk FIRST (the M58 discipline).** Before building anything, `scripts/speaker_id_probe.py` (an interactive instrument — it records on cue, so the live prompts must be visible) measured whether the embeddings actually discriminate the primary voice on this mic: self-vs-self cosine **0.895** vs self-vs-media **0.566** (margin 0.33) → clean separation, PASS. Latency de-risk: the first `embed_utterance` took ~14 s (numba/torch JIT) but steady-state is **~30 ms** — so the cost is a one-time `warm()`, not a per-turn tax. Two install footguns caught: webrtcvad needs the MSVC toolchain (present, from dlib), and **resemblyzer drags in the legacy `typing` backport which SHADOWS stdlib typing on 3.12** — uninstalled, documented in requirements.txt.
- **Phase 1 — `src/speaker_id.py` (the tested core).** Multi-user registry (one `{slug}.npy` embedding + `{slug}.json` metadata per speaker, the M45 one-file-per-fact discipline — individually deletable); `enroll_from_audio` averages N clip embeddings then re-normalizes (mirrors face_auth's mean-of-encodings); `identify` takes the best cosine across the registry with a **fail-open contract** (any failure → `recognized=False`, the CALLER decides what unrecognized means); `warm()`; `embed()` runs Resemblyzer's `preprocess_wav` (VAD-trim + normalize) first. `scripts/speaker_id_test.py` **49/49** (encoder MOCKED so the suite needs no torch — the heavy-dep discipline).
- **Phase 2 — identify in the loop (read-only).** `Transcript` gained an `audio` field set in `transcribe_after_wake`, so identify runs on the SAME clip STT captured (zero re-capture; `None` on the empty/phone paths). The voice loop logs `[speaker] recognized <name> (score=…)` / `[speaker] unrecognized voice (best=…)`. Per-turn `load_registry` is sub-ms at personal scale, so a fresh enrollment takes effect on the very next turn with no reload plumbing.
- **Phase 3 — enrollment.** Voice intent "enroll my voice" + tray "Enroll my voice", mirroring M39's `_trigger_face_enrollment`. Capture opens its own short-lived `sd.rec` stream pinned to `JARVIS_MIC_DEVICE` (a second stream on the mic, the M58 coexistence) and records N consecutive clips while the speaker talks continuously. A background `warm()` fires at startup when a voice is already enrolled (so the first identified turn isn't a 14 s stall).
- **Phase 4 — the gate + named multi-user enrollment.** The **"voice lock" gate** is a runtime-toggleable `threading.Event` (tray "Voice lock" toggle + `JARVIS_SPEAKER_GATE`, mirroring the acoustic toggle): SET ⇒ a confidently-unrecognized VOICE turn is dropped (logged, silent — no "I don't know you" nag per stray media utterance). Placed BEFORE the security/enroll intents so a locked-out voice can't drive them; **the typed/console path is NEVER gated** (physical access = authorization) so there's no lock-out. **Named enrollment** of additional speakers runs through the reliable typed console command — `enroll voice SpeakerB`, `enroll voice SpeakerC in Spanish` (`parse_named_enroll_intent`, checked BEFORE the primary "enroll my voice" because "enroll voice X" also matches the primary's bare "voice"); spoken names work too but Whisper mangles them, so typed is the blessed path. One enrollment trigger handles both (name=None ⇒ primary).
- **Live validation (Phases 1-3, 2026-06-01):** recognized the enrolled primary speaker **0.83-0.95 across 7 turns** (including a 17 s ramble), background separated cleanly. **The load-bearing finding:** one turn scored **0.66** — the same speaker with a hoarse/rough voice, NOT a different person. vs media ~0.566. So a 0.70 gate would have **fail-CLOSED on a real enrolled user having a rough-voice day** — the worst failure. Default dropped **0.70 → 0.60**: below the rough-voice floor (fail-open: never ignore the real user), still above media, but the margin to media is now tight (~0.03) — explicitly a fail-open trade ("better to occasionally answer the television than ignore a hoarse enrolled user") and tunable via `JARVIS_SPEAKER_THRESHOLD`. **Phase 4 is MECHANICALLY validated only (gate 17/17); the gate-drop + second-speaker enrollment are LIVE-PENDING.** *(Note: this 0.60 default was later shown to be built on contaminated data and corrected to 0.72 — see M80.)*
- **Decisions.** (a) Identification activates by ENROLLING (no separate enable flag) — labeling who spoke is harmless. (b) The gate is opt-in AND fail-open because a false-reject (ignoring a real person) is strictly worse than a false-accept (answering the television). (c) Speaker-ID-as-a-gate is a great filter for media but a **blunt instrument for people** (anyone unenrolled is locked out) — so in a multi-person setting you either enroll everyone or leave the gate off; surfaced as an explicit choice, and the chosen configuration was gate-on + enroll-every-regular-speaker. (d) Per-speaker language is the WEAKEST justification (Whisper already auto-detects per turn) — the real unique value is the gate + the security signal.
- **Files:** `src/speaker_id.py` (NEW), `scripts/speaker_id_test.py` (NEW, 49/49), `scripts/speaker_id_probe.py` (NEW — kept as the threshold-tuning instrument), `src/speech_to_text.py` (`Transcript.audio`), `main.py` (identify + gate in the loop, enroll triggers + intents, warm at startup, `speaker_gate` plumbing), `src/ui.py` + `src/tray.py` ("Enroll my voice" + "Voice lock" toggle), `src/config.py` (`speaker_threshold` 0.60, `speaker_gate_enabled`, `user_name`), `requirements.txt` (resemblyzer + the typing footgun), `.env.example`, `CLAUDE.md`, this entry.

**Reusable lessons (M69):** (1) **De-risk the model on the REAL signal before building the subsystem.** The probe (self-vs-self vs self-vs-media on the actual mic) is what justified Resemblyzer over the heavier SpeechBrain ECAPA, and proved discrimination before a single line of the gate existed — the M58 "measure latency before you ship" lesson, generalized to "measure the discriminating power too." (2) **The degraded clip is the threshold oracle, not the clean enrollment.** The 0.66 rough-voice turn — almost mistaken for a different speaker — is what set the threshold; a fail-open gate must be tuned against the WORST realistic clip, not the best. Tuning on the 0.895 enrollment would have shipped a gate that ignores its owner on a sick day. (3) **A gate over PEOPLE is fundamentally different from a gate over media** — false-rejecting a person is a real harm, so default off + fail-open + enroll-every-regular-speaker, and say so out loud rather than quietly shipping a lock-out. (4) **Pick the reliable input channel for the error-prone part.** Names via Whisper are a coin-flip; named enrollment routes through the typed console where the name is exact — same "reliable channel for the hard part" instinct as confirmation-gating destructive actions. (5) **Don't invent specifics.** A placeholder proper noun was written into an early draft of this entry with zero basis and had to be corrected — a fabricated detail stated plainly is the same failure class as M68's unmeasured-cause-as-fact.

## Debugging session — three live-failure fixes

*(2026-06-02)*

- **Trigger.** A typed message "did nothing," then two retries errored, while setting up a monitor for an event-registration opening. A pass through `jarvis.log` found three distinct, independent issues plus two watch-only ones.
- **#1 — `web_search` `container_id` 400 (the blocker).** `WEB_SEARCH_TOOL` was pinned to `web_search_20260209`, whose **dynamic filtering** silently spins up an Anthropic code-execution container; that container threads a `container_id` through the rest of the turn. The agentic loop's container-capture (`final.container` -> `stream_kwargs["container"]`, added M52) proved unreliable when a search was **interleaved with a client-side tool call** (the triggering query did several `web_search`es AND `set_reminder`s), so the re-stream 400'd: *"container_id is required when there are pending tool uses generated by code execution with tools."* This is **the identical error M19 hit with `web_fetch`** — fixed back then by downgrading `web_fetch` to the non-dynamic-filtering `_20250910`. `web_search` was simply never downgraded (on `_20260209` since M12, never exercised hard enough). **Fix:** pin `web_search` -> `web_search_20250305` (the GA version, no dynamic filtering — verified present in SDK 0.97.0). The error class disappears because there's no container to mishandle. The container-capture code stays as defense-in-depth. Live confirmation pending a heavy multi-search query, but the mechanism is structural.
- **#2 — silent failure at the iteration cap.** The first typed turn didn't vanish — it hit `_MAX_LOOP_ITERATIONS=5` (Claude burned all 5 iterations on searches + reminder-juggling) and the `while-else` only *logged*, so the generator ended with no final text = **dead silence**. **Fix:** raised the cap 5 -> 8 (research-style asks legitimately chain more tool calls) AND the `while-else` now `yield`s a spoken fallback so a capped turn degrades to a sentence instead of silence.
- **#3 — recurring reminders couldn't defer their first fire.** Claude narrated this itself mid-turn: *"the recurring reminder fired immediately rather than waiting."* True design gap — `execute_set_reminder` intentionally IGNORED `at`/`delay_seconds` when `repeat` was set, so "every 5 minutes **STARTING at 7:50pm**" was inexpressible (an interval started firing `now+interval`, all day). **Fix:** extracted a shared `_resolve_explicit_fire` tri-state helper (datetime / error-string / `None`) and made an `interval` recurrence honor an explicit first-fire time when given, then re-arm on the interval from there (the M54 re-arm already computes from `now()` each fire, so it stays correct). `weekly`/`monthly` carry their own day+time and still ignore `at`/`delay`. Tool schema + property descriptions updated so Claude knows the capability exists.
- **New test net.** M53/M54 reminders shipped WITHOUT a suite — the "a gate with no enforcing test" gap the M67 post-mortem named, and #3 touched the reminder time-math. Added `scripts/reminders_test.py` (**38 assertions**, hermetic — redirects `LOCALAPPDATA` to a temp dir before import, asserts the store path is isolated, so it never touches the real `reminders.json`): the deferred-start fix, weekly/monthly ignoring at/delay, the legacy interval path, the refactored one-shot paths, the `_resolve_explicit_fire` tri-state, and the M54 `pop_due` re-arm contract. Full gate **18/18**.
- **Watch-only (not fixed, by design).** (4) A native crash `exit 1073807364` (`0x40010004`) fired right after `[speaker] voice-lock gate ON` — brand-new M69 code; the M65 watchdog caught and respawned it cleanly, no work lost. Single occurrence -> watch-and-note; if it recurs on the voice-lock toggle, *that's* the signal to instrument. (5) A `websockets` handshake `EOFError` traceback from a dropped phone/TLS pre-probe — cosmetic log noise, different path than the M48.2c `ConnectionResetError` handler swallows.

- **Reusable lessons:** (1) **A "belt + suspenders" fix needs BOTH halves applied everywhere the hazard exists.** M19 added the suspenders (downgrade) for `web_fetch` and the belt (container-capture) for the loop — but left `web_search` on the dynamic-filtering version, trusting the belt alone.
