## Milestone 16 — file picker + attachments (PDF / image / text)

- `src/attachments.py` (`load_attachment`): pure helper. Takes a path; returns `(content_block, error)` (exactly one is None). - `src/console.py`: attach button next to the entry; a chip frame above the entry shows `filename ✕` when a file is staged; ✕ unstages. File picker via `tkinter.filedialog.askopenfilename` (stdlib; blocks Tk's mainloop only — worker threads keep running). - `main.py`: `process_question` gained an optional `attachments: list[dict] | None` param. When present, the user message becomes `[*blocks, {"type":"text","text":<typed>}]` instead of a plain string; history keeps that structure verbatim, so multi-turn Q&A about the same document works naturally until reset/trim. `text_input_loop` unpacks `(text, attachments)` from the queue and forwards just the blocks to `process_question`.
- **Persistence trade-off** (accepted): documents stay in history for the whole conversation (or until `_trim_history` drops them). - **Shutdown hardening (bundled in this commit):** `summarize_session` now constructs its Anthropic client with `max_retries=0, timeout=8.0` so a Haiku 429 or hang fails fast (best-effort skip) instead of blocking the `worker.join` on quit. `worker.join` timeout bumped 20s → 30s for headroom. Together: a 429 during seal logs the error, returns `""`, and shutdown completes well under the join window. Raw turns are already on disk via `record_turn`, so a skipped summary loses at most a one-line index entry — never conversation content.

## Milestone 17 — audio waveform visualizer (real amplitude reactivity)

- `src/text_to_speech.py`: `speak_streaming()` gained an optional `on_amplitude: Callable[[float], None]` param. Per sentence, before `sd.play(blocking=True)`, we pre-compute the RMS envelope at 33ms windows via `_compute_envelope` (NumPy reshape + `sqrt(mean(x²))`, normalized against int16 full scale of 32768). A daemon ticker thread (`_run_envelope_ticker`) walks the envelope using `time.monotonic()` for drift-free real-time stepping, calling `on_amplitude(level)` once per window. The ticker stops via a `threading.Event` the instant `sd.play` returns. The audio path is **untouched** — the ticker only reads the envelope and emits values.
- `src/console.py`: 24-bar `tk.Canvas` (~400×44) packed between the state pill and the transcript. Resting line at 2px when idle. `set_amplitude(level)` is thread-safe (clamp + `.after(0, ...)` marshals onto Tk). `_wave_tick` runs at 30 fps independently of the existing 8 fps state-pulse: decays stored amplitude (factor 0.85 per frame, ~99% gone in 0.3s), per-bar phase oscillation (golden-angle distribution — deterministic but irregular, no `random` import), smoothing factor 0.4 to dampen jitter, then mutates only the y-values of pre-cached x-coords.
- `src/ui.py`: pass-through `set_amplitude`. `main.py`: the `speak_streaming` call now passes `on_amplitude=ui.set_amplitude`. Voice and text paths both benefit (they share the same `process_question`).
- **Sync quality**: the ticker thread starts immediately before `sd.play`, so the envelope walk and audio playback are in sync to within one window (~33ms) — imperceptible. Between sentences the bars naturally decay during the synth gap, giving a slight "breath" effect that mirrors real speech rhythm.
- **Why a pre-computed envelope** (vs. streaming via `sd.OutputStream` callbacks): it keeps the audio path identical to before (zero regression risk), and amplitude data is stored in memory (cheap — <1KB per sentence) rather than computed on the audio thread, which can cause underruns.
- Future LISTENING-state reactivity (bars reacting to mic input) deferred — it would need a hook into `transcribe_after_wake`'s mic stream. Easy follow-up if it ever feels worth it.

## Milestone 21 — first MCP integration: Plex Media Server

- `src/plex_mcp.py` (`PlexMCPClient`): synchronous façade over an async MCP stdio session. Spawns `python -m plex_mcp_server --transport stdio` as a subprocess, runs `ClientSession.initialize()` + `list_tools()`, then awaits a stop event to keep the context managers alive for the app's lifetime. A dedicated daemon-thread event loop runs the async work; `call_tool(name, args)` synchronously dispatches via `asyncio.run_coroutine_threadsafe(...).result()` and blocks. Defensive contract (matching sports/weather): never raises — bad input, dead server, and timeout all become readable strings.
- **Architectural decision: async↔sync bridge over a full asyncio refactor.** The MCP Python SDK is async-only; our agentic loop in `src/llm.py` is sync (anthropic's `client.messages.stream(...)` is a sync context manager). Rewriting the whole loop in asyncio would touch every tool path. Wrapping just MCP keeps the blast radius to one file. The pattern is reusable for the next async-only library (Home Assistant SDK, OctoPrint async client, etc.).
- **Plex token passed through subprocess env vars, not `--plex-token` CLI args.** Keeps the token out of `ps` / Task Manager listings — the same hygiene as API keys in scripts. plex-mcp-server reads `PLEX_URL` / `PLEX_TOKEN` from the environment when CLI args are unset.
- **Voice-friendly allowlist.** plex-mcp-server exposes 55 tools — far too many for Claude to wade through every turn, and many are dangerous (deletes, edits, scans) or useless for voice (artwork blobs, server admin telemetry, niche client surfaces like `navigate` / `set_streams`). The filter is permissive-include (search/list/get/play/etc.) + strict-exclude (destructive verbs, mutation verbs, whole categories `server_*` / `playlist_*` / `collection_*`, artwork/poster, admin user-management). After tightening against real-server output: 55 → **18 tools** kept across library / media / client / sessions / user. Each is a legitimate voice query ("what's playing", "search media", "library stats", "play X on living room", "what's on deck", "watch history").
- `src/llm.py` plumbing: `stream_response` gains an optional `plex_client`. When present, `_PLEX_PROMPT_ADDENDUM` is appended to the system prompt (gated on actual session presence, so a graceful-fail startup does not promise Claude tools that do not exist), the 18 Anthropic-formatted tool schemas are appended to the `tools` list, and `_execute_client_tool` routes any name in `plex_client.tool_names` through `plex_client.call_tool()`. Telemetry adds `mcp_tools=tool1,tool2` so the log shows exactly which Plex tools fired in a turn.
- `main.py`: `_try_connect_plex(cfg)` runs before `JarvisUI()` — graceful: missing creds / unreachable server / MCP server crash all log + return None, after which Jarvis runs with the existing 4-tool kit. On shutdown (after `worker.join`), `plex_client.close()` cleanly signals `_serve` to exit, awaits the context-manager unwind (5s bound), and joins the loop thread.
- **Tool result formatting:** an MCP `CallToolResult.content` is a list of content blocks (text / image / embedded). For voice we only want text — concatenate text blocks, mark `isError=True` with a "Tool error:" prefix so Claude can apologize, and truncate at 2000 chars (Claude summarizes anyway).
- **Why MCP over a custom Anthropic tool here:** plex-mcp-server is a maintained community implementation (last release Feb 2026, 51+ tools, OAuth-ready). We are a downstream consumer, not the only consumer — exactly the case where MCP earns its keep. The general rule stands: default to a custom Anthropic tool; reach for MCP only when a maintained server is reused across clients.
- Tested end-to-end: "What libraries do I have on the Plex server?" → `library_list` fires, Claude replies *"Two libraries: Movies, with 1,101 titles, and TV Shows, with 66 series. Both were updated just this morning."* Telemetry: `mcp_tools=library_list iters=2`, 10k tokens read from cache (system prompt + 18 schemas cached after the first turn). Graceful fall-through on missing creds confirmed (smoke-tested by running `library_list`, `sessions_get_active`, `client_list` directly through `PlexMCPClient` before wiring them through Claude).

## Milestone 22 — gaming tool (RAWG: release dates, summaries, popular titles, recommendations)

- `src/games.py` (`GAMES_TOOL`, `execute_games_tool`): single client-side tool over RAWG's free public API (~half a million games, every major platform, metacritic/ESRB/genre/tag metadata, no OAuth — just a `key=` query param, 20k req/month free). Four modes covering the natural voice-query distribution: `search` (top 5 brief matches — *"When does GTA 6 come out?"*), `details` (2-hop: search → /games/{id} for the full description, truncated at 600 chars on a sentence boundary — *"Tell me about Death Stranding 2"*), `popular` (`ordering=-added` filtered by platform + timeframe — *"What's hot on Switch right now?"*), `similar` (recommendations — *"I loved Hollow Knight, what else would I like?"*). Same defensive contract as sports/weather/plex: never raises, always returns a readable string; missing key, lookup miss, network failure, and malformed JSON all become voice-friendly error messages.
- **RAWG vs IGDB trade-off (recorded):** IGDB has slightly richer metadata (Twitch/Amazon-owned, Steam-grade detail) but requires a Twitch dev account and a `client_credentials` OAuth flow. RAWG is one signup, one query param, comparable coverage for voice-grade queries. Picked the lower-friction option; revisit if data quality becomes a real complaint.
- **Custom Anthropic tool over MCP (recorded again):** no maintained, voice-friendly gaming MCP server exists at the level of plex-mcp-server. Per the custom-tool-vs-MCP rule, MCP earns its keep when other clients reuse the server — for a single-consumer gaming tool, a custom Anthropic tool is the right call.
- **`/games/{id}/suggested` is paywalled — we built our own similarity instead.** Discovered during M22 end-to-end testing: free-tier keys hit a consistent HTTP 401 on `/games/{id}/suggested`. Rather than degrade or pay, `_do_similar` now uses a 3-hop fallback: `search → /games/{id} for genres + tags → /games?genres=X&tags=Y&exclude_games=ID&ordering=-added`. Genres are coarse (Action, RPG); tags are specific (`survival-horror`, `cyberpunk`, `atmospheric`); combining both makes RAWG's filter behave as "broadly this kind of game, specifically these flavors". The dedicated `/suggested` probe is dropped entirely (we know it 401s; pinging it adds latency + log noise without value). Verified end-to-end with *"I love Pragmata and Resident Evil 9, recommendations?"* → BioShock Infinite, Tomb Raider, Portal, RDR2, with real RAWG data instead of Claude's training cutoff.
- **Platform mapping (`_PLATFORM_IDS`):** voice queries say "Switch" / "PS5" / "Xbox", not "187". Hardcoded a small map for the platforms that come up in voice — Nintendo (Switch, 3DS, Wii U, Wii), PlayStation (5, 4, 3, 2, Vita), Xbox (Series, One, 360), PC, iOS/Android. RAWG has hundreds more, but most never come up.
- **Switch 2 caveat (mapped to id=7 with a comment):** as of 2026-05, RAWG has not split Switch 2 from Switch in their platform catalog — even Switch 2 *exclusives* like Mario Kart World are misclassified under "Nintendo Switch" (id=7). Confirmed via the `/platforms` and `/platforms/lists/parents` endpoints (the Nintendo family stops at Switch). Pragmatic mapping: `"switch 2" / "switch2" / "nintendo switch 2"` → id=7, with a code comment explaining the limitation. The caller gets results (which currently include Switch 2 titles correctly, *because* of the misclassification) instead of an "unknown platform" error. When RAWG splits the catalog (likely within the year), update one line.
- **`_http_get_with_retry` is now triplicated** (sports.py / weather.py / games.py) — at three copies of a ~30-LOC helper the cost-benefit flips toward extraction (rule of three). Flagged for the next tool that needs it: pull it into `src/http_util.py` with a per-tool log-prefix argument.
- **Config decision: `RAWG_API_KEY` read at call time via `os.getenv`, not threaded through `Config`.** Unlike `PLEX_URL`/`PLEX_TOKEN` (which `main.py` reads at startup for graceful-fail logic), the RAWG key is consumed only inside `games.py`. Reading at call time keeps it hot-swappable in development (no restart to add a key), and the `Config` dataclass is `frozen=True` anyway — adding a field there would force a restart. The same asymmetry would apply to weather.py if Open-Meteo needed a key.

Telemetry: `games_tool=yes` joins the existing markers.

## Milestone 23 — local PC diagnostics + allowlisted system control (the Iron Man Jarvis foundation)

- `src/pc_diagnostics.py` (`PC_DIAGNOSTICS_TOOL`, `execute_pc_diagnostics_tool`): read-only Windows telemetry over `psutil` + PowerShell `Get-WinEvent`. Eight modes covering the natural voice-query distribution: `overview` (CPU/RAM/disk/uptime one-liner), `cpu` (% + top processes by CPU), `memory` (% + top processes by RAM), `disk` (per-volume free space), `processes` (top N sorted by CPU or memory), `services` (Windows services, optionally substring-filtered), `events` (System log Errors/Warnings from the last 24h), `network` (interface IPs + throughput counters). Same defensive contract as sports/weather/games/plex_mcp: never raises, always returns a readable string, voice-friendly phrasing throughout (`"44% used"` not `"0.4421 ratio"`), output capped at `limit=10` (max 25). Read-only by design — nothing in this module modifies state.
- `src/system_control.py` (`SYSTEM_CONTROL_TOOL`, `execute_system_control_tool`): seven allowlisted actions: `open_app`, `lock_workstation`, `volume_set`, `volume_mute`, `volume_unmute`, `screen_off`, `kill_process`. No arbitrary command execution. App launches resolve names against `_APP_ALIASES` (~25 entries: edge / chrome / firefox / notepad / vs code / terminal / task manager / settings / etc.); unknown names return an error string, never a `Popen` of attacker-controlled text. Volume via pycaw; lock/screen via direct `ctypes` user32 calls (no extra deps); process kill via `psutil`.
- **Architectural decision: read-only diagnostics ≠ action control.** Two separate tools with different risk profiles. Diagnostics runs freely without confirmation (it cannot break anything). Actions have voice-confirmation rules in the system prompt AND a server-side confirmation gate inside the tool itself for the most destructive action (`kill_process`). The general rule: separate read-only tools from write tools, and enforce destructive-action confirmation IN the tool, never only in the prompt.
- **Server-side enforcement of `confirmed=true` on `kill_process`.** Not merely a system-prompt instruction — the tool itself rejects the call if `confirmed` is missing or false, returning *"kill_process requires explicit user confirmation. Ask the user to confirm terminating 'X', then call this tool again with confirmed=true"* instead of killing anything. This means a misbehaving prompt, a hallucinated tool call, or a future model regression cannot bypass the confirmation. Validated live: *"Kill notepad"* → Jarvis spoke *"Confirm: terminate notepad.exe?"* → *"Yes"* → a second call with `confirmed=true` → terminated.
- **Why no credentials-in-`.env` shortcut for remote access.** An early proposal was to put Windows local-account credentials in `.env` to extend Jarvis to the Plex laptop. Rejected: `.env` is plaintext on disk, easily exfiltrated by accident (cloud sync, screenshot, paste into a chat), and OS passwords are not revocable the way API keys are. Agreed plan: **M24 uses SSH key-based auth** (Windows 10/11 ships OpenSSH; one keypair, one paste of the public key into the target's `authorized_keys`, no password ever in any file).
- **Three psutil smoke-test fixes (caught before voice testing):**
  1. **Per-service try/except in `_do_services`.** Some services on a typical Windows install have stale registrations whose `QueryServiceConfig2W` raises `WinError 2`; without the catch, the first broken service aborts the whole iteration. Now they are skipped and iteration continues.
  2. **CPU percentage normalization.** `psutil.Process.cpu_percent()` returns a per-core percentage (the top/ps convention) — `System Idle Process` showed 726.8% on a 12-core box, crowding out real top processes. Normalized by `_CPU_CORES = psutil.cpu_count(logical=True)` for display (the Task Manager convention), and added `_PROCESS_BLOCKLIST = {"system idle process"}` since it represents *idle* time, not load.
  3. **IPv4 detection in `_do_network`.** The original `str(family).endswith("AF_INET")` did not match on this build (psutil's `AddressFamily` repr varies). Replaced with a direct `socket.AF_INET` comparison + a `127.x` filter for loopback regardless of interface name (Windows interface names vary across builds).
- **Two pycaw fixes that surfaced only in voice testing:**
  1. **`comtypes.CoInitialize()` per thread.** The agentic loop runs in a worker thread (text_input_loop / listen_loop) where COM may not have been initialized — bare pycaw calls fail with `[WinError -2147221008] CoInitialize has not been called`. `_get_audio_endpoint()` now calls `CoInitialize()` defensively before any audio-device access. The call is idempotent — it returns `S_FALSE` if already initialized, a no-op. We deliberately do NOT call `CoUninitialize()`, so the worker thread retains its initialized COM threading state for subsequent calls.
  2. **pycaw 20251023+ API change.** `AudioUtilities.GetSpeakers()` now returns an `AudioDevice` Python wrapper, not the raw `IMMDevice` COM object — so the old `devices.Activate(IAudioEndpointVolume._iid_, CLSCTX_ALL, None)` raises `'AudioDevice' object has no attribute 'Activate'`. The new API is the wrapper's `EndpointVolume` property (lazy-cached; it performs the `.Activate()` internally). A single-line fix once located. The fix dossier (both the COM-init reason and the API-change history) lives in the docstring of `_get_audio_endpoint()` so it does not have to be re-derived.
- **App-launch via `cmd /c start "" <exe>`.** The cleanest Windows-native launch: it respects the App Paths registry (Edge/Chrome resolve without being in `PATH`), supports the `ms-settings:` protocol handler, and returns immediately (start spawns + detaches). `subprocess.Popen` is invoked with a list (not a shell string) so quoting is handled by Python; `exe` only ever comes from `_APP_ALIASES`, never from user input — no injection surface.
- **Event log via PowerShell `Get-WinEvent`** rather than pywin32. Why: pywin32 is an ~80 MB install for one feature, and `win32evtlog` is a mouthful. `Get-WinEvent` is built into every Windows install and returns structured JSON via `ConvertTo-Json -Compress`. Each `Message` field is truncated at 160 chars inside the PowerShell pipeline (Event Log messages can be many paragraphs of stack-trace prose) — keeping payloads short for voice summarization. An 8s subprocess timeout caps the rare case where the System log is enormous or busy.
- `src/llm.py` plumbing: both tools registered alongside the existing five (`tools=[WEB_SEARCH_TOOL, WEB_FETCH_TOOL, SPORTS_TOOL, WEATHER_TOOL, GAMES_TOOL, PC_DIAGNOSTICS_TOOL, SYSTEM_CONTROL_TOOL]`); a new "Local PC control" section in the system prompt advertises both tools with explicit safety rules ("for kill_process, ALWAYS ask first; for low-impact actions, just announce and do it; for *'fix my PC'* / *'improve performance'* requests, diagnose first then propose — never apply unrequested changes"). Telemetry: `diagnostics=yes` and `sysctl=yes` join the existing markers.
- `requirements.txt`: `psutil>=5.9` + `pycaw>=20240210` (the transitive `comtypes` was already present from MCP).
- Tested end-to-end live: *"How's my PC doing?"* → overview (CPU 9% / RAM 62% / C: 77% / 9h uptime), closing with *"nothing alarming"*. *"What's heating up my memory?"* → memory mode + top processes. *"Any errors in the last day?"* → events mode found a real application-update failure, two Secure Boot SBAT events (correctly triaged as known-harmless), and service-binary-missing errors that Jarvis identified as remnants of uninstalled software. *"What's my IP?"* → network mode returned the Ethernet address (192.168.x.x) plus the Hyper-V vSwitch on its own subnet. *"Open Edge"* / *"Lock the workstation"* → both worked. *"Set volume 230"* → Claude pushed back conversationally (*"Volume only goes up to 100"*) before calling the tool. *"Set volume to 30"* / *"…to 100"* → both fired. *"Mute"* / *"Unmute"* → both worked after the COM/pycaw fixes. **Confirmation flow validated:** *"Kill notepad"* → *"Confirm: terminate notepad.exe?"* → *"Yes"* → process terminated; the server-side gate held under voice. As a bonus, *"What's the most played movie in the Plex library?"* triggered a 5-iteration agentic chain across four MCP tools (`library_get_contents` → `sessions_get_media_playback_history` → `user_get_info` → `user_get_statistics`) — emergent multi-tool composition that the M13/M21 architecture made possible, validated alongside the new M23 tools.

## Milestone 24 — remote Plex laptop diagnostics over SSH (first remote-host tool)

- `src/plex_laptop.py` (`PLEX_LOGS_TAIL_TOOL`, `PLEX_LOGS_SEARCH_TOOL`, `PLEX_LAPTOP_HEALTH_TOOL` + `PlexLaptopClient`): three voice-grade read-only diagnostic tools that reach the Plex laptop (hostname MEDIA-HOST, a private-LAN 192.168.x.x address) over SSH. `plex_logs_tail` returns last N lines of `Plex Media Server.log`; `plex_logs_search` does case-insensitive .NET-regex search via `Select-String`; `plex_laptop_health` mirrors M23's `pc_diagnostics` modes (overview/cpu/memory/disk/network) but executes on the remote box. Same defensive contract as the rest of the toolkit — connection failures, command non-zero exits, parse errors all become readable strings; never raises. Read-only by hard contract; no service restarts, no log rotation, no file deletes — that's M25's territory if we ever build it.
- **Architectural decision: paramiko + persistent connection + lazy connect.** paramiko is sync (matches `src/llm.py`'s stream loop — no async↔sync bridge needed unlike the M21 MCP integration), pure-Python (cryptography is the only binary dep, already pulled by anthropic), and the same library Ansible uses underneath. Subprocess'ing `ssh.exe` per call would add 200-400ms of handshake to every tool turn; persistent connection + one auto-reconnect (idle timeout / wifi blip) keeps voice latency low. **Lazy connect** — `_try_connect_plex_laptop` only constructs the client + validates params at startup, the actual TCP+SSH handshake is deferred to the first tool call. So the laptop being off costs zero startup latency; voice queries to other tools work normally, and only an actual remote tool call surfaces "Plex laptop unreachable".
- **PowerShell via `-EncodedCommand` (Base64 UTF-16-LE).** Scripts cross Python → ssh client → remote cmd.exe → powershell.exe — four layers of quote-handling. EncodedCommand is opaque to every layer except powershell.exe (which decodes the Base64), sidestepping the entire class of `$env:LOCALAPPDATA`-not-expanding bugs we hit during the SSH-setup phase. `_ps_encoded()` also prepends `$ProgressPreference = 'SilentlyContinue'` defensively — first-time module loads emit "Preparing modules for first use" progress records that get serialized as CLIXML over the remote channel and corrupt our JSON output (caught during M24 smoke testing on `Get-NetAdapter`).
- **Host-key trust from `~/.ssh/known_hosts`** (`load_system_host_keys` + `RejectPolicy()`). The setup phase captured the laptop's host key interactively; from now on, if it ever changes, paramiko fails closed rather than silently trusting a new identity (no TOFU). Failing closed is the right default for a programmatic client that can't ask a human.
- **SSH transport setup (one-time, walked through end-to-end):** Win10 OpenSSH Server enabled via `Add-WindowsCapability -Online -Name OpenSSH.Server~~~~0.0.1.0` + `Start-Service sshd` + `Set-Service -Name sshd -StartupType Automatic`. ed25519 keypair generated on the PC, **no passphrase** (NTFS permissions on the private key file are the security boundary; appropriate for a desktop the operator controls — passphrase + agent caching would break the Jarvis-as-autostart-service flow). Admin-user gotcha: because the login account is in the local Administrators group on the laptop, OpenSSH ignores `~<user>\.ssh\authorized_keys` and only reads `C:\ProgramData\ssh\administrators_authorized_keys` (per the default `Match Group administrators` block in `sshd_config`). Strict ACLs required (`icacls /inheritance:r /grant 'Administrators:F' /grant 'SYSTEM:F'`) or `StrictModes` silently rejects. Lockdown: `PasswordAuthentication no` + `KbdInteractiveAuthentication no` (must add the latter explicitly — Windows OpenSSH default is undefined-but-on, not in the file). Firewall rule scoped to Domain/Private profiles only, so Public networks stay closed even if password auth ever gets re-enabled.
- **Broken WMI provider on the laptop — flagged + worked around twice.** During setup, `Get-NetFirewallRule` raised `HRESULT 0x80041010 "Invalid class"` against `MSFT_NetFirewallRule` (the entire `ROOT/StandardCimv2` namespace is broken on this box, likely a botched Windows update). Used `netsh advfirewall firewall add rule` instead — pre-WMI legacy interface, doesn't depend on the broken provider. Bit again during M24 smoke testing when `_HEALTH_NETWORK_PS` originally used `Get-NetAdapter` / `Get-NetIPAddress` — same provider, same failure. Switched to `[System.Net.NetworkInformation.NetworkInterface]::GetAllNetworkInterfaces()` (pure .NET, no WMI dependency at all). Old-style `Win32_*` CIM classes (used by overview/cpu/memory/disk via `Get-CimInstance`) live in `ROOT/CIMV2` and are unaffected. Recorded as a standing host-specific note so it doesn't have to be re-derived: avoid NetTCPIP / NetSecurity module cmdlets on this box; .NET or netsh is safe.
- `src/llm.py` plumbing: three tools registered (only when `plex_laptop_client is not None` — same gating discipline as M21 to avoid promising tools that aren't there); new "Remote Plex laptop" section in the system prompt advertising all three with an explicit "for THIS PC use `pc_diagnostics`, for the Plex laptop use `plex_laptop_health`" routing rule + a hard "READ-ONLY, can diagnose but not act" guardrail; static `_PLEX_LAPTOP_DISPATCH` table threaded through `_execute_client_tool`. Telemetry: `plex_laptop_tools=tool1,tool2` joins the existing markers.
- `main.py`: `_try_connect_plex_laptop(cfg)` runs alongside the M21 `_try_connect_plex` — graceful: missing host/user / bad key path / paramiko import fail all log + return None. On shutdown (after `worker.join`), `plex_laptop_client.close()` cleanly tears down the SSH channel.
- `src/config.py`: four new fields — `plex_laptop_host`, `plex_laptop_user`, `plex_laptop_key_path` (blank → `~/.ssh/id_ed25519`), `plex_laptop_log_path` (blank → default `C:\Users\<user>\AppData\Local\Plex Media Server\Logs\Plex Media Server.log`). `.env.example` documents all four with comments explaining the optional defaults.
- `requirements.txt`: `paramiko>=3.4` (pulls `bcrypt`, `pynacl`, `invoke`; `cryptography` was already a transitive dep via anthropic).
- **Voice-tested end-to-end with real telemetry** — 6 queries, every routing correct including the local-vs-remote control test:
  - *"How's the Plex laptop doing?"* → `plex_laptop_health` (overview), Jarvis: *"All looking healthy. CPU is barely breaking a sweat at 5%, RAM is comfortable at 39%, and there's 250 gigs free on the drive. It's been up just over 23 hours without issue."*
  - *"Any errors in the Plex logs today?"* → `plex_logs_search`, Jarvis correctly triaged: UltraBlurProcessor color-palette failures (cosmetic), EventSourceClient relay-retry drops (worth flagging but not critical), no transcoder failures.
  - *"What's Plex up to right now?"* → `plex_logs_tail`, surfaced an actual remote client browsing the movie library at 1:57 PM with sub-65ms response times — emergent ops insight from the log tail without any dashboards.
  - *"How much disk space on the Plex laptop?"* → `plex_laptop_health` (disk), reported all 4 drives including the 32.7 TB media drive at 74% (8.7 TB free).
  - *"How's my PC doing?"* → `pc_diagnostics` (control test — correctly routed to LOCAL not remote despite the prior 4 turns being about the remote box).
  - *"What's taking up so much RAM?"* → `pc_diagnostics` (memory), follow-up that kept context across the boundary between remote and local queries.
- Cache built up cleanly: `cache_read=13215` on first turn → `27650` by the sixth, with the new ~600-token system-prompt addendum + 3 tool schemas slotted into the prefix cache after the first turn. Memory sealed on shutdown with a coherent multi-topic summary spanning Plex laptop diagnostics, log triage findings, disk-space check, and PC RAM follow-up.

## Milestone 25 — console quality-of-life: mute toggle + SRE telemetry surfacing

- **Mute toggle (text-only mode).** Tray menu's "Mute (text only)" checkbox bypasses TTS playback while keeping voice input + console transcript fully working — the primary use case is quiet hours, where audible replies aren't wanted but the assistant should stay usable. State lives on `JarvisUI.mute_event` (a `threading.Event` mirroring the existing `shutdown` event); pystray's `checked=lambda` re-evaluates each menu open so the checkmark stays in sync. Console shows a passive `muted` indicator next to the state pill — read-only on that side, since duplicating the toggle would mean syncing two surfaces. **Captured at the start of `process_question`** so a mid-response toggle doesn't cut off in-flight speech (jarring); the change applies to the next turn. **Not persisted across restarts** — restart = clean slate, one tray-click is cheap.
- **SRE-grade status footer + per-turn telemetry chip.** The existing `[llm] tokens: input=… output=… cache_read=… tools_used=…` stderr line was always written but lived only in `jarvis.log` — invisible during a session. Now exposed visually:
  - **Bottom status bar in the console**: `sonnet-4-6  ·  up 1h 23m  ·  3,421 tok  ·  plex ●  ·  laptop ●`. Filled circle = enabled, hollow = not. Uptime ticks every 60s via a recursive `.after()`; token counter increments after each turn; integration dots set once at startup based on `plex_client is not None` / `plex_laptop_client is not None` (lazy-connect status doesn't change the dot — configured-but-not-yet-reached still shows ●). Single dim line, monospace 9pt, packed at the absolute bottom of the window via the standard "first `side='bottom'` wins" Tk packing trick.
  - **Per-turn telemetry chip**: a small dim line appended under each Jarvis response showing `tools · iters · seconds · tokens`. Format optimized for SRE skim-readability: which tools fired (the verb), then iteration count *if >1* (omitted when 1, to reduce noise), then how long the LLM+tools took, then the token cost. Multi-tool turns join with comma: `web_search, web_fetch · 4.1s · 1,876 tok`. Indented to align under the `[HH:MM] jarvis:` prefix so it reads as metadata-about-the-response rather than a new entry.
- `src/llm.py`: new `TelemetryRecord` dataclass (elapsed_sec, iterations, input/output/cache tokens, tools_used, paused) + optional `on_complete: Callable[[TelemetryRecord], None]` parameter on `stream_response`. The existing stderr line stays (logs are still useful for offline debugging); the callback is purely additive. Backward-compatible — existing callers who don't pass `on_complete` continue working unchanged.
- **Architectural decision: latency excludes TTS playback time.** `elapsed_sec` is wall-clock LLM-and-tools time only, measured from the top of `stream_response` to the end of the agentic loop. Including TTS would conflate "Jarvis's compute time" with "how much text Claude wrote" — for an SRE skimming "did this turn take longer than usual?", the former is the meaningful number. Recorded so the choice isn't second-guessed later.
- **Defensive contract maintained**: the `on_complete` callback is wrapped in try/except so a UI bug can't poison the listen loop. Voice / text / muted modes all surface the chip identically — `on_complete` fires regardless of TTS path, since telemetry visibility shouldn't depend on whether audio played.
- `src/console.py` adds a public thread-safe API: `set_model_name()`, `set_integration(name, enabled)`, `add_session_tokens(n)`, `add_telemetry_chip(text)`, `set_muted(bool)` — all marshal to Tk's thread via `.after()`. Same pattern as the existing `set_state` / `add_user_text` / `set_amplitude`. `src/ui.py` gains pass-through helpers; `src/tray.py` gains the `mute_enabled` / `on_mute_toggle` constructor params alongside the existing autostart equivalents.
- Tested live across all three input modes (voice, text, muted): chip appears uniformly, status bar dots reflect actual integration availability, token counter accumulates correctly across turns, mute checkbox state syncs the console indicator, mid-response mute toggle correctly defers to the next turn instead of cutting off speech.

## Milestone 26 — engineer mode + voice-safe markdown handling

- **Engineer-mode toggle (tray checkbox).** New "Engineer mode" item between "Mute (text only)" and "Start with Windows". When on, two things happen at once: (1) the system prompt gains `_ENGINEER_PROMPT_ADDENDUM` — longer structured replies allowed (paragraphs, bullets, ordered steps, code blocks), explain WHY not just WHAT, for diagnostics hypothesize + propose multiple approaches with trade-offs, with a calibration bullet that keeps depth proportional to question complexity (trivial questions stay brief even with engineer on); (2) `client.messages.stream` gets `thinking={"type": "enabled", "budget_tokens": 5000}` and `max_tokens` bumps 1024 → 8192 to fit reasoning + verbose reply. Extended thinking gives the model a ~5k-token reasoning budget before responding — meaningful for diagnostic questions where the first instinct often misses something obvious.
- State lives on `JarvisUI.engineer_event` (mirroring `mute_event`); the console shows a passive `engineer` indicator next to the state pill (read-only — the toggle stays on the tray to avoid syncing two surfaces). State captured per-turn at the start of `process_question` — a mid-stream toggle applies to the *next* turn (the thinking budget can't change mid-API-call).
- **Architectural decision: engineer + mute are orthogonal toggles.** All four combinations are real: voice + engineer = dictating a deep-dive while away from the screen; muted + engineer = quiet SRE pair-programming; voice + casual = the current default; muted + casual = quiet-hours casual queries. Coupling them would remove degrees of freedom for no benefit.
- **TelemetryRecord gains `thinking_enabled`** + the per-turn chip shows `thinking` when on. Engineer-mode turns visibly cost more — the marker calls that out so the trade-off is visible in real time.
- **Voice-safe markdown handling — `_strip_markdown_for_tts` in `src/text_to_speech.py`.** Engineer-mode responses use `**bold**`, bullets, headers — great on screen, terrible for edge-tts which reads the literal asterisks aloud ("asterisk asterisk memcompression asterisk asterisk"). The strip is applied at the sentence-emission point in `text_producer` (streaming path) and at the top of `speak()` (Tier-A path). The visual transcript keeps the original markdown — **only the audio path** goes through the filter.
- **Defensive orphan-asterisk sweep.** A real edge case caught in testing: the sentence-boundary regex (`[.!?]` followed by whitespace, or newlines) splits inside a `**...**` span because `**1. ` looks like end-of-sentence. The pair-replace regex `\*\*(.+?)\*\*` can't fix the resulting half-spans (one half is `**1.`, the other is `full.**`). Added a final `re.sub(r"\*+", "", text)` sweep that strips any orphan asterisks left after pair replacement. In voice context, isolated asterisks are virtually never legitimate — the sweep is safe.
- **What we deliberately do NOT strip**: single underscores (`MAX_TOKENS` would become `MAXTOKENS` — breaks identifiers); mid-line `#` (hashtags, channel refs, issue numbers like `#engineering`). Only paired `__bold__` and line-start `#` headers get stripped. Conservative, to preserve code-shaped content.
- **Empty-content guard** in `text_producer`: sentences with no alphanumeric content (horizontal rules `---`, isolated punctuation left after stripping) are dropped before reaching edge-tts. edge-tts rejects them with `No audio was received` and they carry no audible content anyway — this was producing log noise during the SSD-diagnosis test, where the model wrote a `---` divider into the reply. One-line `if sentence and any(c.isalnum() for c in sentence)` check.
- **Tested live with real telemetry — the marker is doing real work**: an engineer-mode turn on *"Why is my SSD slow?"* → 29.1s elapsed, 1043 output tokens, diagnostics tool fired through 2 iters, response had numbered sections with hypotheses for capacity / RAM pressure / SLC cache saturation / thermal / wear, plus a prioritized recommendations list. The same question with engineer mode off → 3.2s, 65 output tokens, brief recap. ~16× the depth, ~9× the latency, on demand.

- `src/plex_actions.py` (`PLEX_ACTION_TOOL` + `execute_plex_action`): a single tool with three actions — `restart_plex_server`, `refresh_library`, `empty_trash` — all confirmation-gated with the M23 `confirmed=true` server-side enforcement pattern. Builds on M24's SSH transport + `_ps_encoded` PowerShell shipping. Refresh and empty_trash hit Plex's local HTTP API at `localhost:32400` from the laptop side; restart probes for a wrapper service first and falls back to process kill + relaunch.
- **Architectural decision: single tool with an action enum, not three separate tools.** Same risk profile (destructive, confirmation-gated), same dispatch path, one enum entry per future action vs. three new files.
- **Server-side `confirmed=true` gate** mirrors M23's `kill_process` — the tool itself rejects calls without confirmation, so a misbehaving prompt or hallucinated tool call cannot bypass explicit consent. The confirmation message includes the action name and library_id when applicable so Claude can relay it accurately.
- **Plex token shipped inside the encoded PowerShell command, not via env on the laptop.** The token lives in the encoded payload during transit (SSH-encrypted in flight, base64 obfuscated through the cmd.exe → powershell.exe handoff) and exists transiently in PowerShell's process memory during execution. Same trust boundary as Plex itself storing the token in its data folder. No laptop-side setup step required.
- **Shared API-probe verification on restart.** Both the service-restart path (Restart-Service via wrapper) and the process-relaunch path (`cmd /c start`) need the same honest "is Plex actually serving?" check — service-running ≠ port-32400-responding (Plex needs a few seconds AFTER the service reports Running to bind the port). A common probe with 6 retries × 2s against `localhost:32400/identity` covers both modes; status codes flow back to Python, which translates them to user-facing prose via `_format_restart_status`.
- **Three iterative bugs caught and fixed during live testing — each worth recording**:
  1. **The initial restart "succeeded" but Plex was actually dead.** The original verification only checked `Get-Process` (process exists). A Plex tray-app launched from Session 0 (the SSH context) creates a PID but cannot fully initialize without an interactive desktop. Fix: added the HTTP API probe so verification matches expectations (Plex is *serving*, not just *running*).
  2. **The encoded PowerShell command exceeded Windows' 8191-char cmd.exe limit.** Verbose multi-sentence error messages with workaround guidance bloated the script past the encoded ceiling once base64-of-UTF-16-LE expanded it (~2.67×). Fix: PowerShell emits short status codes (`OK_service:0`, `FAIL_PROCESS_DEAD`, etc.); Python translates them to prose via `_format_restart_status`. Headroom went from ~zero to ~4kB.
  3. **The service name was hardcoded `'Plex Media Server'` but cjmurph/PmsService registers as `PlexService`.** Our probe always returned null after PlexService was installed, so we always fell down the process-launch path and spawned an orphan Plex.exe that fought with PlexService for control of the same process — Plex crash-looped. Fix: probe a list of known wrapper service names (`PlexService`, `Plex Media Server`, `PlexMediaServerService`, `PmsService`) instead of hardcoding one. The broader gotcha (the run-as account must own Plex's data folder; installing the wrapper does NOT require a Plex reinstall; two separate Plex services exist on Windows) is recorded as a standing runbook note.
- System prompt addendum updated: M24's "These are READ-ONLY" line removed; a new "Actions (destructive, all confirmation-gated)" section instructs Claude to confirm in plain language first, wait for explicit consent, then call with `confirmed=true`. Same rule shape as M23's kill_process. Retained the "if asked for an action we don't support yet (rotate logs, restart the laptop itself, clear OS-level caches), say so plainly" guardrail — and verified it fired correctly during testing on *"Restart the Plex laptop itself"*.
- Tested live across the full confirmation flow: `refresh_library` + `empty_trash` worked on first try via the Plex API; `restart_plex_server` required all three iterative fixes above before producing a clean *"Plex service restarted, API responding on localhost:32400."* Final state: PlexService running as the local account that owns the data folder, Plex serving healthy on a clean restart, telemetry chip shows `plex_action · X.Xs · Y tok`. The voice confirmation flow held up — a spoken *"yes"* triggers the `confirmed=true` call; the system prompt's tooling rules and the server-side gate worked together as designed.

## Milestone 28 — read_local_file + deep-diagnostics collector (Jarvis reads files, and drives the diagnostics bundle)

- `src/file_reader.py` (`READ_LOCAL_FILE_TOOL`, `execute_read_local_file`): a read-only "read me that file" tool. Takes a path (absolute or `~`-relative; `/` and `\` both fine on Windows), returns the text with a `[<path>] — N bytes` header. Use cases: ad-hoc config/log inspection (*"check my docker-compose for issues"*, *"what's in my .ssh/config"*) and reading individual files out of a diagnostics bundle (the other half of this milestone). Same defensive contract as the rest of the toolkit — never raises, always returns a readable string.
- **No confirmation gate on read_local_file** — the M23 philosophy says gates are for *destructive* (kill_process) and *expensive* (the collector) operations. The path is named in the request; reading is low-impact. Friction here would annoy with no security payoff.
- **Text-only.** A NUL byte in the first 8 KB → treated as binary, refused with the file's size. The standard "is it text" heuristic (git uses it too). Voice/LLM context has no use for raw bytes.
- **64 KB front-truncation.** Returns the first 64 KB of decoded text with a `[...truncated — N more bytes not shown]` note. Truncating from the *front* is the right call here: the one big file category is event-log dumps (`events/system.txt` ran 252 KB in testing), and `Get-WinEvent` emits newest-first, so the front is the recent stuff. ~16k tokens worst case — already plenty for voice.
- **Credential-material denylist (narrow, by filename).** Refuses private keys (`id_rsa`, `id_ed25519`, …), keystores (`.pem`, `.key`, `.pfx`, `.p12`, `.kdbx`, `.jks`, `.ppk`, `.gpg`, `.asc`), `.htpasswd`, and the Windows registry hives (`SAM`, `SECURITY`, `SYSTEM`, `NTUSER.DAT`) — regardless of location. `.pub` overrides a denied stem (`id_ed25519.pub` is a *public* key → allowed). This is defense in depth: a hallucinated or misguided tool call can't slurp key material into the conversation transcript. It is deliberately NARROW — `.env`, `.ssh/config`, dockerfiles, logs are all allowed (this is a machine the operator controls; a `.env` read leaks nothing new to the API that the request's own API key doesn't, and blocking it would break legitimate *"read my .env to check the format"* requests).
- **`utf-8-sig` decode** strips a leading BOM — many Windows tools (including the diagnostics collector itself) save UTF-8 with one, and a stray U+FEFF at the start of the tool result is just noise. `errors='replace'` keeps us safe on any odd bytes after that.
- **Every read logged to stderr → jarvis.log** with the resolved path + size + truncation flag — an audit trail for "what files has Jarvis looked at".
- `src/diagnostics_collector.py` (`RUN_PC_DIAGNOSTICS_COLLECTOR_TOOL`, `execute_run_pc_diagnostics_collector`): runs a companion Windows diagnostics-bundle repo's script, `~/repos/hs-windows-diagnostics/Invoke-HSWindowsDiagnostics.ps1` (a PowerShell collector that gathers host / security / package / event-log telemetry into a `.tar.gz` of ~47 small text files), extracts the archive, and returns the extracted bundle's root + a listing of relative file paths so Claude can then `read_local_file` the specific ones relevant to the question. Two modes via the `quick` param: `quick=true` (default) → `-Quick -MaxEvents 500`, ~60-100s, right for ad-hoc troubleshooting; `quick=false` → full collection, `-MaxEvents 2000`, a few minutes, right for a support-ticket bundle.
- **Confirmation-gated** (the M23 `kill_process` pattern, enforced *in the tool*, not just the system prompt): the bundle isn't destructive but it writes ~MB to disk and takes a minute-plus — the first call without `confirmed=true` returns a "needs confirmation" string Claude paraphrases (*"Confirm: run a full diagnostics collection? It takes about a minute."*); only after explicit agreement does Claude call again with `confirmed=true`. Validated live: *"Run a deep diagnostic snapshot of this PC"* → Claude asked, no tool call; *"Yes, go ahead — quick mode is fine"* → `confirmed=true`, 102s collection, 47 files extracted, then a 4-iteration agentic chain of `read_local_file` calls (systeminfo, memory_summary, cpu, volumes, events/system, defender_status, bitlocker_status, processes_top_memory, secure_boot — 9 files) → a thorough, accurate report that flagged Defender disabled, two ghost services (HP Comm Recovery / WildTangentHelper), a recurring Secure Boot SBAT update failure, and TCP/UDP port-exhaustion warnings. Telemetry chip: `read_local_file, run_pc_diagnostics_collector · 5 iters · 131.1s · 93,072 tok`.
- **Architectural decision: no startup wiring.** Unlike the M21 Plex MCP and M24 SSH clients (which need a startup connection + graceful-fail logic in `main.py`), these two tools just shell out / read a file when invoked — like M23's `pc_diagnostics` Get-WinEvent call. Both are registered unconditionally; the collector self-reports (*"Diagnostics collector script not found at <path>…"*) if the script isn't installed, with the system-prompt addendum advertised always. No `main.py` changes, no new deps (`tarfile`, `zipfile`, `subprocess`, `shutil`, `pathlib` are all stdlib).
- **Config: `DIAGNOSTICS_COLLECTOR_PATH` read at call time via `os.getenv`, not threaded through `Config`** — same asymmetry as M22's `RAWG_API_KEY`. It's consumed only inside `diagnostics_collector.py`; reading at call time keeps it hot-swappable in dev, and the `Config` dataclass is `frozen=True` anyway. Default: `~/repos/hs-windows-diagnostics/Invoke-HSWindowsDiagnostics.ps1` (the project convention of "code in ~/repos/<name>"). `.env.example` documents it as optional.
- **Output owned by Jarvis, not the script's default.** The collector is invoked with `-OutDir <%LOCALAPPDATA%\Jarvis\diagnostics>` (alongside the log + memory store, not the script's own default output dir), so Jarvis owns the lifecycle: extract the `.tar.gz` (Python `tarfile`, `filter='data'` to neutralize path-traversal entries even though the archive is self-produced), keep the archive, and prune to the 3 most-recent bundles + extracted dirs before each new run. Also invoked with `-NoSplit` (always one archive — never reassemble parts) and `-NoUnicode` (ASCII progress UI → clean captured stdout).
- **The PATH/tar gotcha (caught in testing, hardened against).** The collector script shells out to `tar` for `.tar.gz` packaging. When the *test* was run from a Git Bash shell, `tar` resolved to MSYS2's GNU tar (`/usr/bin/tar`) ahead of Windows' bsdtar (`C:\Windows\System32\tar.exe`) on PATH — and GNU tar mangles Windows-style absolute paths (`C:\…\foo.tar.gz`) → exit code 2 → "No output files were produced" → the wrapper correctly surfaced the error. Not a real bug (Jarvis launched normally has the system PATH and uses bsdtar — proven by a direct invocation), but Jarvis *could* be launched from a Git Bash terminal, so `_subprocess_env()` now pushes `%SystemRoot%\System32` to the FRONT of PATH for the collector subprocess. Belt-and-suspenders for ~6 LOC.
- **Stale-bundle guard.** The wrapper snapshots the set of `.tar.gz`/`.zip` files in the output dir *before* running, and after a clean exit picks the newest archive *not in that set* — so a script that somehow succeeds without writing a new archive can't make the wrapper extract a leftover from a prior run.
- **`.zip` fallback handled.** If the script can't find `tar.exe` it falls back to `Compress-Archive` → `.zip`; the wrapper globs for both and extracts with `zipfile` or `tarfile` accordingly.
- `src/llm.py` plumbing: both tools registered alongside the existing seven (`tools=[…, PC_DIAGNOSTICS_TOOL, SYSTEM_CONTROL_TOOL, READ_LOCAL_FILE_TOOL, RUN_PC_DIAGNOSTICS_COLLECTOR_TOOL]`); dispatch lines in `_execute_client_tool`; the "Local PC control" system-prompt section expanded from two tools to four (6 `pc_diagnostics` = live, 7 `system_control`, 8 `read_local_file`, 9 `run_pc_diagnostics_collector` = deep), with explicit "live vs deep" routing (*"for a quick 'any errors lately?' the live tool is enough — don't kick off a minute-long collection unless the depth or a ticket bundle is actually wanted"*) and the collector folded into the confirmation-gate rule next to `kill_process`. Telemetry: `read_file=yes` and `diag_collector=yes` join the markers; `read_local_file` / `run_pc_diagnostics_collector` join the per-turn chip's tools list.
- **read_local_file voice-tested end-to-end** independently of the collector: *"Read ~/repos/jarvis/requirements.txt and tell me roughly what dependencies it pulls in"* → `read_file=yes iters=2`, Claude categorized them accurately (AI layer / speech pipeline / audio I/O / UI / integrations); *"check ~/repos/jarvis/.gitignore — does it ignore the .env file?"* → *"Yes — `.env` is explicitly the first entry, right under the 'Secrets' comment."* Paths used for tool calls, never read aloud — the voice-format rules held.
- **Known consideration (recorded, not changed):** the collector→read-files workflow can run `iters` up to the `_MAX_LOOP_ITERATIONS=5` cap (the live test hit exactly 5 and finished cleanly — collector call + 4 iterations of batched `read_local_file`s). 5 was *enough*; if a future "analyze the whole bundle" request gets truncated, bump the cap then. The follow-up-question path is cheap regardless — the bundle stays on disk and a later *"any errors in the event log?"* reuses it with `iters=1`, no re-run.
- Relationship to M23's `pc_diagnostics`: both kept, deliberately. `pc_diagnostics` = "what's happening RIGHT NOW" (live psutil/PowerShell, sub-second, no disk artifacts). `run_pc_diagnostics_collector` = "deep snapshot, archive, follow-up analysis" (writes a browsable bundle, minute-plus). Different questions — the same split philosophy as M23's read-only `pc_diagnostics` vs allowlisted `system_control`.

## Milestone 29 — Jarvis can see (webcam vision via Claude's multimodal input)

- `src/cameras.py` (`CAMERA_SNAPSHOT_TOOL`, `execute_camera_snapshot`): grabs a single still frame from a USB/UVC webcam (a Logitech C920e — already attached, since it doubles as Jarvis's microphone) and returns it as a Messages-API **image content block** + a one-line caption. Because Claude is multimodal, the tool *result* is the image itself — Claude sees it and answers in voice. Unlocks the whole class of *"what do you see / is X there / did Y happen"* queries. No params for v1 (one camera); the schema can grow a `camera` param backward-compatibly when IP/RTSP cameras get added.
- **Why a USB webcam, not a cloud doorbell camera (the path not taken):** that ecosystem is a closed cloud — no API, no RTSP, no ONVIF. The only route is a reverse-engineered client library, which the vendor breaks periodically; the design call was to skip it (if it breaks often, it isn't worth carrying). A USB webcam needs none of that — local device, no cloud, no creds, and on a UVC cam the audio and video are separate device interfaces, so `sounddevice` holding the mic and `cv2` opening the video coexist fine (verified). Revisit later via a `ring-mqtt`-style → RTSP bridge if ever wanted.
- **Backend: OpenCV DirectShow.** `cv2.VideoCapture(index, cv2.CAP_DSHOW)`. The Media Foundation backend (`CAP_MSMF`, cv2's Windows default) fails to open the C920e on this box; DirectShow opens it cleanly. `opencv-python-headless>=4.8` (~60 MB, no GUI/Qt bits we don't need; also forward-compatible — `cv2.VideoCapture("rtsp://…")` is the same API if IP cameras get added).
- **Open-on-demand, never persistent.** We could keep `VideoCapture` open for instant snapshots, but that lights the camera's in-use LED the whole time Jarvis runs and blocks other apps (video calls) — wrong for a privacy-sensitive feature. Open → grab → release. Cost: ~3-4s total (DirectShow's open is the bulk; the capture itself is sub-second), comparable to a cloud snapshot or the diagnostics collector — fine for an on-demand "what do you see?".
- **Warm-up frames.** A USB webcam returns dark/stale frames before auto-exposure settles — `execute_camera_snapshot` reads `_WARMUP_FRAMES=6` and keeps the last. Captures at 1280×720, JPEG quality 80 (~140 KB; well within the vision API's image sweet spot — no benefit past ~1568px long edge). Black-frame guard (`mean pixel value < 8`) → returns a readable string ("the privacy shutter is probably closed") rather than handing Claude a black rectangle.
- **Lazy `cv2` import** inside the executor (not at module top): a ~60 MB dep that, if the install ever breaks, degrades to a readable error string ("Camera support isn't installed…") instead of breaking `llm.py`'s import chain and preventing Jarvis from starting. Same pattern as `system_control.py`'s lazy `pycaw` import. Defensive contract maintained throughout — camera busy / not found / black frame / cv2 missing all become a string Claude relays apologetically; never raises.
- **`llm.py` changes:** `_ClientTool.execute` widened from `Callable[[dict], str]` to `Callable[[dict], str | list[dict]]` (and `_execute_client_tool`'s return type likewise) — the agentic loop already passes list-valued `tool_result` content through (it does for the M16 file attachments; the API accepts image blocks in `tool_result.content`), so no loop change, just the type. Registered as `"camera_snapshot": _ClientTool(execute_camera_snapshot, "camera")` in the M28 registry; `CAMERA_SNAPSHOT_TOOL` added to the `tools=[...]` inventory; new "Vision" section in the system prompt (tool #10) nudging Claude to describe what it sees conversationally ("like glancing over and remarking on it, not narrating a photo") and not announce that it's taking a picture. Telemetry: `camera=yes` marker + `camera_snapshot` in the chip's tools list — both come free from the registry.
- **Reuse:** `attachments.py` gained an `image_block(data: bytes, media_type)` helper (and `image_block_from_b64`); `load_attachment`'s image branch was refactored onto it, and `cameras.py` uses it — the webcam-frame-bytes → content-block path and the file → content-block path now share one place.
- **`requirements.txt`:** `opencv-python-headless>=4.8`. `.env.example`: optional `CAMERA_INDEX` (default 0; only needed when several cameras are present).
- **Voice-tested end-to-end:** *"Jarvis, take a look through the webcam and tell me what you see"* → `camera=yes iters=2`, 12.9s (~4s capture + ~9s for Claude to process the ~1500-image-token frame and stream the reply). The reply described the scene accurately (the person at the desk, clothing, the shelving and furniture behind them), persona intact, no paths/IDs read aloud. A follow-up *"What am I wearing?"* → answered from the image still in history (`iters=1`, no re-capture) — multi-turn vision works.
- **Known: latency.** ~12-13s for the first vision turn (DirectShow open + image-token processing). Acceptable for a deliberate "what do you see?" ask; not snappy. Dropping to 640×480 (~40 KB, ~400 tokens) would shave a few seconds but hurts detail for "is the package on the porch" — kept 720p. (Out of scope for v1, on the wishlist: a console thumbnail of the snapshot, multiple/RTSP cameras, screen vision, proactive motion-triggered announcements.)

## Milestone 30 — Jarvis sees the screen (the SRE amplifier)

- `src/screen.py` (`SCREEN_SNAPSHOT_TOOL`, `execute_screen_snapshot`): captures the primary monitor via `PIL.ImageGrab.grab()`, downscales to ≤1568 px long edge with LANCZOS, encodes as PNG, and returns a Messages-API **image content block** + caption — the same plumbing M29 built for `camera_snapshot`. The SRE companion to the webcam: *"Jarvis, what's on my screen?"* / *"what does this error mean?"* / *"explain this stack trace"* — Claude reads the screen and answers in voice. The CLAUDE.md "front-runner" that landed *first* post-M29 (cheaper, higher daily-use leverage than `pc_shell`).
- **Why this was almost free.** The post-M29 list explicitly tagged screen vision as the cheapest cheap follow-up (*"~an afternoon, big for the SRE use case; could reuse the M29 image-block plumbing wholesale"*) — that prediction held literally. Zero new dependencies (Pillow was already in `requirements.txt` for pystray's tray-icon rendering), zero new infrastructure (M29 had already widened `_ClientTool.execute` to return `str | list[dict]` and proved the agentic-loop image-block path), and the `attachments.image_block()` helper M29 extracted is reused as-is.
- **PNG, not JPEG (different from cameras.py on purpose).** Webcam frames are photographic — JPEG q80 (~140 KB) is the right call. Screen frames are typographic — JPEG's chroma subsampling blurs small terminal text noticeably even at q90, so PNG (lossless) is the right call here. The file-size cost is modest (~250-500 KB at 1568 px long edge for typical desktop content) and well under the API's 5 MB inline cap.
- **Primary monitor only for v1.** `PIL.ImageGrab.grab()` defaults to the primary monitor; `all_screens=True` stitches the entire virtual desktop into one wide image, but on the 3440×1440 ultrawide used here a multi-monitor stitch would push past 6000 px wide and get aggressively downscaled server-side (text becomes unreadable). Forward-compatible: a `monitor` param can be added later without breaking callers, the same shape as the wishlisted `camera` slot on `camera_snapshot`.
- **Resize to ≤1568 px long edge locally** (the vision API's sweet spot — the server downscales past this anyway). Doing it locally with LANCZOS gives a slightly higher-quality result than the server's resampler at no extra cost. The 3440×1440 ultrawide downscales to 1568×656 at this cap — short on the vertical, but text remains legible.
- **Defensive contract preserved.** Black-frame guard (probe a 64×64 grayscale downsample, mean < 8) catches locked-workstation captures that come back as a uniform black rectangle rather than failing outright. Pillow missing / capture failure / black-frame all become readable strings ("the workstation is probably locked or the display is off") — never raises, same shape as cameras.py.
- **`llm.py` changes (trivial — the M29 dividend):** one import line, one `_CLIENT_TOOLS` entry (`"screen_snapshot": _ClientTool(execute_screen_snapshot, "screen")`), one addition to the `tools=[…]` inventory, one new paragraph in the system prompt's Vision section (now two tools — #10 `camera_snapshot` for the physical world, #11 `screen_snapshot` for the digital world, with explicit guidance to pick the right one). Telemetry: `screen=yes` marker + `screen_snapshot` in the chip — both come free from the registry.
- **Voice/text-tested end-to-end across four prompts:**
  - *"What's on my screen?"* → `screen=yes iters=2`, 8.7 s, accurate description of the dev session (code editor, task list, terminal logs) — including Jarvis recognising **his own UI window** in the frame ("right in the middle of it all, my own UI window showing me actively thinking through your question. Very meta.").
  - *"What does this error mean?"* (a PowerShell trace visible on screen) → `screen=yes iters=2`, 6.3 s — read the error literally, diagnosed the cause, suggested `ls \repos` as the next step. The SRE use case landing exactly as designed.
  - *"What do you see?"* (deliberately ambiguous) → `camera=yes iters=2` — Claude correctly routed to `camera_snapshot` (physical world) rather than `screen_snapshot`. The "two tools, pick the right one" system-prompt distinction held.
  - *"What's the color of the window header?"* (a follow-up after a camera turn) → re-captured rather than reusing the prior screen frame (`screen=yes iters=2`). Correct behaviour: the most recent image in conversation history was the camera frame from the previous turn, so a fresh capture was the right call, not a bug.

## Milestone 31 — Inline thumbnails of what Jarvis saw (transcript-side vision)

- **What ships:** when `camera_snapshot` or `screen_snapshot` succeeds, a downscaled thumbnail of the captured image appears inline in the console transcript with a labeled header (webcam snapshot / screen snapshot), right between the question and Jarvis's spoken reply. The transcript now shows *what Jarvis actually saw* — not just the spoken description. Closes the M29-wishlist "console thumbnail" follow-up.
- **`src/console.py`:** new public `add_image_thumbnail(image_bytes, label)` (thread-safe via `root.after`). Internal `_append_image_thumbnail` decodes with PIL, downscales to 240 px wide (height preserves source aspect ratio — 240×135 for a 720p webcam frame, 240×100 for the ultrawide screen), wraps it in a `PIL.ImageTk.PhotoImage`, and inserts it into the underlying `tk.Text` via `image_create`. Refs are held in `self._thumbnail_refs` because Tk weakly-references images and would silently garbage-collect them mid-session otherwise.
- **`PIL.ImageTk.PhotoImage` (not `CTkImage`).** `CTkImage` is purpose-built for CTk widgets (CTkLabel, CTkButton) — it doesn't embed cleanly via `tk.Text.image_create`. `ImageTk.PhotoImage` is the standard tk.Text-embed type and what the underlying widget actually wants. CTk's HiDPI scaling isn't needed for ~240px transcript thumbnails on a typical desktop.
- **`src/llm.py` callback plumbing:** new optional `on_image_captured: Callable[[bytes, str, str], None]` param on `stream_response`. The agentic loop already runs every tool result through a uniform path; after `_execute_client_tool` returns, if the result is a list containing an image content block, the loop base64-decodes the data and fires the callback with `(image_bytes, media_type, tool_name)`. **Tool-agnostic by design** — any future tool that returns an image (Plex artwork, OCR captures, etc.) gets thumbnailed for free with zero further changes. Defensive `try/except` wrapper so a UI bug never breaks the mid-turn agentic loop.
- **`src/ui.py` + `main.py`:** pass-through on `JarvisUI`; `main.py` defines an `on_image_captured` closure that maps tool name → friendly label and calls `ui.add_image_thumbnail`. Same shape as the existing `on_telemetry` callback, and sits right next to it.
- **Timing is naturally correct.** Tool fires → thumbnail inserted (mid-stream, on Tk's main thread queue) → Claude's text response streams in → `ui.add_jarvis_text(full_response)` appends below. Sequential `tk.Text.insert("end", ...)` preserves insertion order; the thumbnail lands between the user message and Jarvis's reply with no extra synchronization. No race, because all UI inserts are marshaled onto Tk's thread via `root.after(0, …)`.
- **Voice-tested end-to-end across three prompts** (~5 min session):
  - *"What's on my screen?"* → screen thumbnail rendered inline + accurate verbal description (Jarvis again recognised his own UI window in the frame — the second time the meta-recursion has shown up in vision testing).
  - *"Just take a look through the webcam."* → webcam thumbnail rendered + an accurate scene description of the room in frame.

Defensive contract holds end-to-end.

The realistic "taskbar shortcut" is therefore a discoverable `.lnk` plus a UX hint. - **Flag-and-defer relaunch (M32's only non-obvious design call).** The "Restart" click runs on pystray's thread, but spawning the new process there would race the *still-running* listen_loop for the webcam's audio interface — which doesn't share politely (different from the Plex MCP subprocess, which tolerates overlapping ownership). ## Milestone 33 — pc_shell (read-only Windows investigative shell)

- **What ships:** `src/pc_shell.py` (≈430 lines) — a new client-side tool `pc_shell` that runs ONE Windows command from a strict 18-verb read-only allowlist on the local host. The natural M28 companion: read_local_file reads a specific *file*; pc_shell runs a specific *command*. Together they upgrade Claude from "report a static pc_diagnostics snapshot" to "investigate dynamically" — the SRE amplifier that's been on the wishlist since M28's planning pass.
- **Allowlist (18 verbs):** networking (ipconfig, Get-NetAdapter, Get-NetRoute, Get-NetTCPConnection, netstat, arp), connectivity (ping, tracert, Test-NetConnection, Resolve-DnsName, nslookup), host (Get-Process, Get-Service, Get-WinEvent, Get-CimInstance, systeminfo), files/updates (Get-ChildItem, Get-HotFix). Chosen for the "comprehensive SRE toolkit" scope per the design check-in — covers the network-debug classic chain (ping → tracert → Resolve-DnsName), service-state queries, and event-log triage without overlapping `read_local_file`.
- **Security posture — seven hard rules baked into the module docstring:**
  1. **No arbitrary command path.** `command` is an enum; dispatch is gated by `_HANDLERS.get(command)` returning a real handler. Hallucinated commands short-circuit before any process spawns.
  2. **No shell composition, ever.** Every `subprocess.run([list, of, args])` with implicit `shell=False`. No `os.system`, no `shell=True`, no f-string-into-shell-string. A caller-controlled hostname like `"example.com; whoami"` cannot reach a shell parser because there is no shell parser in this code path.
  3. **Strict per-verb input validation.** `_HOSTNAME_RE` (`^[A-Za-z0-9._%:-]+$`) refuses *every* shell metacharacter — semicolons, pipes, backticks, dollar signs, quotes, whitespace. `_PROCESS_NAME_RE` and `_LOG_NAME_RE` do the same for their domains. Ports are `int` + range-checked. CIM class names match a small allowlist (`Win32_OperatingSystem`, `Win32_LogicalDisk`, etc.) since the full WMI surface is a DoS vector. Paths get an apostrophe-refusal check before being inlined.
  4. **Read-only by design.** No verb mutates host state. `ipconfig` exposes `/all` and `/displaydns` but deliberately NOT `/flushdns`, `/release`, `/renew`, `/registerdns` — those belong in `system_control` if/when wanted, behind confirmation gates. Per the standing diagnostic-vs-action split: read tools and write tools stay separate.
  5. **Bounded.** 20s subprocess timeout via `subprocess.run(timeout=20)`; output truncated to 8 KB / 200 lines (whichever hits first) by `_truncate()`. A runaway `ping -t` or a `Get-WinEvent` that streams millions of records cannot blow up the context window or starve the agentic loop.
  6. **Audited.** Every invocation emits a `[pc_shell]` line to stderr (→ `jarvis.log`) with verb, argv, exit code, and output byte count, written from `_run()`'s `finally` block so even timeouts/exceptions leave a trace. `grep '[pc_shell]'` answers "what has Jarvis been running?" in one command.
  7. **Defensive contract.** Top-level `execute_pc_shell` wraps the dispatch in `try/except` and returns a readable string for any exception. The same shape as every other tool in `src/` — a tool bug never crashes the agentic loop mid-turn.
- **PowerShell argument-passing bug, caught + fixed in smoke testing.** The first pass used `powershell.exe -Command "<cmd>" -- target port` with `$args[0]`/`$args[1]` references inside the command string. **This doesn't work** — `-Command` doesn't bind trailing positional tokens to `$args`, so every PS handler returned `Cannot validate argument on parameter 'X'`. The fix is documented in a 14-line comment block above the handlers section: validate strictly first, then inline values into **single-quoted PS strings**. PowerShell single-quotes are literal (no `$` expansion, no operator parsing); the only escape sequence is `''` for a literal apostrophe — and `_HOSTNAME_RE` already forbids apostrophes. So validated values are provably inline-safe. Native exes (ping, tracert, etc.) keep argv-list passing through Windows' `CommandLineToArgvW`, which is the correct shape for them.
- **`Test-NetConnection` rewritten as a fast TcpClient probe.** Real-world measurement during smoke testing: the PS `Test-NetConnection` cmdlet takes ~30-40s per call on this host (multi-probe behavior: TCP + ICMP + reverse-DNS + sometimes route-trace, with no flag to disable the slow parts while keeping detailed output). Replaced the handler body with `System.Net.Sockets.TcpClient.ConnectAsync` + a 3s `.Wait(3000)` wall-clock for the port case, and the standalone `Test-Connection -Quiet` cmdlet (ICMP-only, fast) for the no-port case. Same tool name from Claude's perspective; new latency: TCP probe 1s, closed-port probe 4s, ICMP probe 2s. The replacement returns clean `TCP <host>:<port> - SUCCESS/FAILED` text — less rich than the cmdlet's full output, but the rich output was rarely worth the wait.
- **`tracert` worst-case bounded via `-w 1500`.** The default tracert hop-wait is 4000ms; max_hops=30 × 4s = 120s worst case (a fully blackholed trace) — way past the 20s subprocess timeout. With `-w 1500`, 30 × 1.5s = 45s theoretical max, and real fast-failing traces complete in 5-10s. Also pass `-d` to skip reverse DNS (faster, and less informative but fine for investigation).
- **`Get-WinEvent` via `-FilterHashtable`, not `-FilterXPath`.** FilterHashtable's keys are a closed enum (`LogName`, `Level`, `Id`, `StartTime`, etc.) and the cmdlet validates them — a far smaller attack surface than the XPath path, which is essentially arbitrary code in a different DSL. The log name flows through a single-quoted PS literal after `_LOG_NAME_RE` validation; level flows through an integer map (`{Error:2, Warning:3, ...}`).
- **`Get-CimInstance` constrained to 8 classes.** WMI is enormous and many classes are slow or huge (`Win32_PerfRawData_PerfOS_Processor` instances stream forever, etc.). The 8-class allowlist (`Win32_OperatingSystem`, `Win32_ComputerSystem`, `Win32_PhysicalMemory`, `Win32_LogicalDisk`, `Win32_Processor`, `Win32_NetworkAdapter`, `Win32_BIOS`, `Win32_VideoController`) covers the SRE-investigation classes Claude reaches for in practice. Adding a class = a one-line code change, not a prompt change.
- **`Get-ChildItem` apostrophe refusal.** Windows paths can legally contain apostrophes (rare in practice). Rather than implement the PS doubled-quote escape dance (`'` → `''` inside `'...'`), the handler refuses such paths with a clear error message. NTFS allows the character but few real installations have it; not worth the escape complexity.
- **System prompt updates in `src/llm.py`:** the "Local PC control (you have four tools — pick the right one)" header bumped to "five tools"; a new section 7 inserted between `pc_diagnostics` (static snapshot) and `system_control` (write actions), since semantically pc_shell sits at "dynamic read-only investigation" — the missing rung between static-look and active-write. The safety-rules paragraph updated to list `pc_shell` alongside `read_local_file` in the no-confirmation-needed bucket. Vision tools renumbered 10/11 → 11/12.
- **Telemetry registration:** added to `_CLIENT_TOOLS` with the `"shell"` short label (between `"diagnostics"` and `"sysctl"` — preserving the read→write ordering). The per-turn telemetry chip + stderr marker pick this up automatically thanks to the post-M28 registry refactor — zero per-tool plumbing.
- **Smoke-tested across the verb matrix:** unknown command → a clear error listing all 18 verbs; a shell-injection attempt (`ping target=example.com; whoami`) → rejected at validation with "contains characters I won't pass through" before any subprocess spawns; ping/tracert/netstat/arp/ipconfig/systeminfo/Get-Process/Get-Service/Get-NetAdapter/Get-NetTCPConnection/Get-ChildItem/Get-WinEvent/Get-CimInstance/Get-HotFix/Resolve-DnsName/nslookup all return valid output inside the 20s budget; Test-NetConnection-via-TcpClient handles SUCCESS / FAILED / ERROR / closed-port / ICMP-only cases cleanly. The CIM-class denylist correctly rejects an unknown class with a message listing the allowed ones.

## Milestone 34 — security mode foundation (announce-only, webcam watcher)

- **What ships:** the first of a four-milestone "proactive vision" arc. New `src/security.py` (~400 lines) with `SecurityWatcher` — a background thread that, while armed, polls the USB webcam every 2 seconds, runs YOLOv8n person detection on each frame via the `ultralytics` library, and fires a proactive spoken announcement when a person enters the scene. Voice intent parser handles `"activate security"` / `"stand down"` (and synonyms) LOCALLY without burning a Claude turn. New 🛡 ARMED red indicator in the console next to the mute/engineer pills; new tray-menu Security mode checkbox toggle. **Two scoped firsts for Jarvis:** (1) proactive speech — Jarvis can now speak without being asked, via the new `_announce` closure in main.py that drives `speak_streaming` with a single-chunk iterator (gets the waveform pulse + state flip for free); (2) pre-LLM intent parsing — transcripts can now be intercepted and handled locally before reaching `process_question`, the same pattern any future "Jarvis, forget that" command would reuse.
- **Four-milestone arc map.** M34 ships the foundation: arm/disarm, watcher thread, proactive speech, announce-only. M35 layers the voice-passphrase challenge + 15s deterrent timer + evidence snapshot. M36 adds facial recognition as a parallel auth path (`face_recognition`/dlib). M37 adds a cloud-camera integration as a second event source. M38 (optional) adds Discord-webhook real notification on top of the deterrent. Each milestone builds on M34's detection backbone; the arc can stop at any point and still leave working functionality.
- **YOLOv8n via ultralytics — model choice rationale.** Person detection on CPU. v8n is the nano variant (6 MB weights, fastest), trained on COCO so class index 0 = "person" stably. Measured on this Ryzen 5 3400G: 0.2s warm inference per 640×480 frame, ~100ms on lighter inputs. At the 0.5 Hz polling rate (one inference every 2s), that's <10% of one core during an armed session — comfortable headroom. Confidence threshold pinned at 0.5: low enough to catch partial views, high enough that the false-positive rate on pets / shadows / curtains is effectively zero. MIT-licensed. The `ultralytics` package pulls in torch CPU (~200 MB) and opencv-python as transitive deps; first inference auto-downloads `yolov8n.pt` to the project root (~6 MB) — gitignored as `*.pt`.
- **Presence-window debounce — the critical UX detail.** Without it, a person standing in the watcher's view would trigger an announcement every 2s polling cycle (comically bad). The watcher tracks `_person_present` as a single boolean: announce on the **transition** EMPTY → PERSON, then suppress further announcements while the same presence persists. After `_PRESENCE_CLEAR_SECONDS` (30s) of no detections, the presence window closes and the next detection counts as fresh. Tested live: walking into frame → one announcement, remaining in frame for 12s → zero further announcements. Standard intrusion-detection pattern.
- **5-second arm-grace period.** Arming security from the desk would instantly fire the watcher on the person who armed it. The 5s `_ARM_GRACE_SECONDS` window suppresses detections immediately after arming, giving time to step away. An intruder can't exploit this — they'd have to arm Jarvis first, which requires being inside and speaking to it. Classic burglar-alarm UX.
- **Lazy YOLO load, cached across arm cycles.** Importing `ultralytics` + `torch` is ~200 MB into memory. Doing it at module-import-time would balloon Jarvis's baseline RSS for every install, including ones that never arm security. So the import happens inside `_watch_loop` on first iteration; subsequent arms reuse the loaded model (`self._model` is the cache). First-ever arm takes ~9s wall clock (model download + load); same session, subsequent arms instant. Cold-disk arm on a fresh clone takes ~9s; cold-disk-but-cached arm is ~0.2s.
- **YOLO failure auto-disarms with announcement.** Defensive contract for the model load path: if `from ultralytics import YOLO` fails (broken install) or `YOLO("yolov8n.pt")` throws (disk full, network down for download, corrupted weights), the watcher announces the failure verbally — *"Security model failed to load, sir. Check the logs."* — and clears the armed state. Nobody is ever left thinking they're protected when they aren't. A `_model_load_failed` sentinel prevents retry storms within a single session — fixing requires a Jarvis restart.
- **Voice-intent parser, regex-loose by design.** `_ACTIVATE_RE` matches `\b(activate|engage|enable|arm|turn on)\b.*\bsecurity\b`; `_DEACTIVATE_RE` matches `\b(stand down|disarm|deactivate|disable|security off|turn off security)\b`. Loose because Whisper hallucinates word order on short commands ("activate the security please" is common). Tested across 10 phrasings: all expected activates fire, "How do I get security clearance?" correctly falls through (no activate verb). Intent-matched transcripts are added to the user transcript line in the console (so the spoken text is still visible) but never sent to Claude — they're handled entirely locally. Returns True/False; main.py's listen_loop uses that to skip `process_question`.
- **Proactive speech via `speak_streaming` single-chunk iterator.** New `_announce()` closure in `main()` wraps `speak_streaming(iter([text]), ...)` with `on_first_audio` flipping the state pill to SPEAKING and `on_amplitude` driving the waveform visualizer — same treatment as a normal voice reply. **Bypasses the mute check** by design: security alerts override quiet mode (the whole point of the bluff is audibility). System text shows the spoken line with a 🚨 prefix so the transcript has a record. Defensive try/except wraps the TTS call — a failed announcement logs but doesn't break the watcher loop.
- **Tray toggle = same code path as voice.** The "Security mode" pystray checkbox calls `watcher.activate()` / `watcher.deactivate()` — the watcher is idempotent so a doubled-arm is a no-op. Useful for testing without voice. `checked=lambda` re-evaluates on each menu open via `_security_is_armed_or_false` so the check mark stays in sync even when state flips from a voice intent.
- **Open-on-demand camera capture, no contention with camera_snapshot.** The watcher mirrors `cameras.py`'s privacy-friendly pattern: `cv2.VideoCapture(index, CAP_DSHOW)` → 2 warmup frames → grab → release. It closes between polls so the webcam's in-use LED stays mostly dark and a concurrent `camera_snapshot` voice call still works (worst case: one watcher cycle's grab fails harmlessly, retried in 2s). Capture at 640×480 (not cameras.py's 1280×720) — YOLO resizes to 640×640 internally anyway, and a smaller source saves JPEG decode + downsample work.

## Milestone 34 follow-on tune — 10s arm-grace + pet-rejection size heuristic.

Live testing in a real deployment (household pets in frame) surfaced two tuning issues: (1) the 5s arm-grace was too tight for the "say activate, walk to the door, step out" use case — bumped to 10s. (2) Household pets can trigger detections. The current filter (`cls == 0 AND conf >= 0.5`) already excludes correctly-classified pets (COCO class 15 = cat) — but YOLO occasionally misclassifies a partially-visible animal as a low-confidence person. Added a **bounding-box size sanity filter** as defense-in-depth: a detected "person" must have `bbox_height >= 30% of frame_height` (`_MIN_PERSON_HEIGHT_RATIO = 0.30`). Reasoning from typical indoor-camera geometry: a standing person occupies 50-70% of frame height, a seated person 30-50%, a pet at typical room distance 10-15%, a close-up pet 20-25%. 0.30 sits comfortably between "smallest realistic person" and "largest realistic pet." The filter catches both well-classified pets (class filter) and mis-classified ones (size filter); two independent rejection layers. A synthetic-bbox unit test exercised 8 scenarios (tall person, small pet-as-person, borderline person, below-threshold person, animal class, low confidence, mixed-detection frame, empty frame) — all correctly classified. Rejected detections log to stderr (`[security] rejected: person@0.55 but bbox height 60px < 144px — likely a pet`) so false negatives can be audited if they ever happen.

- **M34 follow-on — silent-playback bug + dedicated Announcer thread fix.** A live test surfaced a Windows-WASAPI cross-thread audio bug: the activate line spoken from the listen_loop thread played correctly, but every announcement spoken from the SecurityWatcher worker thread produced **no audio + no error in the log + console text still rendered**. Diagnosed from `jarvis.log` — no `[announce] TTS failed` or `[tts] synth failed` lines anywhere, ruling out asyncio/edge-tts failure. Root cause: `sounddevice.sd.play()` uses process-wide global state, and on Windows WASAPI the THREAD that first establishes itself as the audio-output owner gets reliable playback; other threads get silence when an `sd.InputStream` (the long-lived mic capture from `AudioSession`) is concurrently open. The activate path worked because it ran on the listen_loop thread, which had already played audio successfully via the normal `process_question` → `speak_streaming` route earlier in its lifetime. The watcher thread, freshly spawned by `SecurityWatcher.activate()`, had never touched sounddevice before — and silently failed. **Fix:** marshal all proactive speech onto a single dedicated `Announcer` daemon thread. The watcher (and any future proactive-speech caller) calls `_announce(text)`, which `queue.put()`s to an `announce_queue`; the Announcer thread `queue.get()`s and runs `speak_streaming` itself. Always the same thread, so the same audio-owner identity holds across activate / detection / disarm announcements. A sentinel-None shutdown signals the Announcer to exit cleanly during app shutdown. Verified in isolation: both an activate (from a "listen_loop"-named thread) and a detection (from a "SecurityWatcher"-named thread) play through the dedicated Announcer thread — same thread for every announcement, regardless of caller. **Architectural pattern worth keeping:** any future feature that needs to speak proactively (the M35 challenge-response prompt, the deterrent message, etc.) should route through `_announce` — never call `speak_streaming` directly from a non-listen-loop thread.
