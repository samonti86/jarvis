## Milestone 35 — voice-passphrase challenge-response on the M34 watcher

- **What ships:** detection now enters a CHALLENGE state instead of just announcing. *"Please identify yourself within the next 15 seconds, sir."* → 15s to say *"Hey Jarvis, &lt;passphrase&gt;"* (the phrase configured in `.env`; the real value lives only in the gitignored file) → a fuzzy-match comparator clears it (*"Welcome back, sir."*) → 60s cooldown. Timeout fires the deterrent + saves the triggering frame as evidence under `%LOCALAPPDATA%\Jarvis\security\events\YYYY-MM-DD_HH-MM-SS.jpg`. An empty passphrase = M34 announce-only fallback (graceful degradation if the env var is unset).
- **State machine extension:** ARMED → (detection, not in cooldown) → CHALLENGE → (auth | timeout) → ARMED+cooldown. Cooldown blocks re-fire for 60s after EITHER resolution path so an authenticated person walking back through frame doesn't immediately re-trigger. The watcher poll loop (every 2s) runs `_check_challenge_timeout()` before each frame grab, so the 15s timer resolves within ≤2s of expiry. State mutations are guarded by `_challenge_lock` because the watcher thread and the listen_loop thread both touch it (timeout vs `try_authenticate`).
- **Word-level fuzzy matcher — designed around two real failure modes.** The initial implementation used `difflib.SequenceMatcher` against the full string at a 0.7 ratio threshold. Smoke testing surfaced two false-positive classes: **synonym attacks** (substituting a synonym for the final word scored 0.80, because the shared multi-character prefix of the earlier words dominated the whole-string ratio) and, after switching to per-word matching at 0.75, **rhyme attacks** (a rhyming near-word for the final token scored 0.77). Final design: **each word in the passphrase must independently fuzzy-match (≥0.80) some word in the transcript**, with word order ignored. 0.80 is the empirical sweet spot: it admits realistic Whisper wobble (a truncated stem of a passphrase word scores exactly 0.80; a plural-s variant scores 0.93) while rejecting rhymes (0.77 and 0.59 for the two nearest rhyming candidates) and synonyms (0.53). A 15-case smoke test exercises exact / lowercase / trailing punct / plural-s / Whisper-inserted-word / word-order-swap / wake-word-prefix-leak (all accepted) plus synonym / rhyme / wrong-word / half-phrase / empty (all rejected). 15/15 pass.
- **Silent-rejection design.** When a transcript fails the passphrase check, Jarvis does NOT respond — the challenge stays open silently until either the correct phrase arrives or the 15s timer fires. Rationale: announcing "incorrect, try again" gives an attacker feedback to brute-force toward the right answer. A legitimate retry is fine (they know what they said); an attacker hears nothing.
- **Evidence snapshot captured ON DETECTION, saved ON TIMEOUT.** The triggering frame is cached in `_challenge_evidence_frame` the moment the watcher first sees the person. If the timer fires, that cached frame is written to disk as a JPEG — capturing the actual moment of first detection, not a frame 15s later (which would show what they were doing during the challenge, not the detection itself, and might just be them backing away from the camera). If authentication succeeds, the cache is discarded.
- **Evidence directory created lazily** under `%LOCALAPPDATA%\Jarvis\security\events\`. The path is passed in from `main.py` via the SecurityWatcher constructor (the same `default_base_dir()` the memory system uses). JPEG quality 85 — small enough to keep storage trivial (~50-150 KB per snapshot), high enough that faces and clothing are readable for review.
- **Listen_loop diversion order.** In `main.py`, the new check `if security_watcher.is_in_challenge():` sits BEFORE the M34 voice-intent parser. So during a 15s challenge, every transcript goes to `try_authenticate()` — even "stand down" (which is correct: an intruder shouldn't be able to disarm by guessing). After the challenge resolves (auth or timeout), normal voice intent matching resumes. The diversion check is a hot read of a bool flag (no lock — a single-word atomic load on CPython), so latency is negligible.
- **`JARVIS_SECURITY_PASSPHRASE` config addition.** New env var loaded by `src/config.py`. Empty default → CHALLENGE step disabled (M34 behavior). `.env.example` documents the format with a placeholder value + advice on passphrase choice (a 2-4 word phrase Whisper can transcribe reliably). The real value lives only in the gitignored `.env`.
- **What's NOT in M35 (deferred):** the face-recognition auth path (M36), a second camera event source (M37), real notification on deterrent (M38 via Discord webhook). The challenge-response loop ships fully functional on voice alone; M36+ are additive layers.
- **M35 follow-on — defer challenge timer start until prompt playback finishes.** A live test found the 15s timer firing BEFORE authentication was possible. Log analysis pinpointed the cause: the 15s timer started when the watcher entered the CHALLENGE state, then the prompt itself took ~4s to play, leaving only ~11s — minus the 5-10s Whisper "small" model CPU inference latency, the math left no margin. Instructive side-effect: after the deterrent fired, the late transcript leaked into the normal listen_loop path and Claude earnestly answered the passphrase as if it were a trivia question. **Fix:** the Announcer (proactive-speech worker in main.py) now accepts `(text, on_done)` tuples and fires the callback AFTER playback completes (in `finally`, so failed playback still unblocks the caller). SecurityWatcher's `_handle_person_first_seen` passes an `on_done` that arms the 15s timer; until it fires, `_challenge_started_at` stays at 0.0 (a sentinel that `_check_challenge_timeout` skips). Auth-during-prompt-playback still works — the listen_loop diversion checks `is_in_challenge()` (already True the moment the challenge is entered), and once auth resolves, the deferred timer-arm becomes a no-op via `if not self._challenge_active: return` in the callback. Defensive fallback: if the announce call itself throws (TTS path broken), the timer arms immediately so nobody sits in a stalled challenge. 4/4 smoke tests pass. The fundamental STT-latency problem (Whisper "small" on CPU, ~5-10s per transcription) is fixed properly in M36 (GPU offload). This follow-on buys back the wasted budget; M36 buys back the latency itself.
- **M35 follow-on — persistent LOCKED state after deterrent.** Design feedback after the first live test of the working challenge loop: when the deterrent fires, the system should NOT just return to ARMED+cooldown — it should **stay locked** until the correct passphrase is said. Better security posture (an intruder can't simply outwait a 60s cooldown) and closer to the film-J.A.R.V.I.S. behaviour the persona targets. Implementation: a new `_locked` flag on SecurityWatcher + a new `on_locked_changed` callback. `_check_challenge_timeout`, after firing the deterrent, now sets `_challenge_started_at = 0.0` (disables the timer — no second deterrent ever fires) but keeps `_challenge_active = True` so the listen_loop diversion (`if is_in_challenge():`) continues routing all transcripts to `try_authenticate`. While LOCKED: a voice "stand down" is silently consumed by the passphrase comparator (an intruder shouldn't be able to bypass with a guessed disarm command); only the correct passphrase clears it (voice) or the tray Security-mode toggle (a physical-access escape hatch). On unlock via passphrase: `_locked` and `_challenge_active` clear together, the 60s cooldown applies, and a `was_locked` flag in `try_authenticate` triggers the `on_locked_changed(False)` callback before "Welcome back, sir." The watcher stays ARMED — the original intent of security mode is protection, so an unlock just resumes normal operation. A new 🔒 LOCKED indicator in the console (red-600, one shade deeper than ARMED's red-500) swaps in place of the 🛡 ARMED label while LOCKED (showing both would be visual noise — LOCKED implies armed). 5/5 smoke tests pass: (1) deterrent enters LOCKED, (2) a second timeout check is a no-op, (3) "stand down" rejected silently, (4) the correct passphrase unlocks back to ARMED+cooldown, (5) tray disarm clears LOCKED+ARMED+announces. **Behavioral note worth keeping:** `is_in_challenge()` now returns True for BOTH regular CHALLENGE (15s timer ticking) AND LOCKED (no timer, awaiting passphrase) — the listen_loop diversion doesn't need to distinguish, since both states route transcripts the same way. `is_locked()` is a separate public method for callers that care about the distinction.

## Milestone 37 — cloud indoor camera as a second event source for security mode

- **What ships:** new `src/ring.py` with a `RingWatcher` class + a standalone `setup_ring.py` for one-time auth. While security is armed, RingWatcher polls the vendor's cloud API every 5s for motion events on a configured indoor camera. New events fetch a snapshot and feed into `SecurityWatcher.trigger_external_motion(source="ring", jpeg_bytes=...)` — the same challenge/deterrent/LOCKED flow as a local YOLO detection, but with the cloud snapshot as evidence instead of a cv2-captured frame. Closes the "second camera source" item from the original M34 security-arc scoping.
- **Two event sources, one alert pipeline.** The local USB-webcam watcher (local YOLO, 2s polling) and the cloud camera (5s polling) both feed the same challenge state machine. The first to fire enters CHALLENGE; subsequent detections from EITHER camera during an active challenge are suppressed by the existing `if self._challenge_active: return` guard. No deduplication logic needed — the state machine is already "one alert at a time."
- **Why not push notifications via FCM.** `ring_doorbell` does expose a `RingEventListener` for real-time Firebase Cloud Messaging events. Rejected for v1 because (1) FCM setup is complex (separate auth, persistent websocket, project credentials), and (2) the 5s polling latency is fine for security — the challenge prompt itself takes ~4s to play, so polling-induced delay is a small fraction of the total response budget. M37 stays cloud-poll for simplicity; an M37 follow-on can add FCM if/when sub-second latency matters.
- **Async-in-a-thread integration pattern.** `ring_doorbell` 0.9.x is async-only (all methods are `async_*`). The rest of Jarvis is sync/threaded. RingWatcher runs `asyncio.run()` in a daemon thread — giving the integration its own event loop without infecting the main process model. A reusable pattern for any future async-only integration. The sleep in the poll loop is a 100ms-tick `asyncio.sleep` loop checking the sync `threading.Event` stop signal, so disarming feels responsive (no full 5s wait).
- **One-time auth via `setup_ring.py`.** Interactive script: prompts for email/password (getpass masks the password), catches the `Requires2FAError`, re-prompts for the SMS 2FA code, completes auth, lists the cameras on the account, and lets the operator pick which one to watch. Outputs `%LOCALAPPDATA%\Jarvis\ring_token.json` (refresh + access tokens — gitignored, secret) and `ring_config.json` (chosen camera id + name). Subsequent Jarvis startups read both files, build Auth with the cached token, and the vendor lib auto-refreshes when needed (the `_persist_token` callback writes refreshed tokens back to disk).
- **Refactor side-effect — evidence-as-bytes everywhere.** Previously `SecurityWatcher` cached `_challenge_evidence_frame` (a numpy frame from cv2) at challenge entry, then `_save_evidence` encoded to JPEG at deterrent time. The cloud path supplies pre-encoded JPEG bytes (no cv2 involved), so the field became `_challenge_evidence_bytes` and encoding moved from save-time to challenge-entry-time. The local YOLO path now encodes via `cv2.imencode` in `_handle_person_first_seen` and stores bytes. Cleaner: bytes are immutable, don't depend on cv2 buffer lifecycle, and the save path simplifies to `path.write_bytes(jpeg_bytes)` with no cv2 dep. Both paths converge via the new shared `_enter_challenge(jpeg_bytes, source, now)` helper.
- **Graceful fallback when the cloud camera isn't set up.** `ring.is_configured()` checks for both files; main.py only constructs RingWatcher if True, otherwise logs `[main] Ring not configured (run setup_ring.py to enable)` and runs without it. Same pattern as Plex MCP being optional. Re-running `setup_ring.py` is harmless — it just overwrites the cached files.
- **Auth-failure recovery is "re-run setup".** If the vendor rotates the refresh token (rare; happens after suspicious activity from a new IP), the initial `async_update_data` call returns 401 and the watcher logs + exits cleanly. Jarvis keeps running without it; setup can be re-run whenever the integration is wanted back. The watcher doesn't crash, retry endlessly, or affect other subsystems.
- **Snapshot fetch is best-effort.** `cam.async_get_snapshot()` failures (the vendor's snapshot API has occasional flakiness) log and pass `None` to `trigger_external_motion` — the deterrent still fires with empty evidence bytes (no Discord image, no local evidence file, but the spoken bluff + LOCKED state still work). Better than skipping the alert.
- **What's NOT in M37 (deferred):** a real-time FCM listener (an M37 follow-on if needed), multi-camera support (RingWatcher watches one camera; a list of cameras is straightforward but YAGNI for a single-indoor-cam configuration), event-kind filtering beyond "motion" (doorbell rings, light triggers).
- **Files added/touched:** `src/ring.py` (new, ~260 lines); `setup_ring.py` (new, ~100 lines); `src/security.py` (refactored: `_handle_person_first_seen` now encodes-to-bytes-then-delegates to the new `_enter_challenge`; new `trigger_external_motion` public method; `_save_evidence` → `_save_evidence_bytes`; field `_challenge_evidence_frame` → `_challenge_evidence_bytes`); `main.py` (+~25 lines: `RingWatcher` construction + on_armed fan-out); `requirements.txt` (+5 lines for `ring_doorbell>=0.9`).
- **M37 rolled back (2026-05-15) — cloud-camera integration removed. An honest negative result.** After live testing across several days, the cloud-camera integration kept producing false-positive deterrents while the local USB-webcam watcher was solid. Three structural problems that couldn't be fixed without significant rework: **(1) the vendor's snapshot API is gated behind a paid subscription tier** — without it, `async_get_snapshot()` mostly returns None and the event's `snapshot_url` field comes back empty, so our YOLO-on-snapshot filter (added in the M37 follow-on to reject pets) couldn't even run on most events. **(2) The vendor's PIR/CV motion detection is tuned for outdoor doorbell use** — it fires on indoor light changes, curtain movement, pets walking past, HVAC-vent shifts. None of these are filterable without a snapshot. **(3) The "fail-open" defensive behavior** (challenge anyway when the snapshot fails) was the source of the false triggers: in practice snapshot failure was the common path, so we fired challenges on unverified events most of the time — defeating the point. The camera remains useful through its own vendor app (live view, built-in siren, dispatch, motion clips); those features work well in the vendor's ecosystem, they just don't translate to a custom integration. **Removed:** `src/ring.py`, `setup_ring.py`, `ring_doorbell` from requirements, the RingWatcher instantiation in main.py. **Kept:** `SecurityWatcher.trigger_external_motion()`, `verify_person()`, `update_challenge_evidence()` — these are general-purpose external-camera hooks, useful for any future integration (ONVIF/RTSP IP cam, an MQTT bridge, a custom Wi-Fi cam). The architecture investment isn't lost; the vendor-specific code is. **Architectural lessons worth keeping:** the async-in-thread pattern for async-only libs, the parallel-fetch-then-verify pattern for slow snapshot APIs, and the bytes-as-evidence refactor that simplified the local YOLO path too. **For future re-attempts:** the paid tier would solve the snapshot reliability issue but not the indoor-PIR false positives; an MQTT bridge + Docker would give RTSP-stream-based detection (running our own YOLO on the stream), which sidesteps both — but at significant ops cost. Not worth it unless the use case changes.

## Milestone 38 — Discord-webhook real notification on security deterrent

- **What ships:** new `src/notifications.py` with `send_discord_alert(webhook_url, image_bytes, ...)` that POSTs the evidence JPEG to a Discord webhook as a multipart upload. When M35's deterrent timer expires, the watcher now fires this notification IN ADDITION to the spoken bluff + local evidence save — a phone push arrives via the Discord mobile app, with the snapshot of who triggered the alert attached. Free, instant, no API tokens (just a per-channel webhook URL stored in `.env`). Built ahead of M37 in the arc; M37 stayed queued.
- **Why Discord webhooks (vs Pushover, email, SMS, Telegram):** zero cost / zero account friction (a private Discord server was already in place for this project), instant push to phone via the Discord mobile app, native image attachment (Discord auto-embeds the JPEG so it shows inline in the channel feed), and no bot framework / OAuth / API token — the webhook URL alone is the entire auth boundary. The URL is a secret; it lives in `.env` (gitignored) like every other key.
- **Defensive contract preserved.** `send_discord_alert()` never raises into the watcher thread — every failure path (no URL configured / network error / Discord rate-limited / HTTP 4xx-5xx) logs to stderr and returns `False`. The deterrent + local evidence save have already completed by the time the webhook fires; a failed notification is a real loss but mustn't crash the security flow.
- **Fire-and-forget on a daemon thread.** The Discord POST is typically <500ms but can spike to several seconds under load or rate-limiting. `SecurityWatcher._send_discord_alert_async()` spawns a daemon thread (named `DiscordNotify`) so the watcher's main poll loop keeps ticking and the LOCKED state transition isn't delayed by a slow upload. Daemon = dies with the process if Jarvis quits mid-upload (acceptable: the deterrent already played and the evidence is on disk).
- **Message format.** Markdown-aware Discord content (`🚨 **Security Alert** · 5:30 PM` headline + a short body), a `username: "Jarvis"` override so the message displays under that name regardless of the webhook's default, and the JPEG attached as `files[0]` — Discord's multipart conventions. The emoji at the start makes the lock-screen push-notification preview eye-catching.
- **Graceful M35 fallback if no URL is configured.** An empty `DISCORD_WEBHOOK_URL` = the M35 bluff still fires and evidence is still saved locally, just no push. Useful for deployments that don't want a phone push, or that are still setting Discord up.
- **Webhook setup flow** documented in `.env.example`: right-click channel → Edit Channel → Integrations → Webhooks → New Webhook → Copy URL → paste into `.env`. ~30 seconds end-to-end.
- **Smoke-tested:** an empty URL returns False without raising; an invalid hostname returns False after a clean ConnectError log; a real test against the project's Discord server confirmed the message + image attachment arrived correctly in the channel (and on the phone via Discord mobile push). The end-to-end deterrent test (walk into frame → 15s silence → deterrent + push) then validated it live.
- **Files touched:** `src/notifications.py` (new, ~120 lines); `src/config.py` (+1 field); `src/security.py` (+~25 lines: new constructor arg + `_send_discord_alert_async` helper + call site in `_check_challenge_timeout`); `main.py` (+1 arg passed to SecurityWatcher); `.env.example` (+15 lines documenting webhook setup + the security tradeoff).

## Milestone 36 — STT GPU offload to the homelab GPU host (faster-whisper on a GTX 1650)

- **What ships:** new `stt_server/` package (FastAPI app + requirements + a portable `run_server.bat` + README) running on the homelab GPU host (the same laptop that runs Plex). A single `POST /transcribe` endpoint accepts a WAV upload + an optional language hint and returns `{text, language, duration_ms}`. It loads faster-whisper "small" with `device="cuda"` + `compute_type="float16"` at startup; ~700 MB VRAM resident, plenty of headroom on the GTX 1650's 4 GB even with Plex transcoding active. A client refactor in `src/speech_to_text.py` adds dual-backend routing — `_dispatch_transcription` picks local CPU vs remote GPU based on `STT_BACKEND` (`auto`/`gpu`/`cpu`) + `STT_SERVER_URL`. **Auto-fallback is silent**: any remote failure (timeout / HTTP error / parse error) logs to stderr and falls back to local CPU for that one turn — a slightly slower response, but no interruption.
- **Measured speedup (M36 smoke test, GTX 1650, "small" model, 2s audio):** CPU local 5860 ms → GPU server-inference 1013 ms (5.8×) → GPU end-to-end 1500-2500 ms incl. HTTP (3.3×). The M35 challenge window with ~3s of speech: CPU was 5-10s (the timer often expired), now 1.5-2.5s (a comfortable margin). The numbers are conservative — synthetic audio without real words forces the decoder to run a long pass; real speech with a language hint clocks ~300-500 ms server-side.
- **Three install hurdles surfaced + fixed during deployment** (worth documenting because all three would re-bite anyone deploying ctranslate2 GPU on Windows):
  1. **Missing CUDA runtime DLLs.** `faster-whisper` and `ctranslate2` do NOT transitively pull in the `nvidia-*-cu12` packages. The cuBLAS load failed with `cublas64_12.dll is not found` on first inference. Fix: `requirements.txt` declares all four explicitly — `nvidia-cublas-cu12`, `nvidia-cudnn-cu12`, `nvidia-cuda-nvrtc-cu12`, `nvidia-cuda-runtime-cu12` (the last is the silent transitive dep of cuBLAS — cublas needs `cudart64_12.dll`).
  2. **`os.add_dll_directory` alone is insufficient.** That API covers Python's extension-module loader (the `.pyd` file), but ctranslate2 internally calls plain `LoadLibrary()` for cuBLAS at first inference. Plain LoadLibrary uses the default Windows search path (System32, exe dir, PATH) — NOT the Python-added dirs. The symptom was insidious: model LOAD worked (cuDNN loaded via the `.pyd`-honored path); model INFERENCE failed. Fix in `server.py`: also prepend each CUDA bin dir to `os.environ["PATH"]` before importing faster-whisper.
  3. **`os.add_dll_directory` cookies get GC'd.** The function returns an `_AddedDllDirectory` whose `close()` (auto-called on GC) removes the directory from the search path. The first attempt discarded the return value — so the path was valid at module-load time but gone by inference time. Fix: store the cookies in a module-level `_dll_cookies: list`.
- **Host-specific WMI gotcha (re-discovered).** `New-NetFirewallRule` failed with "Invalid class" on the GPU host — a known-broken `StandardCimv2` WMI provider on that box. Workaround: `netsh advfirewall firewall add rule ... profile=any`. The README now warns about this.
- **Why a separate venv on the server.** `stt_server/` lives in the same git repo as the main Jarvis project — same source of truth, evolves in lockstep. But the server's deps (faster-whisper + 4 nvidia CUDA pip pkgs + fastapi + uvicorn + python-multipart) differ from the desktop client's. An independent `stt_server/venv/` keeps them clean. `requirements.txt` lives next to `server.py` so the install is `cd stt_server && pip install -r requirements.txt`.
- **Autostart on the GPU host via Task Scheduler (not NSSM).** Simpler — no admin needed, no third-party tool. `schtasks /create /tn JarvisSTTServer /tr run_server.bat /sc onstart /ru <user>` survives reboots. `run_server.bat` uses `%~dp0` so it's path-portable across clone locations. NSSM remains documented as the alternative (faster startup, a true service that runs before user login) for anyone who wants that pattern.
- **Connect vs read timeout split on the client.** The initial smoke test with the server down made every voice turn wait 15s before falling back to CPU — bad UX. Switched to `httpx.Timeout(connect=2.0, read=15.0)`: a DOWN server is detected in ~2s (TCP SYN timeout), so auto-fallback feels close to instant; the read still has the 15s budget for slow cold inference or a server under GPU contention from Plex.
- **5/5 backend-routing scenarios pass + an end-to-end live test:** (1) `cpu` forced → local only, (2) `auto` + empty URL → local only, (3) `auto` + URL + reachable → remote, (4) `auto` + URL + unreachable → silent fallback to local in ~2.5s, (5) `gpu` forced + unreachable → returns a clear `[STT GPU offload failed: ...]` error string (no crash, no hang).
- **Files added/touched:** `stt_server/server.py` (~200 lines new), `stt_server/requirements.txt`, `stt_server/run_server.bat`, `stt_server/README.md`; `src/speech_to_text.py` (+~120 lines for backend dispatch); `src/config.py` (+2 fields); `main.py` (+2 args passed to `transcribe_after_wake`); `.env.example` (+13 lines documenting both env vars).

## Milestone 39 — face recognition as a parallel auth path during CHALLENGE

- **What ships:** new `src/face_auth.py` (~340 lines) wrapping `face_recognition` (dlib-based, MIT) into Jarvis's voice-first flow. One-time enrollment via a new tray menu item ("Enroll my face") OR a voice intent ("Jarvis, enroll my face" / "remember my face" / "register my face") captures 5 frames in one camera-open cycle, runs HOG face detection + 128-d encoding on each, averages the successful frames into one canonical (128,) vector, and persists it to `%LOCALAPPDATA%\Jarvis\security\face_encoding.npy`. During an active CHALLENGE (or LOCKED) state, the watcher loop runs face verification against the stored encoding on every YOLO tick (2s cadence) IN ADDITION to the voice-passphrase path — first match wins, either path clears the challenge. No new poll cadence; it piggybacks on M34's existing 0.5 Hz watcher.
- **Shared auth-resolution helper.** `try_authenticate()` was refactored to extract `_mark_authenticated(method)` — both the voice path and the new `_try_face_auth(frame)` path call it. A single source of truth for the state transitions (clear `_challenge_active`, clear `_locked`, enter cooldown, fire the UI callback, announce "Welcome back, sir."). The `method` parameter ("voice" or "face") only changes the log line — user-facing behavior is identical, so the voice flow doesn't notice it's running alongside another auth.
- **Encoding lifecycle: lazy load on each arm.** `SecurityWatcher.activate()` reads `face_encoding.npy` from disk every time security is armed (`np.load`, ~1ms). Re-enrollment mid-session takes effect without a Jarvis restart. None on any failure (no path configured, no enrollment yet, corrupt file, shape mismatch) — the face-auth path is silently skipped and the voice passphrase continues to work alone. It logs `[security] face auth enabled — enrolled encoding loaded` or `... disabled — no enrolled encoding` so the active mode of the current arm is visible.
- **Tunable strictness via `JARVIS_FACE_MATCH_THRESHOLD`.** A Euclidean-distance threshold for `face_recognition.face_distance`. Default **0.5** (security-grade strict) vs `face_recognition`'s permissive default of 0.6 (photo-album use). Live measurements: a clean head-on match scored 0.139 (~4× under threshold), a partial off-angle scored 0.378 (still a clear pass), and a far-from-camera position scored above 0.5 → no match → fell through to the voice-passphrase path. Exactly the intended behavior: face auth gives a free pass when the person is properly in frame; the camera-too-far case still requires voice. Tune lower (0.4) to require even cleaner shots; tune up (0.55-0.6) to make face auth fire in more borderline cases.
- **Voice-intent regex anchored on "face".** `\b(enroll|remember|register|memorize|learn|save)\b\s+(my\s+|your\s+)?face\b`. The "face" anchor prevents false positives from casual "remember to..." sentences. The cost of the anchor: a Whisper mis-hearing of "enroll" as "and roll" (observed live) falls through to Claude as a question — which is the right failure mode: Claude asks for clarification instead of doing the wrong thing.
- **Listen-loop dispatch order: security first, then face-enroll, then Claude.** Voice-intent matching in `main.py` checks face-enrollment AFTER the security-watcher diversion (so a passphrase-during-challenge utterance can't be hijacked) and BEFORE the LLM call (so Claude doesn't try to fulfill the intent with the wrong tool). Both the typed-text path and the voice path use the same `on_enroll_face` callback wired by `main.py` — the same dispatch contract whether the request is typed or spoken.
- **Defensive contract: a `face_recognition` import failure ≠ a Jarvis crash.** Module-level `_fr = None`, `AVAILABLE = False`, and `_IMPORT_ERROR` cache the import result on first call. Every public function returns a sentinel value if the import failed — `is_enrolled` returns False, `load_encoding` returns None, `enroll_from_frames` returns `(False, "Face recognition isn't available, sir.")`, `verify_frame` returns False. Face-auth is purely additive: if the dlib install ever breaks, the voice passphrase keeps working.
- **Multi-frame capture helper in `cameras.capture_frames`.** A new helper opens the configured webcam ONCE, captures N frames spaced by `interval_seconds`, and releases. Saves ~3-4s of DirectShow init per frame vs N independent camera-open cycles (which is what naively reusing `execute_camera_snapshot` would have done). Same warmup + black-frame guard as the existing snapshot path. Never raises — failures return `None` with a log line.
- **The dlib silent-segfault gotcha — worth documenting for anyone who touches this code.** The initial `enroll_from_frames` used the idiomatic-but-now-unsafe zero-copy BGR→RGB conversion: `rgb = frame[:, :, ::-1]`. That returns a numpy VIEW with negative strides on the channel axis. Under the current install (dlib 20.0.1, numpy 2.4.4, Windows + Python 3.12), the HOG detector segfaults silently when handed a non-contiguous frame at 1080p — exit code 139, no traceback (a native crash in C++ before Python can catch it). The 480×640 case survives because the detector short-circuits early on uniform images, which is the exact gotcha that makes the issue invisible to small smoke tests. Fix: `rgb = np.ascontiguousarray(frame[:, :, ::-1])` at both call sites (enroll + verify). One ~6 MB memcpy per frame at 1080p; well worth not crashing. The constraint is documented so a future optimization pass doesn't remove the copy again.
- **Real-world geometry observation from live test.** HOG needs the face to be a meaningful fraction of the frame. At seated-at-the-desk distance (the camera sees the whole scene, the face is ~5% of frame area), HOG often misses entirely; at standing-in-front-of-the-camera distance (face ~20-30% of frame area), it nails the match within one watcher tick. This IS the intended safety property — face auth shouldn't be a free pass from across the room. Two follow-ons worth considering when this becomes a limiter: (a) crop to the YOLO person bbox before HOG — the bbox already exists in the watcher, so HOG gets a much larger relative face; a free win architecturally; (b) pass `number_of_times_to_upsample=1` to `face_locations` — HOG's built-in 2× pyramid, ~3-4× CPU per call but finds smaller faces. Not implemented in M39 because the current 7-attempts-per-15s-challenge already works well in a normal "I'm here to use my PC" posture.
- **Smoke test landed alongside the integration.** `smoketest_face.py` exercises enroll → persist → load → verify in ~10s with no Jarvis launch needed. It caught the dlib segfault during development; kept around as a regression check for future dlib / face_recognition / numpy upgrades.
- **What's NOT in M39 (deferred):**
  - **Multiple enrolled faces.** Currently one encoding file = one authorized person. Multi-user enrollment would change the data shape from `(128,)` to `(N, 128)`, and `verify_frame` would take the min distance across all enrolled users. Useful when an additional household user needs auth too; a trivial extension when it becomes a real need.
  - **CNN model fallback when HOG misses.** `face_recognition.face_locations(rgb, model="cnn")` is far more robust to angle/occlusion but requires CUDA and is much slower. Currently HOG only. Could become a CUDA offload to the GPU host, like the M36 STT path.
  - **Enrollment refresh UX.** Currently re-running enroll just overwrites the encoding file. A `delete_encoding` helper exists in `face_auth.py` (and would also be a tray menu item) but isn't wired — YAGNI until a "forget my face" flow is actually wanted.
- **Files added/touched:** `src/face_auth.py` (new, ~340 lines); `smoketest_face.py` (new, ~100 lines); `src/cameras.py` (+~70 lines for `capture_frames`); `src/config.py` (+1 field for the threshold); `src/security.py` (+~85 lines: encoding-path constructor args, lazy-load on activate, `_try_face_auth`, the `_mark_authenticated` refactor, the watcher-loop face check); `src/tray.py` (+~15 lines for the "Enroll my face" menu item); `src/ui.py` (+~17 lines for the on_enroll_face wiring); `main.py` (+~44 lines for the `_trigger_face_enrollment` closure + listen_loop dispatch for both typed-text and voice intent + SecurityWatcher constructor args); `.env.example` (+threshold doc); `CLAUDE.md` (status + future-work updates).

## Milestone 40 — `system_control` mutating-verb companion (`flush_dns` + `restart_service`)

- **What ships:** two new confirmation-gated actions on the existing `system_control` tool — `flush_dns` (runs `ipconfig.exe /flushdns`) and `restart_service` (runs `Restart-Service -Name <target>` via PowerShell). Both follow the M23 `kill_process` confirmation pattern (Claude must ask in plain language, get an explicit yes, then call again with `confirmed=true` — a server-side gate, not a system-prompt promise). Both additionally require Jarvis to be running as Administrator; if not, they return a clean "needs admin" error string that Claude paraphrases. `restart_service` further validates the service name against `^[A-Za-z0-9._-]{1,128}$` before any subprocess fires — the same per-verb input-validation discipline `pc_shell` (M33) established.
- **Architectural decision: extend `system_control`, NOT `pc_shell`.** The diagnostic-vs-action split and `pc_shell.py`'s own docstring both explicitly carve out: read-only tools and mutating tools stay separate. Adding `flush_dns` / `restart_service` to `pc_shell` would conflate them and break the "narrow blast radius" property `pc_shell` was designed for. So M40 grew the right tool — `system_control` already had `kill_process`, and the new actions slot in alongside it with no surface refactor.
- **Confirmation contract reuse.** Both new actions return the same shape of "needs confirmation" string that `kill_process` returns: `"<action> requires explicit user confirmation. Ask the user to confirm X, then call this tool again with confirmed=true."` Claude reads it, asks, the user agrees verbally, Claude calls again with the flag set. The gate is enforced in the function body — if Claude (or a future hallucination, or a misbehaving prompt) ever forgets to ask, the worst outcome is that the tool refuses and tells Claude what to do. Defense in depth without UI complexity.
- **Elevation handling: detect once, fail loudly, don't UAC-bump mid-flow.** A module-level `_IS_ADMIN: bool = _detect_admin()` queries `ctypes.windll.shell32.IsUserAnAdmin()` exactly once at import. The mutating actions check this and return a friendly "Restart Jarvis from an elevated prompt and try again" string when False. **Explicitly rejected:** prompting for elevation mid-voice-flow via `ShellExecuteEx(verb="runas")`. That would surprise the user with a UAC popup partway through a conversation, and it would require complex subprocess + temp-file-output capture plumbing for marginal benefit. The honest failure mode wins. The follow-on for "I want to do an M40 action right now without restarting Jarvis" lives in the M41 candidate — an opt-in "Restart elevated" tray item — not in M40 itself.
- **Why this scoping is the entire point: least privilege by default.** The design principle, stated at M40 scoping time: Jarvis stays an assistant, not an unbounded agent with root on the host. The architectural translation is least-privilege by default, power as opt-in, every privileged path gated and audited. Three structural defenses in M40 enforce this: (1) a per-action server-side confirmation flag, (2) a per-action elevation check, (3) per-action input validation (a regex on the service name). None of those defenses live in the system prompt — they're in code, where a model regression or a prompt-injection attempt can't slip past them. This principle now applies to every future scoping conversation.
- **Why `ipconfig.exe /flushdns` and not `Clear-DnsClientCache`.** They do effectively the same thing on Windows 10/11 — both invoke the DnsApi flush via the same RPC. But `ipconfig.exe` is older, smaller, always present, and not subject to PowerShell module breakage across Windows updates. `Clear-DnsClientCache` lives in `DnsClient` (a built-in module) which has occasionally regressed. ipconfig is the "always works" path; we stick with it.
- **Why PowerShell `Restart-Service` and not `net stop` + `net start` or `sc.exe`.** `Restart-Service` handles dependent-service ordering correctly, surfaces SCM errors as catchable exceptions, and with `-ErrorAction Stop` + try/catch in a small inline script we get an explicit `exit 1` on failure plus a usable error message. `net.exe stop` / `start` ignores dependents and gives terrible error text. `sc.exe` works but its output is harder to parse cleanly.
- **Per-action audit log line.** `[system_control] flush_dns exit=0 in 0.03s` and `[system_control] restart_service 'Spooler' exit=0 in 1.41s`. Same shape as pc_shell's audit lines; grep `jarvis.log` for `[system_control]` and you have a complete log of every privileged action Jarvis has ever taken on the host.
- **Tool-description changes.** The Anthropic `SYSTEM_CONTROL_TOOL` dict description now enumerates `flush_dns` and `restart_service` in the action enum, describes the service-name format in the `target` field, and the `confirmed` field's description names all three confirmation-gated actions explicitly. Claude's prompt-cached system message therefore knows about the new actions on the very next conversation turn — no separate "rolling out a new tool" choreography.
- **Live test (2026-05-15):** (1) non-elevated launch → "Hey Jarvis, flush my DNS cache" → Claude asked for confirmation → confirmed → got the clean "needs Administrator" message; (2) elevated launch → same prompt → flush succeeded, exit 0 in 0.02s, "DNS resolver cache flushed."; (3) elevated launch → "Restart Spooler" → confirmation → success, exit 0 in 1.41s. All three confirmation prompts fired in plain English before the second tool call. One curious observation: in test (3) Claude ran `iters=3` and called `flush_dns` AGAIN preemptively before `restart_service` — likely the model reading a recent session summary ("there was a privileges issue with the DNS flush") as a hint to retry. Harmless (flushing an empty cache is a no-op) but worth knowing if it escalates.
- **What's NOT in M40 (deferred):**
  - **`dhcp_cycle`** — `ipconfig /release` + `/renew`. Useful when the network is genuinely broken, but judged less common than DNS flush + service restart for V1. Same elevation requirement, same confirmation pattern; mechanical to add.
  - **`Clear-DnsClientCache` as a separate verb** — semantically identical to `flush_dns` on modern Windows; not worth a second action.
  - **`Restart-NetAdapter`** — a bigger blast radius (drops the network connection) and harder to test safely; deferred until requested.
  - **On-demand elevated restart** — the M41 candidate. A "Restart Jarvis elevated" tray item that uses `ShellExecuteEx(verb="runas")` to relaunch under UAC. Reuses M32's flag-and-defer relaunch plumbing. The "occasional sudo" experience for when M40 actions are actually needed, without baking elevation into the default Jarvis runtime.
- **Files added/touched:** `src/system_control.py` (+~140 lines: `_detect_admin` + the `_IS_ADMIN` cache, `_do_flush_dns`, `_SERVICE_NAME_RE`, `_do_restart_service`, two new dispatch branches in `execute_system_control_tool`, an expanded tool description + enum + field docs); `CLAUDE.md` (status, system_control capability bullet, M41 "Next" candidate, "Possible future work" strike-through for M40 + new follow-on bullet).

## Milestone 41 — "Restart Jarvis (Administrator)" tray menu item

- **What ships:** a new tray menu item directly below the existing M32 "Restart Jarvis" entry. Clicking it from a non-elevated Jarvis → the normal M32 shutdown sequence runs (mic released, listen_loop joined, Plex MCP + SSH closed, in-progress memory session sealed) → at the end of `main()`, `autostart.relaunch_elevated()` invokes `ShellExecuteW(None, "runas", pythonw, jarvis.pyw, cwd, SW_NORMAL)`, which triggers the Windows UAC dialog → accept → a new Jarvis process spawns elevated → the old Jarvis exits. The menu item is **conditionally visible** — when the current process is already elevated, the item is omitted from the menu entirely (no point offering an upgrade path when there isn't one to take). Result: the tray menu IS the elevation indicator. Symmetric drop-back: click the regular "Restart Jarvis" to relaunch non-elevated.
- **The "occasional sudo" UX, by design.** The least-privilege principle established at M40 scoping gets its first opt-in elevation path here. Default Jarvis stays at user privilege; SRE-grade power is one tray click + one UAC click away when actually needed; it goes away again at the next regular restart. Same lifecycle as `sudo` granting a single shell, not granting a whole login session.
- **`autostart.is_admin()` is the new single source of truth.** Centralized in `autostart.py` alongside the relaunch helpers (the natural home — `autostart` already owns "spawn a new Jarvis process"). `system_control.py` was refactored to import from there, eliminating the M40-era duplicate `_detect_admin`. A lazy ctypes call to `shell32.IsUserAnAdmin()`; defensive — it returns False on any failure, which keeps the M40 mutating gates closed if Windows ever does something weird with the syscall.
- **`autostart.relaunch_elevated()` — why ShellExecuteW and not Popen.** `subprocess.Popen` has no API for "launch this elevated" on Windows — the runas verb is a shell concept, not a process-creation flag. ShellExecuteW with `lpOperation="runas"` is the canonical Windows entry point that Explorer's right-click "Run as administrator" uses internally. It returns an HINSTANCE-coded int (>32 = success, ≤32 = an error code such as ERROR_CANCELLED 1223 for a UAC cancel). We pass `None` for the parent HWND, the venv pythonw as `lpFile`, the quoted launcher path as `lpParameters`, and the project root as `lpDirectory`. Same path correctness as the existing `relaunch()`.
- **Tristate relaunch flag.** `ui._relaunch_requested: bool` became `ui._relaunch_mode: str | None` with values `None`, `"normal"`, `"elevated"`. `_handle_restart` sets `"normal"`, `_handle_restart_elevated` sets `"elevated"`. The `relaunch_requested` boolean property survives as a thin wrapper (`mode is not None`) so any future code that only cares about "did someone click some restart?" keeps working. `main.py` dispatches on the new `relaunch_mode` property and calls the matching `autostart.*` function.
- **UAC cancel = no new Jarvis.** Decided up front to do the UAC handshake at the very end of shutdown (after `worker.join()`), not before — the same release-mic-first ordering the M32 design carefully chose. The cost: if the UAC prompt is declined, the current Jarvis has already finished sealing its session, and no new instance starts; a manual relaunch is needed. An acceptable tradeoff because the cancel path is rare AND the alternative (UAC-first, then shutdown) risks the new elevated process fighting the dying old one for the mic / Plex MCP / SSH handles. Cleanly logged: `[main] elevated relaunch was cancelled or failed — Jarvis will not restart`. Confirmed as expected behavior in live test.
- **Startup elevation log line.** Every Jarvis start now writes `[main] running elevated: True/False` to stderr near the "Jarvis ready" banner. A trivial grep in `jarvis.log` shows the elevation state of every session — useful when correlating an M40 action that worked vs. failed across the same day.
- **Live test (2026-05-15):** (1) non-elevated launch → the tray showed both "Restart Jarvis" and "Restart Jarvis (Administrator)"; (2) clicked the Administrator item → "restarting Jarvis (Administrator)…" in the console → normal shutdown → UAC dialog → accepted → the new Jarvis came up elevated, the log showed `[main] running elevated: True`, and the (Administrator) item was correctly absent from the elevated session's menu; (3) M40 `flush_dns` succeeded under the upgraded session, confirming the elevation path actually wired through; (4) repeated the test declining UAC → expected log line and clean exit, no second Jarvis spawned. All four passes.
- **What's NOT in M41 (deferred / rejected):**
  - **Voice intent** ("Hey Jarvis, restart yourself as administrator"). Adds intent-parsing complexity; tray-only for V1. Same regex-extension pattern as M39's `matches_enroll_intent` if it becomes a real ergonomic need.
  - **A "drop back to non-elevated" sibling menu item.** Symmetry would be nice but is redundant — the existing "Restart Jarvis" already does this when invoked from an elevated session (the spawn is via `subprocess.Popen`, which inherits the parent's token by default, so a non-elevated `Popen` from an elevated Jarvis would *still* spawn elevated; punted because the practical workflow is "click Quit, manually relaunch," which is already one step).
  - **Persistent elevated mode across restarts.** Explicitly out of scope — it would conflict with the least-privilege principle.
  - **A status-bar admin badge in the console UI.** Tempting (visual confirmation at a glance) but the tray menu itself is already the indicator (item present = non-elevated, item absent = elevated). Adding a console badge is a small follow-on if wanted; not load-bearing.
  - **Scheduled-task-based elevated autostart.** Considered + rejected during the M40/M41 conversation — silently auto-elevating Jarvis at every boot defeats the entire least-privilege design. M41 makes elevation an opt-in gesture, not a baseline.
- **Files added/touched:** `src/autostart.py` (+~80 lines: `is_admin()`, `relaunch_elevated()`, ctypes + sys imports added); `src/system_control.py` (-15/+3 lines: dropped the duplicate `_detect_admin`, now imports from autostart); `src/ui.py` (+~25 lines: tristate flag + new `_handle_restart_elevated` + `relaunch_mode` property + tray wiring); `src/tray.py` (+~20 lines: new constructor kwarg, conditional menu item via `is_admin()`, `_handle_restart_elevated` bridge); `main.py` (+~25/-7 lines: tristate dispatch in the post-shutdown relaunch block + the startup elevation log line); `CLAUDE.md` (status + "Next" rewrite + M41 strike-through in "Possible future work").

## Milestone 42 — `dhcp_cycle` as the third mutating verb (closes the SRE arc)

- **What ships:** a new `dhcp_cycle` action on `system_control` — runs `ipconfig.exe /release` then `ipconfig.exe /renew` sequentially, with the same confirmation + admin gates as M40's `flush_dns` and `restart_service`. A single combined verb rather than separate `dhcp_release` / `dhcp_renew` actions, because the two are virtually never useful in isolation: release alone leaves you offline, renew without release won't dislodge a stuck lease. The combined cycle IS the SRE move. With M42 the trio of "fix my network" verbs (`flush_dns`, `dhcp_cycle`, `restart_service`) is complete; combined with `kill_process` from M23, system_control now covers the realistic 90% of single-user Windows-desktop troubleshooting.
- **Why this closes the arc** rather than continuing to bolt on verbs: the M40/M41/M42 scoping audit explicitly weighed candidate follow-ons — `stop_service` / `start_service` granularity, `Restart-NetAdapter`, `netsh winsock reset`, per-verb timeout overrides — against actual use cases for a single-user Windows desktop. Conclusion: the trio plus `kill_process` is a saturating set for the realistic 90%; further verbs either duplicate functionality (`stop_service` is subsumed by `restart_service` for normal workflows), have an unacceptable blast radius (`Restart-NetAdapter` momentarily kills Jarvis's own network paths to Plex MCP / SSH / the Anthropic API), or are too rare to justify the allowlist surface (a Winsock reset requires a reboot). All those candidates remain documented in CLAUDE.md's "Possible future work" with their explicit rationale, so the list survives — but they don't block calling M40+M41+M42 architecturally complete. This is least privilege applied to *scope*, not just permissions: add what you'll actually use, defer what you won't, write down why.
- **Failure ordering: release-fails → abort.** If `ipconfig /release` returns non-zero, the new code does NOT proceed to `/renew`. Rationale: renewing on top of an uncertain network state risks compounding the breakage — better to surface the release error verbatim and let a human diagnose. The opposite case (`release` succeeds, `renew` fails or times out) gets a dedicated error message that explicitly flags "the host has no active lease right now," so Claude can warn that connectivity is currently dead and a retry is needed.
- **Timeouts: 30s per subprocess.** On a typical home network: release <1s, renew 1-5s (measured live run: 0.91s + 4.73s = 5.6s total). Sluggish DHCP servers can push renew toward Windows's own internal 60s ceiling; 30s catches the "server is down / unreachable" case before the wait gets tedious, while still allowing a normal-slow renew to complete.
- **Tool-description language: warn about the connectivity drop.** The confirmation-prompt instructions explicitly tell Claude to warn that this will briefly drop network connectivity, not just ask "Confirm?". The live test verified Claude relays this — *"Heads up — this will briefly drop your network connectivity while the lease cycles. Confirm: release and renew the DHCP lease?"* That language correctness is non-trivial: a sterile "Confirm: cycle DHCP?" would get a yes without the user realizing they're about to lose internet for ~5 seconds. A confirmation gate is only a real gate if it carries the information needed to evaluate it.
- **Live test (2026-05-15) — M41+M42 ran in an actual SRE-loop sequence**, not as isolated test runs: (1) non-elevated launch → *"Release and renew my DHCP lease"* → Claude warned about connectivity + asked for confirmation → confirmed → got the clean "needs Administrator" error; (2) clicked tray "Restart Jarvis (Administrator)" → UAC accepted → a new elevated session came up; (3) *"Cycle my DHCP lease"* → Claude warned + confirmed → release in 0.91s + renew in 4.73s → *"Done. Lease released and renewed on all adapters. You're back online."*; (4) a subsequent web-search-backed question returned cleanly, proving connectivity was actually restored. The whole flow exercised M40 (the mutating gate), M41 (tray-driven elevation upgrade), and M42 (the new verb) in one continuous workflow — exactly the "occasional sudo for SRE actions" UX the arc was designed to enable.
- **What's NOT in M42 (and explicit reasons for each, so the analysis isn't redone later):**
  - **Adapter-name targeting** (e.g. "release only WiFi"). When DHCP is broken you almost always want to cycle everything; per-adapter targeting adds an input-validation surface and a `target` parameter for a use case that rarely shows up. Easy to add later if needed.
  - **Separate `dhcp_release` and `dhcp_renew` verbs.** See above — they're never useful in isolation. The combined verb is the SRE move.
  - **`Restart-NetAdapter`.** A bigger blast radius (drops all connectivity, not just the IP lease), and crucially: it kills Jarvis's OWN network paths mid-conversation (Plex MCP, SSH to the homelab host, Anthropic API streaming). Doing that in the middle of a voice exchange is exactly when you don't want it. Deferred until it has a clear use case that justifies the disruption.
  - **`stop_service` / `start_service` separate from `restart_service`.** The theoretical use case ("stop Windows Update while I install something") isn't on the actual workflow list, and the realistic pattern there is "stop, do stuff, manually start back" — not a single tool call. Wait for actual demand.
  - **`netsh winsock reset` / `netsh int ip reset`.** These require a reboot to take effect — they're emergency-mode fixes, not "Jarvis, cycle me" verbs. Out of scope unless a recurring need develops.
- **Files added/touched:** `src/system_control.py` (+~85 lines: `_do_dhcp_cycle` with sequential release/renew + ordered-failure logic, expanded `SYSTEM_CONTROL_TOOL` description + enum + `confirmed` field doc, new dispatcher branch); `CLAUDE.md` (status bump, capability bullet expanded to include dhcp_cycle, "Possible future work" M40 follow-on bullet folded into the new M42 strike-through entry).

## Milestone 43 — TMDB movie/TV tool + the `_http_get_with_retry` extraction it rode in on

- **Two-part milestone, deliberately bundled.** The M22 milestone note left a standing instruction: `_http_get_with_retry` was triplicated across `sports.py` / `weather.py` / `games.py` (byte-identical except the `[tool]` log prefix), and the extraction should ride in "on the next tool that needs it" rather than as a speculative standalone refactor — the rule-of-three discipline. M43's TMDB tool is that next HTTP tool, so the refactor lands first (TMDB consumes the shared helper from line one — no fourth copy ever exists).
- **Part A — `src/http_util.py`.** A new module exposing `http_get_with_retry(url, params=None, *, tag, timeout=10.0, backoff=0.5)`. The behavior is byte-for-byte the original contract: one retry, transport errors only (`RequestError`); never retry `HTTPStatusError` (a 404/500 won't fix itself and this is a latency-critical voice path); returns `httpx.Response | None`, and callers branch on `None` and never see an exception. The 10s-timeout / 0.5s-backoff constants moved with it as keyword defaults. `tag` is **keyword-only and required** — a shared helper with anonymous failures would be a debugging regression versus the per-tool copies it replaces, so every caller must still identify itself in `jarvis.log`.
- **The `functools.partial` call-site decision (recorded).** Each consumer binds its prefix once: `_http_get_with_retry = partial(http_get_with_retry, tag="games")`. This is *partial application* — pre-binding `tag` yields a callable with the original `(url, params=...)` signature, so all ~12 existing call sites across the three modules stayed **byte-identical**. The alternative (rewriting every call to pass `tag=` explicitly) churns ~12 lines of working, tested code for zero behavioral gain. Smallest-diff-over-working-code is the right call for a pure extraction; the diff is "delete the function body, keep the name as a `partial` alias." Dead `import time` + `import httpx` + the two moved constants were removed from each of the three modules (the only `httpx`/`time` references in those files were inside the helper). Verified post-refactor that `partial(...).keywords == {'tag': 'games'}` and that the three modules still import + behave identically.
- **`requirements.txt` comment correctness.** The `httpx>=0.27` line carried a comment "we use it directly in src/sports.py" — after the extraction that's `src/http_util.py`. (The comment was kept accurate; the dependency itself is unchanged — `httpx` is still a transitive of `anthropic` and now a direct dep of `http_util`.)
- **Part B — `src/tmdb.py` (`TMDB_TOOL`, `execute_tmdb_tool`).** A deliberate structural twin of the M22 `games.py`: the same four modes (`search` / `details` / `popular` / `similar`), the same never-raises defensive contract, the same read-`os.getenv`-at-call-time API-key handling, the same voice-shaped brief/detail formatting, and the same 600-char sentence-boundary overview truncation. It backs onto TMDB's free API with the `api_key=` v3-auth query param — the exact same low-friction shape as RAWG (no OAuth dance, no dev-account gate, instant key, no credit card).
- **Why TMDB over OMDb / TVDB / IGDB-style (recorded).** OMDb's free tier is 1k req/day and its data is thin (no real recommendations, no trending). TheTVDB moved to a paid API. TMDB is free, has both movies AND TV in one API, exposes a genuinely good `/recommendations` engine, and uses the same `key=`-query-param auth as RAWG, so it slots into the established pattern with zero new auth machinery. The same "lowest-friction comparable-coverage option" logic M22 used to pick RAWG over IGDB.
- **Movie-vs-TV field asymmetry is the only real divergence from games.py.** TMDB splits fields by media type: movies carry `title` / `release_date` / `runtime` / `production_companies`; TV carries `name` / `first_air_date` / `number_of_seasons` / `networks` / `created_by`. Normalized behind `_title()` / `_date_str()` / `_media_label()` helpers so the mode functions stay readable. `_media_label` infers movie-vs-TV three ways in priority order: an explicit `media_type` (present in `/search/multi` + `/trending`), the endpoint the caller used (a typed `/search/movie` omits `media_type`, so callers pass `forced=`), then a TV-only-field heuristic as a last resort.
- **`similar` is a clean 2-hop, NOT M22's 3-hop workaround.** RAWG's `/games/{id}/suggested` turned out to be paywalled in M22, forcing a genre+tag fallback. TMDB exposes `/<type>/{id}/recommendations` on the free tier — its tuned engine (the one their own UI surfaces), strictly better than the coarser `/similar`. So `_do_similar` is just `search → resolve (id, media_type) → /recommendations`. The endpoint choice is documented inline so a future reader doesn't "fix" it to `/similar`.
- **Voice-friendliness touches.** `_runtime_str` renders `155 → "2h 35m"` (TTS reads "two hours thirty-five" far better than "one hundred fifty-five minutes"); `_rating_str` suppresses TMDB's `0.0/10 (0 votes)` seed values on unreleased titles (otherwise Jarvis would say "rated zero out of ten" for an unannounced film); genres are intentionally omitted from `search`/`popular` briefs (those payloads only carry `genre_ids`, not names — resolving them is an extra call per result; `details` carries named genres) — the same lean-brief tradeoff as `games.py._format_brief`.
- **The `media` filter is silently-widening, not erroring.** An unknown/absent spoken media word → `None` → search both / trend across all, rather than M22's platform-style "unknown X" error. Rationale: `media` is an *optional narrowing the user often didn't say at all* ("what's trending?"), whereas a RAWG platform is something the user explicitly named; rejecting a fuzzy/absent media word would be a worse voice experience than just widening. Persons are stripped from `/search/multi` results (a "what has X been in" feature is explicitly out of scope — noted as a follow-on).

## Milestone 44 — the OOM post-mortem: ultralytics-in-a-loop leak fix + a process memory watchdog

- **Trigger: a real production incident, not a planned feature.** Security mode was left armed and unattended for an extended period. At the end of that window the machine was unusable and required a hard reboot. `jarvis.log` showed a `MemoryError` deep in openWakeWord's `model.predict` (`utils.py:_streaming_melspectrogram`) plus a cascade of `[security] frame grab failed: ... Insufficient memory` OpenCV `OutOfMemoryError`s. The crash *site* was a red herring — a few-KB melspectrogram slice only fails when the machine is already exhausted.
- **The trace that named the culprit (the value of looking past the stack):** Windows' own `Microsoft-Windows-Resource-Exhaustion-Detector`, System log, **Event ID 2004**, fired twice (13:12:05 and 13:17:05 on 2026-05-16): *"pythonw.exe (6664) consumed 33,981,431,808 bytes"* — i.e. `jarvis.pyw` alone held ~**31.6 GB** and was still climbing (+1.2 GB in the 5 min between the two events). Discord/msedgewebview2/MBAMService in the same events were 300–500 MB each — normal, red herrings. Jarvis started 12:21:24 and hit ~30 GB by 13:12 (~50 min). The box is **9.9 GB physical / 15.4 GB commit limit** (RAM + 5.5 GB pagefile), so Jarvis didn't just fill RAM — it blew past the *system commit limit*, which is why every process (not just Jarvis) starved and a hard reboot was the only way out. ~30 GB ÷ (1 poll / 2 s over 50 min ≈ 1500 ticks) ≈ **~20 MB leaked per watcher tick**. Lesson recorded: **on an OOM, the Python traceback points at the victim; the Windows Resource-Exhaustion-Detector (Event 2004) points at the cause.** That event literally enumerates the top virtual-memory consumers at diagnosis time — first stop for any "what ate the RAM" post-mortem on Windows.
- **Attributed root cause (later falsified — see M44.3): `ultralytics` `model(frame)` called in the armed watcher's 2 s loop.** The reasoning at the time: this is the textbook ultralytics long-running-loop leak — the predictor retains `Results` objects across calls, each holding `.orig_img` (the full frame) in a reference cycle that plain refcounting never reclaims. At 0.5 Hz, unattended, for ~50 min, it would compound to OOM, and the ~20 MB/tick magnitude appeared to match the ultralytics signature. The secondary suspect — `cv2.VideoCapture(..., CAP_DSHOW)` open/close churn every 2 s, a documented Windows native-handle leak — was judged real but a much smaller term. **Neither attribution was ever measured. M44.3 later proved the ranking was inverted:** the capture churn was the entire leak and ultralytics was flat. The wrong turn is left in the record deliberately; the correction is the point.
- **Secondary latent leak found while investigating: `wait_for_wake_word` rebuilt a fresh openWakeWord `Model()` every wake→process→respond cycle** (`main.py:460` is the sole caller, looping). ONNX Runtime inference sessions are notorious for not fully releasing native memory on GC, so every voice round-trip leaked tens of MB. *Not* the incident's cause (only one Model was alive during the unattended window — the loop was parked in `listening`), but a genuine bug on the active-use path. Fixed in the same pass: a process-wide singleton built once and `reset()` between cycles (the installed openWakeWord `Model` API confirmed to expose `reset()`). `_ensure_models_downloaded()` moved into the one-time init — the old code re-hit that disk/network check every wake cycle for no reason. Threading invariant documented: single consumer thread (`listen_loop`), so the singleton needs no lock; a future cross-thread caller must add one.
- **The persistent-camera trade-off (decided and recorded so it isn't re-litigated).** The originally-scoped "hold `VideoCapture` open while armed" would have eliminated the DSHOW-churn term *and* the ~3-4 s DSHOW init per tick — but DirectShow allows only one capture per device, and the watcher shares device 0 with the `camera_snapshot` tool ("what do you see?") and face enrollment. Holding it open would make both fail with "camera in use" for the entire armed duration — a real regression to a working feature, in exchange for what was *believed* to be a minor leak term already backstopped by the watchdog. Decision at the time: **keep the camera open-on-demand**; rely on the ultralytics fix for the (assumed) dominant leak and the watchdog for everything else. (Challenge-time face auth reuses the watcher's already-grabbed frame, so it has no camera-contention issue either way.) This is the same "smallest change that actually solves it, don't regress working features for marginal gain" discipline as the M43 `functools.partial` call-site decision — **but here it was applied on top of an unmeasured premise, and it deferred the actual fix by two milestones.** M44.3 revisits it and finds the scoped version (persistent capture bounded to armed lifetime) costs nothing.
- **The fix, three parts:**
  1. **`src/security.py` `_detect_person`** — the YOLO result scan wrapped in `try: … finally: del results` so the reference drops on *every* exit including the early short-circuit `return True`. `del` alone reclaims only the acyclic portion.
  2. **`src/security.py` `_watch_loop`** — `gc.collect()` once per poll iteration (placed before the normal-path sleep, after the inference path). At the 2 s cadence the cost is sub-millisecond; this was believed to be what breaks ultralytics' predictor reference cycle. (It does not — the leak was native, with zero Python objects involved. See M44.3.) `import gc` added.
  3. **`src/wake_word.py`** — the Model-reuse singleton described above.
- **The structural backstop: a psutil RSS watchdog (the load-bearing part).** `SecurityWatcher._check_memory_watchdog(proc)` runs once per watcher tick (right after `_check_challenge_timeout`, before the frame grab). It reads process-wide RSS via a `psutil.Process()` handle resolved once at loop start; if RSS ≥ `_MEMORY_WATCHDOG_MB` it logs a loud `MEMORY WATCHDOG TRIPPED` line, speaks *"Sir, I'm consuming an unusual amount of memory. I'm standing down as a precaution."* (routed through the injected `self._announce` → main.py Announcer thread, per the WASAPI thread-affinity constraint — **never** a direct `speak_streaming` from the watcher thread), calls `_auto_disarm()`, and the loop returns. **Why this is the milestone, not the leak fix:** the leak fix patches *this* leak; the watchdog ensures the "never crash the listening loop / degrade gracefully" rule — which failed here at the *process* level, taking down the whole machine — is enforced where it failed. Any future in-process leak (this thread OR another, since RSS is process-wide) should degrade to a logged auto-disarm instead of a forced reboot. Threshold 1500 MB: assumed comfortably above realistic baseline (torch CPU + YOLO + openWakeWord ORT + Tk ≈ 0.5–1 GB; STT is offloaded off-box per M36) and far below the 9.9 GB / 15.4 GB ceilings. Override via `JARVIS_MEMORY_WATCHDOG_MB`; `<= 0` disables it. Defensive on every axis (None proc / disabled / psutil read error all return False quietly) — the guard must never itself become a new failure mode. `import os` added for the env read; `psutil` lazy-imported in the loop (declared dep since M23; missing → watchdog disabled with a log line, watcher still runs). **Both the metric (RSS) and the threshold (1500) turn out to be wrong — M44.1 corrects the threshold, M44.2 corrects the metric.**
- **Known scope boundary (documented, not a bug):** the watchdog only runs while security is armed, because that's the only time the watcher thread exists — and "armed + unattended" is exactly the catastrophic scenario. An always-on, arm-state-independent process memory guard (e.g. in `main.py`'s loop or a dedicated daemon) is a clean follow-on if a leak ever bites on the non-armed path; deliberately not built speculatively (same "iterate on real usage" discipline as M22/M42).
- **Verification:** close-out sanity gate `python -m py_compile main.py jarvis.pyw src/*.py` clean; import smoke on both changed modules (`src.security._MEMORY_WATCHDOG_MB == 1500`, `src.wake_word._get_model` present, `_model` lazily `None`). Live end-to-end armed re-validation deferred — the defensive contract means Jarvis runs normally regardless, and the incident is reproducible only over ~tens of minutes of armed runtime. **In hindsight this deferral is the mistake that made M44.1/M44.2 necessary: the entire arc was shipped without a reproduction.**
- **What's NOT in M44 (deferred / rejected, so future work doesn't redo the analysis):**
  - **Persistent camera while armed** — rejected, see the trade-off bullet above (believed to regress `camera_snapshot`/enrollment for marginal, watchdog-covered gain). *This rejection is reversed in M44.3, where it turns out to be the actual fix.*
  - **Pinning/upgrading `ultralytics`** to a version claiming the loop leak is fixed — the `del` + `gc.collect()` workaround is version-independent and the accepted community remedy; chasing a "fixed" version is fragile vs. a 2-line guard that always holds. (Moot: ultralytics was not the leak.)
  - **Arm-state-independent process watchdog** — see scope-boundary bullet; clean follow-on, not built speculatively.
  - **Auto-restart on watchdog trip** (vs. auto-disarm) — rejected: auto-restarting an OOMing process risks a restart loop, and silently re-elevating/re-arming violates the project's least-privilege rule (never default to elevated or persistent privilege; power is opt-in, narrow, audited). Auto-disarm + a spoken heads-up + a loud log line is the least-surprise, least-privilege response; re-arming stays a deliberate human action.
- **Files touched:** `src/security.py` (+~55 lines: `import gc`/`import os`, `_watchdog_limit_mb` + `_MEMORY_WATCHDOG_MB` module constant, `try/finally del results` in `_detect_person`, psutil handle + watchdog call + `gc.collect()` in `_watch_loop`, new `_check_memory_watchdog` method); `src/wake_word.py` (+~30/-3 lines: module singleton + `_get_model()`, call-site swap, `_ensure_models_downloaded` moved into one-time init); `.env.example` (+`JARVIS_MEMORY_WATCHDOG_MB` block, matching the existing `JARVIS_*` tunable doc style — added during M44 close-out QA, which caught it missing); `CLAUDE.md` (status rewrite + this milestone's strike in "Possible future work"/"Known unknowns"); `docs/MILESTONES.md` (this entry).

### M44.1 — Watchdog threshold recalibration (false-positive post-mortem, 2026-05-17)

- **Trigger:** the day after M44 shipped, security mode was armed and the
  watchdog *immediately* tripped: `MEMORY WATCHDOG TRIPPED: process RSS 1501 MB
  >= 1500 MB limit`. The obvious first reading was that the M44 leak had recurred
  and the backstop had caught it. Log analysis said otherwise.
- **What the log actually showed** (`jarvis.log`, session started
  `2026-05-17T13:14:13`, the *elevated* relaunch child): `watcher loop started`
  and `MEMORY WATCHDOG TRIPPED` are **consecutive lines**. It tripped at
  **1501 MB — 1 MB over threshold — on the first watcher tick**, on a process
  **~1 minute old**. The suspected M44 leak source (`self._model()` in
  `_detect_person`) had not executed even once. The real M44 incident was ~30 GB
  over ~50 min; this was +1 MB at t≈0. **No leak — there was no time for one.**
- **Root cause:** the 1500 MB default was a *guess*. The M44 code comment
  estimated armed baseline at "0.5–1 GB" — wrong. It omitted torch CPU's real
  resident footprint and the M39 dlib/`face_recognition` stack (face auth was
  loaded this session; `jarvis.log`: `face auth enabled — enrolled encoding
  loaded`). The true cold-start armed baseline is **~1.5 GB**, so the watchdog
  fired on the legitimate baseline and made security mode **unusable** (it
  self-disarmed within one tick of every arm).
- **The honest split:** *Good* — the M44 mechanism is sound; detect → announce →
  auto-disarm → clean exit executed flawlessly, and the leak-mitigation code
  (`del results` + `gc.collect()`, the `wake_word` ORT fix) is untouched, with no
  evidence at this point that the 30 GB leak had recurred. *Bad* — the threshold
  was calibrated against a wrong baseline *estimate* instead of a *measurement*.
- **Fix:** default raised **1500 → 3500 MB** (`src/security.py`
  `_watchdog_limit_mb`, both literals), `.env` set to 3500, `.env.example`
  block + the stale `security.py` "0.5–1 GB" comment rewritten with the
  *measured* baseline and the "set ~2x measured baseline" rule. 3500 is ~2.3x
  the ~1.5 GB measurement: never trips on baseline, still far below the 9.9 GB
  physical / 15.4 GB commit limit, still catches a real runaway (M44 = ~30 GB)
  long before danger.
- **Lesson (reusable):** a graceful-degradation backstop calibrated against an
  *estimated* baseline instead of a *measured* one will false-positive on the
  baseline and disable the feature it was meant to protect. The first real arm
  *was* the measurement; the threshold should have been a post-measurement
  follow-up in M44, not a guessed constant.
- **Test-method caveat:** to validate that the *real* leak is gone, an armed-soak
  test must keep YOLO running. Covering the camera **lens** is valid —
  `_grab_frame()` still `read()`s a (dark) frame, so `self._model()` runs every
  ~2 s (the suspected leak path) without triggering detections/deterrent.
  **Unplugging** the camera is NOT valid — it hits the `frame is None` branch and
  skips YOLO entirely (the path under test is never exercised → a false "all
  clear").
- **Still pending:** the M44 end-to-end soak (arm 30+ min → 60 min → overnight,
  lens covered, watch RSS stay flat in `jarvis.log`/Task Manager). Now
  *possible* — pre-fix it self-disarmed in one tick. Target bar: a 1–2-day
  continuous armed uptime, not 30 min.
- **Files touched:** `src/security.py` (default 1500→3500 ×2 + comment
  rewrite); `.env` (`JARVIS_MEMORY_WATCHDOG_MB=3500` + rationale comment);
  `.env.example` (watchdog block rewrite); `CLAUDE.md` (M44 status + Known
  unknowns); `docs/MILESTONES.md` (this entry).

### M44.2 — Watchdog metric fix: RSS → private bytes + system floor (post-mortem, 2026-05-17)

- **Trigger:** the first real armed soak after M44.1. ~30 min of healthy
  operation, then a full machine lockup roughly an hour in. Hard reboot required.
- **Forensics (Event 2004, the M44 technique):** `pythonw.exe (PID 20808)`
  held **37 GB virtual memory**, climbing 36.4→37.1 GB across 17:36–17:56.
  The leak recurred *at full force* — the M44 `del results` + `gc.collect()`
  mitigation did **not** stop it (separate, still-open root cause = M44.3).
  Process log end-state: a 6 MB OpenCV frame alloc failing, openWakeWord
  `MemoryError`, tray thread dead — total commit exhaustion (~16 GB ceiling:
  9.9 GB RAM + 6 GB pagefile).
- **The decisive finding — the guard never tripped.** Full grep of the
  16:14 soak session: zero `MEMORY WATCHDOG TRIPPED`, zero `memory watchdog
  read failed`, zero `psutil unavailable`. The watchdog ran every tick,
  read its metric, compared, and stayed silent while commit hit 37 GB.
- **Root cause — wrong metric.** The guard watched **RSS** = the Windows
  *working set* (resident physical pages). The leak grows **commit / private
  bytes**; under memory pressure Windows aggressively *trims the working
  set*, evicting pages so RSS stays bounded while private bytes explode. RSS
  is the one number Windows actively suppresses during exactly this failure
  — an RSS guard is *precisely backwards* for it. Sharpest framing: it
  **false-tripped on the harmless thing** (the 1501 MB cold-start
  working-set spike, M44.1) and **stayed silent on the lethal thing**
  (37 GB commit). The original M44 Event-2004 line already said "virtual
  memory," never "working set" — the signal was present in the first
  post-mortem and the guard was built on RSS anyway.
- **Fix (this entry):** `_check_memory_watchdog` rewritten to two
  independent triggers — (a) process **private bytes**
  (`psutil … memory_info().private`, the Windows Private-Bytes / per-process
  commit field; the metric that actually grew to 37 GB),
  `JARVIS_MEMORY_WATCHDOG_MB` default 3500; and (b) a **system available
  memory** floor, `JARVIS_MEMORY_MIN_AVAIL_MB`, default 512. (a) is
  load-bearing: the M44.2 leak was *this process's own* private bytes, so
  3500 alone trips within minutes, far below danger. (b) is the
  leak-source-agnostic net for leaks (a) can't see (e.g. an MCP child) — and
  structurally defuses the M44.1 calibration trap, since the universal "box
  is dying" trigger no longer depends on nailing a per-process number.
- **Live-measurement honesty (the M44.1 lesson, applied immediately):** a
  pre-ship `psutil` probe showed this box idles at **~1.2 GB
  system-available while unarmed**. A 1 GB floor would M44.1-false-trip on
  every arm (arming loads ~1.5 GB of ML stack). So (b) ships at 512 — an
  explicitly *guessed-low conservative placeholder pending a real soak
  measurement, NOT a calibrated value*, documented as such in code and
  `.env.example`. Same discipline as M44.1: loose first, calibrate from
  measurement, never trust a guessed fail-safe constant.
- **Verification:** a `psutil` probe confirmed `memory_info()` exposes
  `private` on Windows (field present in the named tuple); `getattr(…,
  "private", None)` + rss fallback so it degrades, not crashes, off-Windows.
  Sanity gate (full `py_compile`) passes.
- **Reusable lessons:** (1) on Windows, a memory backstop must watch
  **commit / private bytes** (or system commit), never the working set —
  the OS suppresses RSS under exactly the pressure you're guarding against;
  the Task-Manager analog is "Commit size", not "Memory (working set)".
  (2) The robust backstop is the **leak-source-agnostic system check**
  ("is the machine in danger"), not a proxy for one leak's assumed shape; build
  the universal trigger and the per-process number stops being load-bearing.
- **Still open (M44.3 — separate):** the leak *itself* is not fixed — M44's
  `del`/`gc.collect()` didn't hold under the covered-lens soak. Its own
  root-cause hunt remains (covered-lens dark-frame YOLO path? ultralytics
  version? a source outside `_detect_person` entirely?). The M44.2 guard makes
  this fail *safe* (auto-disarm before lockup), not absent. **Do not leave the
  system armed unattended until M44.3** — the guard now prevents machine death
  but Jarvis will still self-disarm under the live leak.
- **Files touched:** `src/security.py` (`_watchdog_min_avail_mb` +
  `_MEMORY_MIN_AVAIL_MB`, comment-block rewrite, `_check_memory_watchdog`
  two-trigger rewrite); `.env` and `.env.example` (added
  `JARVIS_MEMORY_MIN_AVAIL_MB`, metric-change docs); `CLAUDE.md` (status +
  Known unknowns); this entry.

### M44.3 — Leak root-caused & fixed: per-tick camera open/release (2026-05-17)

- **Method:** built `scripts/leak_repro.py` — an instrumented reproduction +
  bisection harness (psutil private/RSS + tracemalloc, hard self-safety
  caps, toggleable mitigations). It compresses the ~90-min armed soak to
  minutes by running the watcher's hot path flat-out. **Reproduce →
  instrument → bisect → fix → verify**, the named loop, applied specifically to
  defeat the guessing that produced M44 and M44.1.
- **The differential matrix (all measured, not assumed):**

  | Config | Result |
  | --- | --- |
  | Inference only, no camera, 600 iters | −0.4 MB — **flat; ultralytics exonerated** |
  | DSHOW open-per-tick (production as written) | ~+160 MB/iter — hit a 2.2 GB cap in **10 iters** |
  | MSMF open-per-tick | +3 MB/min — ~1600× smaller but still a real leak |
  | **DSHOW persistent (open once, read per tick)** | **dead-flat over 400 reads — FIX** |

- **Root cause:** the leak is the **per-tick `cv2.VideoCapture(idx,
  CAP_DSHOW)` open → read → release** in `_grab_frame()` — a *native*
  (C/C++) DirectShow capture-graph/buffer leak (RSS flat while private/
  commit explodes — the exact M44.2 signature, and precisely why
  `gc.collect()` was useless: zero Python objects are involved). **NOT
  ultralytics.** The M44 and M44.2 code and doc attributions to "ultralytics'
  predictor reference cycle" were an assumption that had gone unmeasured for two
  milestones — **falsified by the first 600-iter run.** The correction is
  recorded in place rather than quietly overwritten: the arc's value is that the
  wrong attribution survived two ships and was killed by one measurement.
- **The fix:** `_grab_frame()` now opens **one** `VideoCapture` (DSHOW —
  kept; see backend note), reuses it every poll, and releases it in
  `_watch_loop`'s `finally` via the new idempotent `_release_cap()`. ~2,700
  open/release cycles per soak → **one**. Self-healing: any read failure
  drops the capture so the next poll transparently re-opens. Strictly

- **Why FTS5 and not embeddings (yet):** `sqlite3` with FTS5 ships in CPython's stdlib on Windows — **zero new heavy deps, fully local, privacy-aligned**. v1 proves the entire ingest → tool → "update" UX loop on keyword search before any embedding infra. FTS5 specifics: `porter unicode61` tokenizer (so "restarting" matches a query for "restart" — high-value on a small corpus), `path UNINDEXED` (stored to name the source file, not searched), `bm25()` ranking, `snippet()` for focused excerpts.
- **Query sanitization (the non-obvious correctness bug avoided).** FTS5's MATCH grammar treats `" * ( ) : - ^ AND OR NOT NEAR` as operators; raw voice transcripts contain them freely ("what's my printer's temp?") and an unescaped one raises `sqlite3.OperationalError: fts5: syntax error` — i.e. the tool would crash on perfectly normal questions. `_build_match_query` reduces the query to bare alnum tokens, drops stopwords, and OR-joins them double-quoted as literals. **OR not AND** is a deliberate recall-over-precision call for a small personal corpus: better to surface a loosely-related passage and let Claude judge it than to return nothing on a slightly-off phrasing. Smoke-tested against deliberate syntax-bait queries.
- **Heading-context chunking.** Chunks split on blank-line paragraph boundaries up to a ~1200-char cap (never mid-paragraph unless one paragraph alone exceeds it). The nearest preceding Markdown heading is carried into each chunk as a one-line prefix — so a paragraph under `## Proxmox` becomes findable by a "proxmox" query even when that word isn't in the paragraph. ~15 LOC for a real recall win; the embedding layer (M46) is the escalation if this heuristic ever stops being enough.

### Security armed-mode TTS-stutter post-mortem — the cooperative speech gate (2026-05-19)

**Numbering:** recorded as a non-numbered post-mortem on the M34 security
subsystem (precedent: the "Telemetry refactor (post-M28)" entry). It's a
*fix to an existing milestone*, not a new capability; consuming a fresh
integer would also collide with the reserved M48. A documented number stays;
a fix doesn't take one.

**Symptom (live report).** While security was *armed*, Jarvis's spoken
announces intermittently but *strongly* stuttered. Never reproduced unarmed
(questions, video playback all clean) — that isolation to armed-mode was the
load-bearing clue.

**Diagnostic signature.** jarvis.log only ever logged `[audio] status:
input overflow` — the *mic capture* buffer overflowing — never an output
underrun (the TTS path has no status callback; only the `InputStream` in
`audio.py` logs status). The realization: input-overflow is the
*instrumented* side of the *same* thread-starvation that underruns the
*uninstrumented* output buffer. Overflow clusters lined up exactly with
armed/camera/YOLO activity. Armed-only + input-overflow-tracks-watcher ⇒
the watcher thread was starving the Python-fed audio threads (shared GIL +
CPU). Lesson: an instrumented symptom on one side of a shared resource can
localize an uninstrumented failure on the other side.

**Three distinct mechanisms behind one symptom:**
- **A — uncapped torch.** No `set_num_threads` anywhere; torch defaults its
  intra-op pool to physical-core count (measured: **4** on this Ryzen 5
  3400G). Every 0.5 Hz YOLO inference pinned all cores ~200-400 ms →
  starved audio. Fixed: `JARVIS_YOLO_THREADS` (default 1) applied via
  `torch.set_num_threads` at YOLO load. Measured 4→1. Steady-state term.
- **C — cold face/dlib stack faulted on the hot path.** `import
  face_recognition` (builds + loads dlib detector / 68-pt predictor /
  ResNet — measured ~2.7-2.9 s, GIL-held) was lazy and first ran inside
  the first CHALLENGE, concurrent with the "identify yourself" prompt
  (the `face_recognition_models`/`pkg_resources` warning interleaved with
  it in the log). First fix attempt (warm via a *blank* `verify_frame`)
  was doubly flawed: it ran concurrently with the "standing watch"
  announce (relocating the stutter, not removing it) AND a blank frame →
  no face → `face_encodings` never ran, so the **encoder JIT stayed
  cold** and still faulted on the first real challenge face. Measured:
  even fully warm, each encode inherently costs **~437 ms** (ResNet
  forward pass — not a JIT artifact).
- **B — vestigial per-tick `gc.collect()`.** Leftover from the *falsified*
  M44 "ultralytics reference cycle" theory (M44.3's repro harness
  exonerated ultralytics). A GIL-holding steady-state contributor that
  was never actually needed for the (camera-open/release) M44 leak.

**The meta-lesson — stop point-fixing.** A (torch cap) shipped and
confirmed; the stutter moved. C-attempt-1 relocated it onto a different
announce. Four rounds of moving individual heavy ops around is whack-a-mole
by construction: the root is architectural, so relocating a burst just
stutters whichever announce the *next* burst overlaps. When point-fixes
don't converge, escalate to the architecture.

**Architectural root + fix.** Heavy watcher/vision bursts (camera grab,
YOLO + the per-tick `gc.collect`, face encode, the cold-start warm) and the
Python-fed proactive-TTS path share the GIL + CPU; *any* overlap underruns
the audio buffer. Fix = make them **mutually exclusive in time**:
- A shared `threading.Event` (`announce_speaking`) the Announcer thread
  brackets around actual `speak_streaming` playback (set before, cleared
  in `finally` so a TTS failure can't wedge it), passed into
  `SecurityWatcher`.
- `_watch_loop` defers the entire heavy block (grab/YOLO/gc/face-auth) for
  any tick where `_is_announcing()` — the cheap timeout + memory-watchdog
  checks stay live (safety). The cooperative gate.
- `face_auth.warm()` now replays the **full** path including the encoder
  (forced via an explicit synthetic `known_face_locations` box — runs the
  pose predictor + ResNet with no real face needed), and the watcher runs
  it only **after the arm announce goes quiet** (`_wait_for_quiet`, bounded
  so a dropped announce can't deadlock).
- Announce strings tightened to the persona spec ("Standing watch, sir." /
  "Identify yourself, sir.") — also a smaller collision surface.

**Why the gate is load-bearing (measured, not assumed).** `warm()` removes
the *one-shot* 2.7 s cold cost, but each encode *inherently* costs ~437 ms
forever. Completing the warm *alone* would still stutter the prompt — the
gate is what guarantees that recurring ~437 ms encode (and YOLO, and gc)
never overlaps an announce. This measurement is the proof the architectural
fix was necessary and the half-measure (warm-only) would have failed. **B
is absorbed** — the per-tick `gc.collect()` no longer matters because it
can't overlap speech; it is no longer a separate open item.

**Recorded trade-off (conscious, not buried).** The gate defers detection
for the ~1.5-2 s an announce plays. Safe by design: the 30 s arm-grace
covers it, the challenge timer only starts *after* its prompt, voice-
passphrase auth runs on a different thread (unaffected), and announces are
short and discrete (arm/challenge/deterrent/welcome/standdown), never a
continuous stream that could starve detection.

**Reusable lessons:** (1) an instrumented symptom on one side of a shared
resource (mic input-overflow) localizes an uninstrumented failure on the
other (TTS output underrun). (2) torch defaults intra-op threads to
physical-core count — cap it for *any* inference sharing a box with a
real-time audio path. (3) a warm-up must replay the real hot path
*including its heaviest sub-op*, and you must *measure* that warm-alone
suffices — here it didn't (437 ms recurring), so the gate was required.
(4) when relocating a burst just moves the stutter, the fix is to sequence
the contending work, not relocate it again. (5) `[audio] status: input
overflow` is now a known armed-mode-health grep.

**Status: live-validated by ear 2026-05-19** — both "Standing watch, sir."
and "Identify yourself, sir." clean, no input-overflow at the announces.
A + B + C all subsumed under the one architectural fix.
