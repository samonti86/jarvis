# Jarvis — Engineering Log

This is the milestone-by-milestone build log for Jarvis, a Windows always-on
voice assistant: wake word → local Whisper STT → the Claude API driving an
agentic tool loop → streamed TTS, plus ~40 tool integrations, a vision/security
subsystem, a phone PWA client, and a proactive monitoring layer. It was built
incrementally over ~88 milestones.

It is an engineering log, not a changelog. Each entry records what shipped, the
architectural decision behind it, and the trade-off that was accepted. It also
records the things that went wrong: the post-mortems, the misdiagnoses, the
conclusions that were written up confidently and later retracted when the
evidence failed to support them, and the features that were built correctly and
then shelved because they did not solve the real problem. Those entries are kept
deliberately — a build log that only records successes is not a useful engineering
artifact.

## Start here

Six entries that carry the most engineering, if you want to skim rather than
read 105 of them. Each is a case where the first answer was wrong.

| Entry | Why it's worth reading |
|---|---|
| [M44 — the OOM arc](milestones/part-2.md#milestone-44--the-oom-post-mortem-ultralytics-in-a-loop-leak-fix--a-process-memory-watchdog) | A memory leak blamed on the ML library for two milestones. An instrumented repro harness falsified that and found the real cause: a per-tick video-capture handle. Also where the metric itself turned out to be wrong — RSS was hiding the growth; private bytes showed it. |
| [M52 — WASAPI thread affinity](milestones/part-3.md#milestone-52--barge-in-interrupt-jarvis-mid-reply) | Windows audio is thread-affine. Calling `sd.stop()` off the stream's owning thread doesn't fail — it hard-crashes the process. The fix was an ownership rule, not a try/except. |
| [M67](milestones/part-4.md#milestone-67--armed-stutter-regression-fix-acoustic-speech-gate--mic-device-pin) → [M68](milestones/part-4.md#m68--the-armed-turn-reply-stutter-root-caused--fixed--live-validated) — the two-sided gate | M67 shipped a fix and declared victory; M68 found the bug M67 missed. A cooperative gate has two halves — every consumer that yields *and* every producer that raises it — and only testing one half is how a "fixed" regression comes back. Includes the retraction. |
| [M80 — speaker-ID threshold](milestones/part-5.md#m80--identity-aware-replies-jarvis-addresses-the-recognized-speaker-by-name--2026-06-12) | Why you cannot tune a recognition threshold on scores alone. The number only means something once correlated with the transcript that produced it. |
| [M46 — semantic search that couldn't prove a win](milestones/part-3.md#milestone-46--hybrid-semantic-search-for-the-knowledge-base-the-reserved-conditional-follow-on-shipped) | Built correctly, shipped, and honestly recorded as *not demonstrably helping* — the corpus was too small to show a difference. The limiter was data, not algorithm. |
| [M88 Phase 2 — the feature that was shelved](milestones/part-5.md#m88-phase-2--hands-free-talk-over-aec-de-risk-viable--2026-06-15) | Hands-free interruption worked mechanically and was shelved anyway: once echo is cancelled, an energy gate detects the *presence* of sound, not the *intent* to interrupt. Working ≠ right. |

Written to be read by engineers. Dense on purpose.
